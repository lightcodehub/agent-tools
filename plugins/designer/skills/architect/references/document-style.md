# 产出文档表达规范

适用对象为 skill 交付的设计文档、API 文档、使用说明和测试报告。以下条目是生成与检查这些文档的执行指令，不是需要复制到成品中的正文。architect、developer、validator 各携带同文副本，随插件独立分发。

Skill 本体按 Agent Skills 规范组织元数据、执行指令与引用资源；产出文档按以下质量要求编写。表达调整不得改变业务规则、模板结构、角色权限或验证要求。

## 文档生成、修改与核查

生成、修改、核查文档时，先确定授权范围、文档类型和适用的 skill 规则，从负责该类文档的 skill 或项目明确指定的位置读取模板的适用部分。没有专用模板的文档按 skill 对该类文档的要求核查。设计文档须执行 architect 随附的 `references/design-audit.md` 核查步骤及 `scripts/audit_design.py` 盘点。该插件不可用时，按适用模板建立等价的逐文件、逐项、逐契约清单并核实。全仓任务将总设计索引与实际文档目录交叉盘点，覆盖每份范围内文档。用户举例只提供线索，明确限定范围时才缩小检查或修改范围。

- **格式**：从模板的必需章节、条件章节、字段、表头及定位要求出发逐项、逐行对照成稿，包括应有却缺失的字段或链接。条件章节按项目事实判断是否适用。
- **内容**：按文档用途核实需求、已审核设计、实际接口、调用关系、测试断言或运行证据。依赖表逐行核对“预期用途”，从“关联接口或类型”中的名称分别打开定义，确认实际调用或引用与目标一致。调用方表核对真实使用方式和兼容约束。
- **结论**：生成或修改后读回最终版本，复查范围内同类位置，包括沿用的旧行。在可写范围内修正偏差，仅核查时给出位置、要求与实际差异。必需项有偏差即不符合，依据或模板无法取得时说明未核实项及影响。完整符合须有格式和内容两方面的证据。

## 内容与语气

- 面向未参与对话的读者，直接说明对象、行为、条件和边界。段首先给出设计结论或规则，必要时说明依据、影响与取舍，读者无需回看聊天即可理解和执行。
- 使用自然、克制的专业书面语。主语明确、动词具体，句子按逻辑衔接；避免口语填充和夸张修辞，不虚构经验。
- 正文不记录请求、答复、澄清轮次、操作经过或角色交接过程。不写“根据你的要求”“经过讨论”“我先检查了”“我们又调整为”等对话措辞；将已确认内容直接写成有效规则。
- 同一概念使用同一术语；保留准确的接口名、字段名、单位、条件、状态和用例编号。避免用“相关处理”“适当优化”“充分保障”等模糊措辞代替可核验要求。
- 每句话承载必要信息，删除重复解释、套话和无依据的效果评价。精简不能省略异常行为、兼容约束、风险、适用范围或必要证据；不为改善句子而补造事实。
- 已确认事实、设计要求、待核实假设与建议分开表达。证据不足时写明未知项和影响，不把建议写成已实施，不把计划验证写成验证通过。

## 结构与呈现

- 总文档 §5.1 按公共代码规范固定使用三列、八个规范项及其顺序；无对应机制也简述实际边界与核验方法，不以“内容按需”改变格式或覆盖范围。表内只写公共约定和引用，具体业务行为在模块文档维护。
- 沿用既定章节、编号、表格字段和状态定义。段落用于解释规则与依据，列表用于并列事项或执行步骤，表格用于契约、映射和结果比较；不为追求短句把完整逻辑拆成零散词组。
- 填充模板后删除占位符、填写提示和面向生成者的操作说明；保留有实际值的元信息、契约及必要约束。文件头按适用模板填写字段及顺序。“所属设计”使用总设计一级标题的完整可见文字并链接首页；“所属服务”使用服务总览标题中的服务名并链接总览首页。示例、引用和跨文档术语保持一致。
- 设计正文中的状态字段只保存当前值，验收章节说明技术验收条件与核验方法；不追加本次只做设计、角色交接或谁负责将状态改为完成等管理说明。测试报告仍按既定结构记录实际验证范围、状态与后续责任方。
- 更新文档时原位维护有效内容，不追加会话摘要、修复经过、新旧方案回顾或按日期排列的讨论记录。当前有效的执行步骤和技术依据可以保留。
- 文档表达与聊天汇报分开：聊天可说明工作进度、改动范围和交接情况，不将这些叙述复制进正文，也不以聊天代替必需文档内容。

## Markdown 紧凑格式

- 表格保持正确列数和对齐语义，单元格边界保留一个空格，不按最长内容填充列宽。分隔行使用 `---`，需要左、中、右对齐时分别使用 `:--`、`:-:`、`--:`。
- 普通段落不按列宽硬换行，保留段落间空行、列表缩进、标题层级及有语义的硬换行。紧凑格式不压缩正文或合并不同事项。
- 章节引用写明标题。模块与功能索引、跨文档契约直接链接到目标；普通正文写清章节标题即可。
- 正文和表格中的命令、路径、文件名、标识符、签名、正则、通配符及输入输出字面值使用行内代码；多行内容使用带语言标记的代码块。有效 Markdown 链接可保留，不把链接语法包进代码。普通技术概念无需代码格式。
- 以最终文件在目标 Markdown 方言中的渲染为准。逐个正文块、标题、列表项及表格单元格核对普通文本、行内代码、强调和链接的边界，包括连续选项、跨行文字与显式转义；对照命令声明、交互说明或用例断言，按完整调用核实程序名、子命令、参数及参数值；输入键、组合键、终端显示值和协议字面值同样核实。检查代码节点两侧的普通文本，避免只标参数而漏掉命令名。作为可直接执行的完整调用时，命令名、参数和取值放在同一代码片段，正文分别说明多个元素时各自标记。用例中的参数化实例名、驱动或协议返回的多词字段名、用于匹配的输出和筛选命令，按测试或契约中的原拼写及分隔符渲染。类别标签作为整体显示，例如分类名不应只把末词标成代码；不改写可执行筛选器中的真实匹配串。通用名词与自然语言按其在句中的含义判定。按模板核实表格字段与单元格里的链接是否真正渲染出来。合法的含反引号字面值、带空格的命令、链接标签内的代码可以保留。疑点按上下文与真实契约逐项判定，修订后重新渲染；未取得渲染结果或仍有未经核实的疑点时，整稿格式列为未核验。
- 检查 Markdown 解析后的技术文本，避免下划线、星号、反引号或表格竖线被当作格式语法而丢失、拆列。必要时选择合适的代码定界符或转义，保持实际显示与原字面值一致；不得改动命令、链接目标、正则、样例值或有意义空白。格式化工具通过不等于语义显示正确。
- 使用 Prettier 时，仅对 Markdown 设置 `proseWrap: "never"`、`printWidth: 1`、`embeddedLanguageFormatting: "off"`。这组设置利用表格超出行宽时的紧凑输出行为，不是全局代码行宽要求，也不是独立的表格开关。
- 检查实际生效的 Markdown 配置；若现有命令会重新填充列宽，可对本次 Markdown 文件通过命令行指定上述选项，不擅自修改其他语言的格式设置。工具不可用时按同样规则手工格式化。

## 设计信息的层级

- 总文档面向整体实现：说明设计目标、总体方案、代码架构、项目约束及公共约定。背景与目标不展开局部函数缺陷或内部算法；单模块项目可以简短，不能靠重复详细设计补足篇幅。
- 新项目与存量补档使用相同架构粒度：总文档以模块、层、包及必要的目录边界说明职责、依赖和共享契约归属，不列模块内部文件、类、函数入口或源码行号，不把目录树或 import 清单当作架构。依赖图节点使用模块名称，关系依据真实职责与依赖归并。
- 只有文件本身承载独立架构模块的职责、公开契约与依赖边界时，总文档才可在模块说明中注明该文件名；仍以模块名称表达架构，不展开内部符号。文件可被导入、编译或独立存放不构成例外依据，也不得为保留文件名而把内部文件人为升级为模块。
- 模块文档维护具体业务规则、流程、接口、数据、错误处理、测试和验收。总设计 §3.1 的模块索引使用“模块标识、职责摘要”两列，模块标识直接链接相应模块的设计文档首页；模块设计中的接口名、类型名链接到其唯一设计定义。架构和功能设计不通过业务源码路径、行号或私有符号定位实现。代码位置和断言证据由开发自测、独立核验或问题说明记录。
- 设计文档链接，以及公共开发与测试约定所需的配置引用、可执行命令和报告路径按既有规则保留；这些是文档导航或执行依据，不作为架构节点，也不能借此在总文档罗列业务实现文件。
- 局部任务保留项目整体定位，只更新受影响的总体设计；资料不足时注明已知范围和未决项，不虚构更大的产品背景或宣称全项目设计完成。

模块文档按 [模块设计规则](module-design.md) 以功能组织详细行为：共享定义单处维护，接口和流程随功能说明，测试与计划引用功能契约。功能标题采用业务行为名称，必要的语义锚点保持稳定；简单行为不强制流程图或空小节。

## 实施状态判定

状态表达实际实施与验证情况，不表达设计文档是否修改过。三角色回写同一字段时使用相同含义，并遵守已有完成判定权限：

- **§8 测试用例**：按测试源码判定。尚未编写为 `⏳ 待实现`，已有测试需要修正为 `🔄 待迭代`，已编写但缺少有效执行证据为 `🧪 待测试`。
- **§10 验收条件**：按该行要求交付的对象判定。业务行为已有实现依据、仅缺验证证据为 `🧪 待测试`；行为尚未实现为 `⏳ 待实现`；已证实实现偏离约定、需要返工为 `🔄 待迭代`。用例编号和人工核验方法只说明如何验证，不传递状态。若条件本身要求交付测试源码，则按该源码是否具备判定。不同状态的条件分行；保留未受影响的有效状态，完成须有独立验收依据。
- **模块头部**：已有业务或测试实现需要修正时为 `🔄 待迭代`；不存在这类返工且业务能力尚未全部实现时为 `⏳ 待实现`；业务实现已具备、仅需补齐测试实现或验证证据时为 `🧪 待测试`，其中尚未编写的测试用例仍为 `⏳ 待实现`。只有全部技术验收满足且无未完成条目时，由 validator 标为 `✅ 已完成`；局部范围通过不覆盖模块其余未完成内容。

- **§9 实施步骤**：architect 定义计划、初始化新步骤；进入实施后，步骤状态和实施时间由 developer 维护。validator 只读 §9，即使发现返工或完成标记失效，也只在报告列出步骤、原因和归属。developer 收到退回后先更新受影响步骤，修复并自测后再更新完成状态。
- **§8 用例日期**：developer 对当前用例和实现自测通过后写 `✅ 已完成 (YYYY-MM-DD)`，日期取该版本实际自测证据。独立 validator 按本轮证据回写用例结果；若通过，保留同一版本有效的自测日期，缺失时仅凭同版自测回执或日志正文中带时区的实际完成时间补齐，不能用文件创建或修改时间推算，否则写 `✅ 已完成 (自测日期未知)`。这表示独立验证已通过，不证明 developer 做过自测。独立执行时间记在规范报告，不用验收日、设计日或旧版本日期填补。未通过的用例按当前状态记录，不沿用旧的完成标记。

例如：导出器已按约定转义分隔符，但相应用例尚未编写。§8 的用例为 `⏳ 待实现`，§10 的“含分隔符的字段正确转义”为 `🧪 待测试`。若已证实多行字段丢失换行，将保留换行的条件单列为 `🔄 待迭代`。纯文字或排版修正不重置有效状态，状态日期仍按角色流程维护，不追加历史。

## 正文与实现一致性

- 设计要求描述应实现的方案，现状陈述描述有证据的事实；两者不能混写。设计阶段不预先声称已实现、已测试或已验收；实施后也不能保留与当前代码、测试相矛盾的现状陈述。
- 实施状态集中在已有状态字段维护。正文只保留影响设计或使用的现状、限制及依据，不在概述、架构和风险中重复“尚未实现”“暂无测试”等易失效状态；确有必要保留的内容必须随事实同步。
- 核对“接入后须复验”“尚待联调”等措辞时，对齐当前源码和配置版本、被验行为、用例与环境。若同版同范围的有效证据已满足条件，删除一次性待办；已有长期回归约定则写清下次触发变更和需运行的用例。证据仅覆盖部分场景时，只保留未验部分及所缺条件。旧版通过、替身结果、模块完成标签均不能补证；不要把当前欠验改写成未来规则，也不要把一次性待办升级为永久回归要求。
- 交付前核对本次范围的总体设计、模块正文、README、API/使用说明及状态。更新或删除已失效的描述、风险和未决项，保留仍有效的限制和范围外未完成项；不以新增“已完成”说明或改状态标签代替原位修正。
- architect 维护方案与契约；developer 可依据代码和执行证据直接同步不改变方案的现状、路径、命令及文字格式，不能把实现偏差改写成设计要求。涉及行为、约束、风险判断或验收标准变化时交 architect；技术验收状态仍由 validator 判定。
- validator 核对本次交付文档与代码、测试、状态的实际对应关系，报告具体矛盾及归属，不因测试通过忽略正文失实。仅验证请求不授权修正文档正文；原任务包含实施时按角色衔接完成修正并复核。模板或 skill 明定的排版要求逐项核验，个人风格偏好不作为失败依据；本次交付文档存在已证实的当前事实矛盾时不能宣称交付完整。
- 明确标识的历史验证、固定版本基线和外部权威资料保持其时间与版本含义，不用当前结果覆盖历史事实；发现引用已不适用时更新当前引用或说明适用边界。修正当前正文不追加迭代过程或新旧对照。

## 交付前文档核验

完成正文与状态更新后，独立核验新产出的最终文本，不以编写时的记忆或格式化结果代替读回。已在有效上下文且未变的规则作为对照，不为此重新加载规则原文：

1. 按任务与依赖索引定位本次涉及的总体/模块设计、README、API/使用说明和报告段落，读回完整相关正文及必要上下文，包括受影响的未修改描述；不只检查新增行或状态，也不因此加载无关模块或无关正文。整份新文档属于本次输出时，核对完整成稿。
2. 扫描正文和表格中尚未被行内代码、代码块或有效链接保护的技术字面值，重点检查含下划线的标识符、带后缀的文件名、路径、命令、通配符和正则。根据真实契约逐处辨认，按角色权限补齐代码格式或记录问题并交相应角色；同一符号的其他出现位置一并核对，不能只修正示例中的一处。
3. 用项目已有 Markdown 解析器或预览核对字面值和表格；无可用渲染器时将正文排版列为未核验，并注明范围。确认如 `__file__` 的下划线不会成为强调语法，修正不改动代码块、链接目标与样例值。不为此自动安装新工具。
4. 对照当前代码和执行证据核验现状、限制、风险、未决项及状态，按角色权限原位修正或报告问题。本角色写入或更新的文档须在最后写入后再次读回；validator 还须复核报告及状态回写后的最终文本，不能只检查生成报告之前的版本。

architect 在交付摘要中简述实际核验范围与方式；developer 将文档核验范围、方式和结果随已有交验输入提供；validator 在报告 D/E 节记录实际核验范围、方式、发现与限制。无需另建文档检查报告，也不把检查过程写入设计正文。无法完成的检查明确为未核验，不预填“文档一致性通过”。

## 按文档用途表达

| 文档 | 表达重点 |
| --- | --- |
| 设计文档 | 当前方案、接口契约、约束、必要取舍、实施与验收依据；未决事项说明影响 |
| API 与使用说明 | 调用条件、输入输出、错误行为、使用步骤和限制；示例与真实接口一致 |
| 测试报告 | 验证范围、版本、命令、实际结果、失败原因和证据限制；按既定规则保留必要重试、历史及负向验证摘要 |

报告中的执行记录是验证证据，不能因删除对话痕迹而删去失败或重试事实。只保留影响结论的摘要，不写“先尝试、再发现、随后修复”的工作故事，不附完整原始日志或样本。

技术表达示例：项目根由 `Path(__file__).resolve().parent` 定位，测试文件匹配 `test_*.py`。这些字面值在解析后仍须完整显示。若实现与测试证据已具备，模块概述应说明当前职责与有效入口，删除过期的“函数仍为未实现桩”，不改写为一段实施经过；尚未完成的其他模块仍保留真实状态。

交付前读回成稿，核对正文是否可独立理解，是否保留必要条件与证据，技术字面值解析后是否完整，正文与当前实现和状态是否一致，是否含对话痕迹、模板提示、重复内容或无依据断言。
