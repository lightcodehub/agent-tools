# 模块设计的粒度与功能组织

模块文档承载内部设计与功能详细设计，供 developer 实施、validator 核验。关键行为及协作方式必须明确；普通变量、循环写法和私有辅助函数拆分留给实现者，不把文件、类或接口数量当成设计完整性的依据。

## 设计到什么程度

- 明确模块职责、状态或资源归属、对外契约及必要内部协作。简单模块可用一句话说明组成；有实际多个组件时再说明各自职责、依赖与所有权，不为模板制造分层或组件。
- 会改变外部行为、数据一致性、兼容性或验收结果的选择须在设计中确定。算法或数据结构影响性能约束、错误优先级或一致性时也是设计内容；其余实现手段不预先固定。
- 存量设计以真实源码为依据，记录必要实现映射；新设计只规划关键包、组件、入口和必要文件，不排列全部私有实现。既有能力、规划方案与未知信息分清，不能把目标描述成已实现。
- 无法确定的关键行为写入 §11，并指明受影响功能、步骤与验收；相关范围不能宣称可实施；未请求的可选能力不作为当前功能的前置，某个入口受阻也不自动扩大为全部功能受阻。不为填满功能说明臆造权限、重试、事务、恢复或依赖能力。

## 章节分工

保留模块 §1、§4–§11 的编号。§2 为“内部设计与共享规则”，§3 为“功能行为与接口”；测试、实施、验收与未决问题仍为 §8、§9、§10、§11。

- §1 说明职责、依赖、调用方和必要实现映射；不要在概述堆放全部业务规则。总文档仍只表达架构模块及组织边界。
- §2 说明实际内部协作、状态/资源所有权，以及确被多个功能共用的规则或接口协议。状态定义、通用错误/操作协议可在此单处维护；不要把所有功能流程集中到此处而让功能小节只剩链接。
- §3 按功能组织行为和对应接口。§4 定义共享类型/字段，§5 定义持久化结构，§6 定义界面布局及具体交互；已有定义直接引用，不重复完整声明。各功能特有规则仍留在该功能内。
- §8 给出具体测试输入、前置与可断言结果，§9 安排可测试实施单元，§10 判定需求是否满足；通过功能链接、已有需求标识和用例编号关联，不分别复制一遍业务规则。测试的具体断言值不能因去重而省略。

## 功能单元

一个功能单元对应一项可独立说明、实施和验证的行为，可由多个接口或组件共同完成；一个通用接口也可承载多个功能。不得机械地把每个文件、类、私有函数或每个条件分支拆成一个功能。

功能小节用行为命名，例如“创建任务”“领取任务”“提交处理结果”。采用本组织的多功能模块必须提供简短的“功能—入口—行为位置”导航，不能因文件较短而省略；单功能省略索引表。被引用的功能使用稳定语义锚点，不随函数签名变化，不将旧锚点重用为另一行为。组织调整本身不授权改变已确认的接口或业务预期。

每个功能按以下顺序说明实际适用的信息，允许合并为短段落或表格，不强制六个子标题、六张表或成排“不适用”：

1. **目的与触发**：功能提供的能力、调用方和触发条件。
2. **前置条件与输入**：必要初始状态、调用条件和输入校验；列出真实接口签名或协议入口、参数类型/位置及共享定义引用。多个协议入口只补差异，不重复共同业务规则。
3. **处理规则**：关键判断、顺序、分支和跨组件协作。校验/错误优先级、状态迁移、事务、竞争、重试等仅在适用且影响行为时明确。
4. **结果与副作用**：成功返回、输出、状态或数据变化、资源取得/释放和对调用方的影响，明确可观察的完成条件。
5. **失败行为**：失败条件、异常或错误结果及失败后的可观察状态；涉及部分完成、提交未知、清理错误或恢复时明确保证范围。已知的失败保障或不保证事项须在本功能或其明确引用的 §2 共享契约中获得，不能仅放到 §7 风险、影响或兼容说明。存量按真实实现说明，不扩大为未提供的回滚保证；无相关机制不添加实现要求。
6. **验证关联**：直接引用测试用例 ID，或链接 §8 中显式列出 ID 且带功能归属的用例组或表，使本功能的引用与 §8 中实际断言该契约的实例一致。引用混合用例组时按该功能筛选，既检查遗漏也检查多引。引用不复制测试表，也不能用组名代替具体 ID；共享用例的参数分支仍须明确。仅测试用例要求版本内稳定的 ID，功能用名称和语义锚点定位，不要求额外编号或追踪矩阵；完整规则见[测试用例标识与引用](test-management.md#测试用例标识与引用)。

读者应能通过本功能小节及其明确引用的共享定义理解完整行为，不需要猜测或在无关功能中拼接条件。共享规则只有一个权威位置；功能中可简述关键前提并引用，不维护多份完整状态表或错误规则。

接口的参数、返回和错误语义必须可获得，不能因改用功能标题而省略。若同一接口服务多个功能，将共用签名、类型和通用协议定义一次，各功能明确自己的调用方式、分支及结果。外部服务契约资料仍按外部 API 模板组织，不把其内部实现或验收纳入本模块。

## 表达与衔接

- 交付前先检查多功能入口导航，再逐功能模拟定向阅读：只看本功能及其明确共享引用，能否确定输入、处理、结果和全部已知失败保证。若关键行为只在风险章节或其它无关功能中出现，迁回所属功能/共享定义并同步引用，不能仅以章节齐全判定通过。
- 从 §8 的每条用例及参数实例反查其验证的功能或共享规则，再检查相应功能的验证入口能否定位到它。前置条件、输入或方法名本身不能代替归属引用；按功能分组时可在组头统一链接，共享组须注明实际覆盖功能。§9/§10 引用保持对应，不丢弃测试断言。功能与用例的多对多引用不产生重复定义或重复统计，参数实例仍按测试管理规范记录。
- 简单行为可用文字与接口表说明；复杂分支、状态变化或跨组件协作再选择流程图、状态图或时序图。图须承载实际信息，不强制每个模块或功能生成示意图。
- 定向阅读从功能索引或入口映射进入功能小节，再读取其所需共享定义与依赖；不能因功能组织而丢失影响面、必要调用方或验证条件。
- developer 按 §9 实施，关键行为缺失交 architect 补齐，普通私有细节可在设计约束内决定。validator 核对功能契约、实际调用、测试边界与验收证据，不只看接口或章节是否齐全。
- 新建和完整补档采用此组织。既有有效设计文档可用对应章节；仅存在源码不等于已有有效设计。局部任务只补必要行为和引用，不因版式不同重排无关内容。改名、移动或重组时同步索引、依赖、测试/实施/验收链接，保留仍有效的契约，按本次交付的模块编号同步引用。
