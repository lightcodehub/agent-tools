# 设计交付自检清单

设计文档写入后、向用户交付前核对。以 `SKILL.md` 和本次需求为依据，本清单不新增设计要求。

适用项满足后标记通过；未满足项注明缺失内容；条件不成立的项目注明“不适用”及原因，不当作失败，也不为勾选而补造内容。迭代时重点核对本次变更及相关引用，保留未变更部分。

## A. 范围与依据

- [ ] 目标、范围、非目标及约束已写明，设计没有扩大本次任务范围
- [ ] 未因用户要求直接实现或改动行数少而排除必要设计；已有充分设计直接复用，缺项仅按本次范围补齐
- [ ] 已查阅相关项目本地 skill；对既有实现的描述有代码依据，新增设计有需求或已确认约束依据，未把推测写成现状
- [ ] 新项目没有现有代码时已如实说明，并明确框架、规范等实施所需选择
- [ ] 存量项目已检查文档覆盖情况；缺文档时已主动按规则补齐当前实现，并向用户报告合理性、缺陷、代码依据、影响和建议，未把未经确认的建议写成现有设计
- [ ] 未决问题已按模块内 §11、跨模块总文档 §6.2 归位；影响实现或测试预期的问题标为实施阻塞项

## B. 文档结构与依赖

- [ ] 总文档及业务模块文档位于 `design-doc/index.md`、`design-doc/{name}/index.md`，必需章节齐全
- [ ] 可选章节仅在适用时出现；省略后保留固定编号，没有空标题或占位内容
- [ ] 按业务职责划分模块，索引、文档与依赖图一致；新设计无环且被依赖方优先，存量补档如实记录现存环并标明整改需求，未伪造拓扑顺序或检查通过结论
- [ ] 依赖说明包含可用的相对链接及章节引用，共享数据结构只在定义方模块维护；模块没有未声明的依赖
- [ ] 已按项目可用工具或模板完成格式检查，流程图语法和文档链接已核对

## C. 方案与实施计划

- [ ] 当前范围内每项需求都在现有计划或验收条目中对应到设计章节及 UT/IT 用例；不能自动化验证的约束已说明核验方法和原因，未以章节齐全代替需求覆盖
- [ ] 业务规则、判定条件、行为预期及适用的性能或时限要求明确，影响实施的答案已写入文档而非仅留在聊天中
- [ ] 新增或变更接口的签名、参数、返回值及错误行为完整，数据结构和核心 Mermaid 流程一致
- [ ] 接口输入范围、空值约束及适用的鉴权、权限、幂等性契约明确；并发、事务、重试、超时和降级等适用场景已有处理策略及对应测试
- [ ] 目标运行环境、版本和兼容范围明确；涉及的配置项、默认值及迁移兼容策略已在相应章节写明
- [ ] 模块影响、兼容性、风险与回滚说明符合本次变更，验收标准能判断结果
- [ ] 实施计划逐单元包含实现、设计章节、测试用例编号及运行验证；每步绑定的完整用例所依赖行为在该步结束时均已实现，未让前一步用例依赖后一步能力；没有把全部测试推迟到最后

## D. 按需设计

- [ ] 涉及用户交互时，已有设计资源或经确认的线框图、组件层次、交互状态及状态归属齐全
- [ ] 涉及用户交互时，已按“已有组件 → 项目组件工具集 → 开源组件 → 自研”选型，并记录来源；只有前三项不能满足需求时才建议自研
- [ ] 涉及用户交互时，总文档 §5.3 链接现有设计系统或附属视觉文档；适用的颜色、主题、字体、间距、圆角及阴影有真实依据，不重复复制维护
- [ ] 涉及持久化时结构明确；表关系、索引及结构/数据变更按实际适用性说明，没有模板预设字段或策略
- [ ] 涉及外部服务时，`external-service/` 仅记录 API 契约，无实施状态、测试设计、实施计划或验收；本地调用逻辑归调用方业务模块

## E. 测试设计

- [ ] 总文档 §5.2 与模块 §8 的合并内容已明确测试框架、运行命令、工作目录、测试文件路径及 mock 策略；源码固定在 `tests/{module}/unit/`、`integration/` 及规定 support，跨模块用例归发起或协调模块
- [ ] 每个业务模块 §8.2 均有可直接实施的具体用例，包含场景、输入、预期结果、类型和状态，覆盖 happy path / boundary / error，未把测试设计留给 developer
- [ ] 单元用例编号符合 `{module-name}-UT-{NNN}`，项目内唯一；旧编号未重排，新增用例追加编号，参数化用例有明确参数实例
- [ ] 需要项目内集成验证时，§8.4 已定义具体 IT 用例、真实调用与 mock 边界、运行条件、文件及命令，并在实施计划与验收中引用；不适用时未新增集成要求
- [ ] 涉及外部 API 调用时，本地参数组装、响应及错误处理的测试在调用方模块中定义，以 mock 验证；未要求单元测试验证远端可用性
- [ ] 最终报告路径声明为项目级唯一的 `tests/test-report.md`，未在模块正文重复写入职责或规划独立报告

- [ ] 已读取测试管理规范；源码后缀和框架命名规则明确，辅助源码有实际调用方，框架配置在根目录且只发现规定测试目录
- [ ] 根目录解析不依赖命令当前目录；数据生成、run-id、用例/并发隔离、artifacts 输出及只读数据集来源/版本/校验/缺失处理明确
- [ ] 前置断言、替身边界、预期错误识别及重要防护负向验证的故障变体确实改变目标行为，未把删除冗余判断视为必然失效；未复制业务逻辑自证
- [ ] 成功、失败、取消、超时均有资源回收，临时数据默认清理；保留策略和必要位置例外完整，未误删他轮目录或数据集
- [ ] 未规划数据/日志入库或变相嵌入；生产资源归属明确；已规划 `/build/` 忽略、历史跟踪处理和失效引用修正

## F. 状态与交付边界

- [ ] 新设计、迭代、补档和修复中的设计调整均只描述当前有效方案；失效内容和已解决未决项已清理，没有旧方案回顾、新旧对照、版本沿革、变更日志或修复记录，历史仅由 Git 保存
- [ ] 总文档及本次涉及模块的设计时间已更新；模块实施状态和实施时间只在业务模块文档维护
- [ ] 迭代时保留仍有效且未变更条目的当前状态，变更条目按主规则标为“待迭代”并附日期；时间与状态字段没有累积历史轨迹
- [ ] 影响行为、契约、测试或验收的变更已同步将模块头部标为待迭代，未出现头部已完成而相关条目未完成；纯文字或排版修正未误重置状态
- [ ] 存量补档未把代码存在当成测试通过，未臆造历史时间或验证结果；预期行为不明、依赖环等阻塞项已说明，未将补档完成等同于具备实施条件
- [ ] 交接说明文档路径、本次 scope、可实施结论或阻塞原因；原请求含实施且具备条件时返回 developer 继续，纯设计请求在交付后结束
- [ ] 没有直接修改业务代码、跨项目设计、自动提交或生成 PR；文档不包含完整业务函数、超过 15 行的连续业务代码或估时

- [ ] 已明确 developer 更新实施与自测状态、validator 判定技术验收及模块头部完成；未把自测、设计就绪或部分范围通过等同于模块验收完成

## 产出文档表达

- [ ] 已执行交付前文档核验，逐文件读回范围内完整相关正文（含存量未改段落），修正后复核最终文本；实际核验方式与范围有据可查，本角色写入或更新的文档已在最后写入后检查（validator 包括报告）

- [ ] 命令、路径、标识符、正则和样例字面值使用代码格式或有效链接，Markdown 解析后字符与表格结构完整，未把格式化工具通过视为语义核验
- [ ] 已逐项核对本次范围正文、代码、测试与状态；无过期的现状陈述或失效风险，范围外未完成项及明确版本的历史事实未被误改；事实同步、方案调整和验收状态按角色职责处理

- [ ] 已按文档表达规范读回成稿，正文无需聊天上下文即可理解，无对话记录、工作故事或遗留模板提示
- [ ] 结论、条件、依据与限制清楚，术语一致，语言自然精简，无重复套话或无依据的效果评价
- [ ] 表达调整未改变业务规则、文档结构、角色职责、状态或用例；必需验证证据及失败、重试事实完整保留

## 设计内容与公共约定

- [ ] 总体协作中的跨模块读取、状态变化和结果写回均有归属明确的操作契约；调用方依赖、测试和实施前提已同步，未用类型或表存在代替能力就绪
- [ ] 单元用例预期在真实可观察边界内，未以创建/投递/替身成功证明下游结果；完整业务预期由相应模块或真实集成用例覆盖，边界调整未丢需求

- [ ] 公共代码与测试约定由项目级文档集中定义，模块链接可解析；具体接口、测试路径、命令、数据准备及必要例外完整，未把引用误判为缺项
- [ ] 不适用的可选章节或子节已省略且编号稳定，实际契约与依赖未遗漏；没有空表、批量“无”或模板默认的技术选择
- [ ] 运行时失败处理与测试替身分开，成品未包含角色操作规则、填写提示或未经核实的检查声明；状态字段之外未追加只交付设计或状态写回管理说明，项目约定中无 skill 发现或工具检查过程记录

- [ ] Markdown 表格没有列宽填充，分隔行保留必要对齐标记；格式调整未改变链接、代码块、元数据、样例值或有语义的空白

## 总体与详细设计分层

- [ ] 新项目与存量补档遵守相同粒度；仅确有独立职责、公开契约与依赖边界的单文件模块可在总文档注明文件名，未以可导入为由拆出伪模块
- [ ] 模块详细设计承接必要实现映射，新项目规划与存量事实分清；具体位置未因下沉而遗漏，公共约定的配置、命令和文档链接仍可执行、可解析

- [ ] 总文档给出整体目标、总体方案和代码架构，背景未被函数缺陷清单替代；局部任务未覆盖或扩写无关项目设计
- [ ] 总文档以模块、层、包和组织边界表达架构，依赖图使用模块名称；内部文件、类、函数入口及源码证据在模块详细设计，未将存量文件清单当作架构
- [ ] 项目约束有依据且与设计选择、工程约定分开；本次范围的实现和验收有对应约束及证据
- [ ] 公共约定及适用视觉资料引用有效，读取后内容完整；已有有效设计未因章节编号不同被误报缺项

## 公共代码规范一致性

- [ ] 类型行未列记录/数据对象的实现方式，即使多个模块都使用也仅引用模块契约；注释行在缺乏统一惯例时明确缺口，核验范围不超过实际证据

- [ ] 结构与语义分开核验：单模块业务事实未冒充公共规则，局部类型/依赖实现方式已下沉；源码惯例只适用于有一致证据的范围，未将少数注释样例推广到全项目

- [ ] §5.1 使用固定三列和八行，规范项名称与顺序和模板一致；未删减、合并、改名或用段落代替，已有规范引用仍保留相应行
- [ ] 八类均有实际约定或有效引用、适用范围与核验方式；无机制时写明事实和边界，未知未冒充不存在，没有空项或仅写“不适用”
- [ ] 新项目采用的规范与工具规划明确；存量成文规则、配置与源码归纳有依据并区分，未把局部实现、缺陷或建议提升为全项目规范
- [ ] 表内只保留公共编码原则；字段取值、参数校验、构造器行为、具体异常/状态/恢复流程和事件定义在模块文档，引用有效且未因下沉丢失必要信息
- [ ] 核验方法对应检查对象，命令与配置真实存在；未把单元测试通过当作风格或注释检查，也未为填表引入工具或默认业务规则
- [ ] 无日志、自然异常传播或无资源机制已在对应行交代，没有因固定八行新增不必要代码；实际需要的恢复、资源回收、必要日志和信息保护未被省略
