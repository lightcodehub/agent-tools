- [ ] 新项目区分需求事实、约束与拟定方案；存量补档核对真实入口、配置和调用链，保留仍有效的文档与接口。未把“没有运行证据”写成“已经通过”，也没把改进建议写成已实现。

- [ ] 检查代码依赖而非运行时往返，声明实际核实范围。不以类型或表代替跨模块读写契约；共享定义唯一归属。新设计存在环不放行，存量环不隐去或强排行序。

## 模块、测试与实施

- [ ] 每个业务模块都有自己的文档。逐功能只读 §3 和它明确引用的共享定义，即可确定接口、输入、关键分支、输出、副作用和失败后的状态。逐行核对“API 定义”：函数或协议入口各自可点，点击后的标题就是该入口的签名或协议定义。一行多个入口无遗漏，同一入口跨行复用同一地址；索引严格两列，不把准备或内部调用加入入口清单。§2 只保留内部协作和共享规则。涉及先后写入时区分已保证和未保证的原子性；不从“校验失败无副作用”推导出所有故障均回滚。
- [ ] 可选章节只覆盖真实 UI、持久化、外部 API 或协作边界；外部契约不作为实施模块。必要实现映射可定位，但不固定普通私有细节；状态、数据和接口叙述无冲突。
- [ ] 在本次模块范围逐个对照函数、方法、构造函数的定义及签名（含共享定义和沿用的旧接口）：每处均按签名标题、简介、参数、返回、错误的顺序填写；简介说明用途，返回与错误独立说明。参数表列名、顺序一致，名称、类型和行数与显式入参一致；无参统一写“参数：无。”，没有空表。检查单个参数、共享类型及可传空值的参数，避免漏表或误标可省略。
- [ ] 从每项需求找到所属功能、完整的用例或非自动核验方法及 §10 条件。逐步遮住后续交付物，从基线和明确的前置步骤出发，检查本步每个 ID 的真实入口、依赖与全部断言是否已就绪。声明、替身自身或最终工作树的绿测不能充当本步依据。若一步覆盖多个行为，而其中一组用例不依赖其余行为就能通过，应先交付该组，不把全量 UT 留到所有业务完成后。未以模板齐全代替覆盖。
- [ ] 逐条读 §8：输入、前置、预期及类型足以写断言，正常、边界、异常有覆盖。对每个参数分支核对 §3 引用：仅准备或观测的行为不获覆盖；同一场景明确断言的其他功能不漏引。把每个“调用 → 断言”分别与该功能契约对照：例如用查询确认写入失败后状态未变，归写入；若还断言查询返回的是所存对象本身，则这个身份断言也归查询。把这些归属从 §8 反查到 §3，再展开 §3 的引用复核一遍。对并列 API 或命令，能逐个回答“这个 ID 在这个入口及模式下断言了什么”；无对应实例的入口未被列为已覆盖。已有场景、预期、参数标识和顺序步骤未因排版或改号丢失。
