# architect

`/designer:architect` 先核对需求与代码现状，再输出总体与模块详细设计；新项目基于已确认需求和约束，存量项目以实际实现为依据。

它的目标不是直接写实现代码，而是把需求整理成一份可直接交给 AI 或工程师继续落地的设计文档。文档重点是：职责边界、内部协作、功能行为与接口、适用的数据和交互设计，以及可追溯的验证依据。

## 什么时候用

适合这些场景：

- 新增功能前，需要先梳理设计
- 需求跨多个模块，直接写代码风险高
- 需求涉及 API、数据库、用户交互、测试设计
- 希望先让 Claude 看懂当前代码，再做方案
- 实现或小修复请求中，现有设计缺失、过期或不足，需要先补齐相关设计

不适合这些场景：

- 纯讨论，没有代码上下文
- 本次实施已有充分有效的设计，不需要新增或调整方案

判断依据是设计是否足够支撑本次实施，不是用户是否说“先设计”或需要改几行。developer 可在同一任务中转入 architect，携带原需求、范围和缺项完成设计后返回继续；用户只要求设计时则在设计交付后结束。

## 这个 skill 会做什么

触发后，它会按固定顺序工作：

1. 先理解你的需求
2. 搜索并阅读相关代码
3. 识别当前项目里的测试框架、测试目录约定、组件目录
   - 存量项目缺少设计文档时，主动按模板补齐当前实现，并审查设计合理性与缺陷
4. 按业务逻辑划分模块，检测循环依赖
5. 输出模块化设计文档（总文档 + 每个模块独立文档）
6. 自检

## 这个 skill 不会做什么

- 不直接修改业务代码
- 不自动提交 commit / PR
- 不凭空猜现状
- 不写很多实现代码
- 不绕开项目已有组件和测试体系另起炉灶

## 输出内容

输出分两层：

### 1. 聊天摘要

简要说明：

- 读了哪些代码
- 推荐方案是什么
- 是否存在未决问题
- 文档路径、本次范围，以及“可实施”或“存在阻塞”的交接结论；补档完成不等于设计就绪

### 2. 完整设计文档

模块化输出，结构如下：

```text
design-doc/
├── index.md              ← 总体设计（目标/总体方案/代码架构/约束/公共约定/风险）
└── {module-name}/
    └── index.md          ← 模块设计文档（概述/流程/API/数据结构/DB/组件/测试/实施计划/验收）
```

每个模块独立一个文件夹，按业务逻辑划分。总文档含模块依赖图和循环依赖检查结果。模块间通过相对链接引用。

章节编号固定，可选章节省略后不重编号。共享数据结构在定义方业务模块中定义；实施状态在业务模块文档维护，总文档维护总体方案、代码架构与项目约束，不重复模块详细设计。`external-service/` 仅存放外部 API 契约；本地调用逻辑的实现、mock 测试和验收归属调用方业务模块。

## 文档的强约束

### 设计缺项在设计阶段补全

architect 负责澄清并写明业务规则、接口契约、异常和边界处理、目标运行环境及兼容约束，并同步具体测试用例。用户在聊天中给出的答案应原位写入当前设计，影响实施的未决问题未解决时不宣称设计可实施。developer 发现缺项后返回该流程，不通过编码前追问代替设计文档。

完整性按需求逐项核对：在现有实施计划或验收条目中关联需求要点、设计章节及测试编号；不能自动化验证的约束说明核验方法和原因。章节齐全不能替代需求覆盖，也不为此另建记录文档。

本次需要验证的项目内模块协作在归属模块 §8.4 定义具体 IT 用例、运行条件、真实调用与 mock 边界，并映射到实施计划及验收。外部 API 仍使用 mock，不强制远端联调。集成结果在同一测试报告中单独记录，不计入单元测试统计。

### 存量项目缺文档时主动补齐

阅读代码后发现缺少设计文档，按既定结构主动补齐当前实现，不等用户另行要求。补档后向用户说明哪些设计合理、哪些存在缺陷，并提供代码位置、影响、严重程度和改进建议。未经确认的改造建议不写成当前方案，业务代码不因补档而改动。

现存循环依赖等问题也应如实记录，不能为满足模板而隐瞒。代码已存在不代表测试通过；验证不足、测试预期不明和其他阻塞项明确标注，不把“补档完成”当作“已具备实施条件”。

### 设计文档始终描述当前方案

无论新设计、迭代、补档还是修复中的设计调整，都只保留当前有效方案。需要变更方案时原位改写，删除失效内容及已解决未决项；恢复既有设计的修复不新增过程记录，但须同步失效的现状描述。developer 可按证据直接同步不改变方案的事实和格式，涉及方案与契约变化交 architect。不在文档中回顾旧方案、追加修复经过或对照新旧版本，历史由 Git 保存。当前所需的兼容、迁移、回滚操作照常说明；时间与实施状态只保留当前值。

影响行为、接口、测试或验收的变更，要同时将相关条目和模块头部改为待迭代；纯文字或排版修正不改变实施状态。

### API 必须理出来

所有新增或变更接口，都要列出：

- 签名或路由
- 参数
- 返回值
- 错误码或错误行为

### 图示按行为复杂度使用

复杂分支、状态变化或组件协作使用有信息量的 Mermaid 图；简单功能用文字或表格即可，不强制绘制示意图。

### 测试框架与源码布局

已有框架时核对实际配置和发现规则；尚无框架时在设计阶段选定，并给出配置及执行命令。两种情况均按固定目录发现测试源码。

每个模块必须在设计阶段写出完整、可直接实施的具体测试用例，不能只写“覆盖关键路径”等测试目标，也不能留给 `/engineer:developer` 临时补充。各模块分别使用 `{module-name}-UT-{NNN}`、`{module-name}-IT-{NNN}`，两类定义各自从 001 连续排列。迭代可调整修改模块的编号，同步本版引用。测试代码固定在 `tests/{module}/unit/`、`tests/{module}/integration/`，辅助源码只在模块或跨模块 `support/`，并要求真实调用，项目唯一规范测试报告统一由 `/inspector:validator` 写入 `tests/test-report.md`，architect 不生成模块级报告。

### 设计尽量模块化

设计不能是一大坨描述，要按职责拆开。

### 用户交互必须结构化、组件化

如果涉及用户交互：

- 要拆页面层、区域层、基础组件层
- 要说明状态放在哪一层
- 要说明组件怎么组合

### 组件复用有优先级

用户交互组件不能上来就自己写，必须按这个顺序：

1. 项目内已有组件
2. 项目内组件化工具集中存放位置
3. 开源组件搜索结果
4. 最后才自研

### 涉及数据库时，必须有数据库设计

明确实际持久化结构；存在表关系时提供 ER 图，存在索引或结构、数据变更时说明对应设计与必要处理。不生成无内容子节，不预设数据库字段或迁移方式。

## 使用示例

### 示例 1：单模块后端需求

```text
/designer:architect 为用户资料新增昵称更新能力，先看现有 user 模块代码，再给我设计文档
```

预期输出重点：

- 用户模块代码证据
- 更新昵称 API
- 昵称更新的完整行为；复杂分支按需配图
- 涉及持久化时的现有映射与必要变更，不预设新增字段或索引
- 基于当前测试框架的测试设计

### 示例 2：前后端联动需求

```text
/designer:architect 为订单页新增批量导出能力，前后端都要考虑，先查现有组件和导出相关逻辑
```

预期输出重点：

- 页面模块拆分
- 用户交互组件复用方案
- 后端导出任务 API
- 异步处理流程图
- 导出任务表设计
- 前后端测试设计

## 产出质量判断标准

一个合格的输出，至少要满足：

- 存量描述有代码依据，新设计有需求与约束依据
- 模块及内部职责边界清楚
- 功能行为完整，实际接口和共享定义可定位
- 复杂行为有适当图示，简单行为说明简洁
- 有测试设计
- 用户交互需求有组件化设计
- 数据库需求有 DB 设计
- 实施计划可直接执行

## 建议用法

对复杂需求，先用 `/designer:architect`，等设计文档稳定后，再进入实现阶段。这样可以显著减少边做边改、返工和接口跑偏。

## 测试目录与运行产物

遵守 [测试管理规范](references/test-management.md)：所有路径从消费项目根解析；源码按设计模块放在 `tests/{module}/unit/`、`integration/` 及实际调用的 `support/`，框架配置放根目录。临时数据在 `build/tests/runs/{run-id}/data/{module}/{case-id}/`，产物在同轮 `artifacts/`，只读数据集在 `build/tests/datasets/{dataset-id}/{version}/`。根 `/build/` 必须被忽略且无索引文件。

唯一规范报告是 `tests/test-report.md`；不得提交数据、原始产物或其改名、编码、嵌入版本。设计明确格式白名单、生成方式、缺失策略、隔离清理与必要位置例外；developer 负责实现、自测、文件自查与修复；validator 负责独立审查、验证、文件复核与唯一报告。失败、中断和取消适用同一规则。

## 三角色交接

architect 定义行为预期、用例与验收标准，developer 编写实现和测试、逐单元自测并修复，validator 独立审查和运行验证，统一输出规范报告及技术验收结论。developer 更新实施步骤与自测用例状态；validator 判定模块 §10 技术验收与头部完成状态。设计缺项返回 architect，不以改低预期来通过测试。技术验收不代替产品验收或发布决定。

## 产出文档要求

交付的项目文档遵守 [产出文档表达规范](references/document-style.md)：直接说明有效规则、条件和依据，语言自然、精简、准确；不带对话痕迹或工作过程叙述。Markdown 表格采用紧凑格式，不填充列宽；测试报告保留必要的结果、失败原因和重试证据。 命令、路径及标识符使用代码格式并核对解析后的字面值；本次范围的正文、实现与状态保持一致，不能只更新状态而保留过期现状。

## 设计文档读取与适用性

总文档承载概要设计与代码架构设计：§1 目标与范围、§2 总体方案、§3 代码架构、§4 项目约束、§5 公共约定、§6 风险与待确认。§5.1 定义代码规范，§5.2 定义公共测试约定；模块 §8 以相对链接引用，并提供具体路径、命令、用例、数据准备与必要例外。既有有效设计使用其对应章节。实际接口、依赖、业务规则与测试验收信息必须完整；无适用内容的 HTTP、依赖、数据结构、数据库和 UI 子节按规则省略。

模板仅提供成品字段和可删除的填写提示。实际语言、数据库及视觉参数来自项目依据，运行时失败处理与测试替身分别定义；文档不复制角色操作规约或预填检查结论。

## 总体与详细设计的边界

总文档明确整体能力和实现方向，以模块、层和包的组织边界、依赖及约束指导开发；函数现状、局部缺陷、字段校验、算法和具体用例在模块文档维护。单模块项目可保持简短，局部任务不覆盖无关设计。详细视觉资料通过总文档 §5.3 引用，已有完整资料不再复制。技术文档按事实组织，不因后续材料转换用途自动增加注册申报章节或未经证实的业务背景。

## 公共代码规范

依据 [公共代码规范](references/coding-conventions.md)，总文档 §5.1 固定使用三列、八个规范项及规定顺序；新项目与存量补档的格式和覆盖范围一致。每行写明公共约定或有效引用、适用范围与核验方式，没有相关机制仍说明实际边界。区分采用的规则、存量成文依据与源码归纳；具体业务契约下沉模块文档。固定八行不要求增加工具、日志、捕获包装或机械注释，已有必要处理仍须落实。

总文档的新项目设计与存量补档均按架构模块、层和包组织，不列内部实现文件或函数入口。具体代码映射在模块详细设计维护；仅文件本身构成独立架构模块时可注明文件名，依赖图仍使用模块名称。配置引用、测试命令和文档链接不作为架构单元。

跨模块读写及状态变化必须有归属明确的操作契约，并与调用方依赖、测试及实施前提对应。单元验证本层可观察结果，异步下游产物由实际模块或真实集成验证；共享类型、表结构或替身成功都不能代替这些证据。

## 定向读取

依据 [定向读取规则](references/scoped-reading.md)，总设计兼作模块与依赖索引：先定位目标及公共约束，再读相关设计、契约和实现。依赖内部细节按需展开，公开契约变更时核对调用方；索引失效或出现新证据时扩大范围。读取量优化不改变实现授权、必要回归和独立审查要求。

`scripts/read_section.py` 使用 Python 3 标准库，提供 Markdown 标题列表与精确章节读取；只输出所选章节，不修改项目文件、不缓存正文。用它承接总设计中的契约链接，避免宽行号读取带入相邻契约。

## 模块文档组织

按 [模块设计规则](references/module-design.md)，模块文档定义内部设计与功能详细设计。关键行为及协作明确，普通实现细节留给 developer；§2 集中内部职责与真正共享的规则，§3 按功能说明完整行为与实际接口，§8/§9/§10 引用其设计并分别承担测试、实施和验收。简单功能可以短段落表达，不强制六张表或流程图；旧有效设计按对应内容使用。
