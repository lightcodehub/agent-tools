# architect

`/designer:architect` 是一个先读代码、再出设计文档的 skill。

它的目标不是直接写实现代码，而是把需求整理成一份可直接交给 AI 或工程师继续落地的设计文档。文档重点是：模块拆分、API、流程图、数据库设计、用户交互设计、单元测试设计。

## 什么时候用

适合这些场景：

- 新增功能前，需要先梳理设计
- 需求跨多个模块，直接写代码风险高
- 需求涉及 API、数据库、用户交互、测试设计
- 希望先让 Claude 看懂当前代码，再做方案
- 实现或小修复请求中，现有设计缺失、过期或不足，需要先补齐相关设计

不适合这些场景：

- 纯讨论，没有代码上下文
- 本次实施已有充分有效的设计，不需要新增或调整方案

判断依据是设计是否足够支撑本次实施，不是用户是否说“先设计”或需要改几行。fullstack 可在同一任务中转入 architect，携带原需求、范围和缺项完成设计后返回继续；用户只要求设计时则在设计交付后结束。

## 这个 skill 会做什么

触发后，它会按固定顺序工作：

1. 先理解你的需求
2. 搜索并阅读相关代码
3. 识别当前项目里的测试框架、测试目录约定、组件目录
   - 存量项目缺少设计文档时，主动按模板补齐当前实现，并审查设计合理性与缺陷
4. 按业务逻辑划分模块，检测循环依赖
5. 输出模块化设计文档（总文档 + 每个模块独立文档）
6. 自检

## 这个 skill 不会做什么

- 不直接修改业务代码
- 不自动提交 commit / PR
- 不凭空猜现状
- 不写很多实现代码
- 不绕开项目已有组件和测试体系另起炉灶

## 输出内容

输出分两层：

### 1. 聊天摘要

简要说明：

- 读了哪些代码
- 推荐方案是什么
- 是否存在未决问题
- 文档路径、本次范围，以及“可实施”或“存在阻塞”的交接结论；补档完成不等于设计就绪

### 2. 完整设计文档

模块化输出，结构如下：

```text
design-doc/
├── index.md              ← 总设计文档（背景/范围/证据/模块索引/依赖图/跨模块约定/风险/未决问题）
└── {module-name}/
    └── index.md          ← 模块设计文档（概述/流程/API/数据结构/DB/组件/测试/实施计划/验收）
```

每个模块独立一个文件夹，按业务逻辑划分。总文档含模块依赖图和循环依赖检查结果。模块间通过相对链接引用。

章节编号固定，可选章节省略后不重编号。共享数据结构在定义方业务模块中定义；实施状态在业务模块文档维护，总文档只维护索引与依赖。`external-service/` 仅存放外部 API 契约；本地调用逻辑的实现、mock 测试和验收归属调用方业务模块。

## 文档的强约束

### 设计缺项在设计阶段补全

architect 负责澄清并写明业务规则、接口契约、异常和边界处理、目标运行环境及兼容约束，并同步具体测试用例。用户在聊天中给出的答案应原位写入当前设计，影响实施的未决问题未解决时不宣称设计可实施。fullstack 发现缺项后返回该流程，不通过编码前追问代替设计文档。

完整性按需求逐项核对：在现有实施计划或验收条目中关联需求要点、设计章节及测试编号；不能自动化验证的约束说明核验方法和原因。章节齐全不能替代需求覆盖，也不为此另建记录文档。

本次需要验证的项目内模块协作在归属模块 §8.4 定义具体 IT 用例、运行条件、真实调用与 mock 边界，并映射到实施计划及验收。外部 API 仍使用 mock，不强制远端联调。集成结果在同一测试报告中单独记录，不计入单元测试统计。

### 存量项目缺文档时主动补齐

阅读代码后发现缺少设计文档，按既定结构主动补齐当前实现，不等用户另行要求。补档后向用户说明哪些设计合理、哪些存在缺陷，并提供代码位置、影响、严重程度和改进建议。未经确认的改造建议不写成当前方案，业务代码不因补档而改动。

现存循环依赖等问题也应如实记录，不能为满足模板而隐瞒。代码已存在不代表测试通过；验证不足、测试预期不明和其他阻塞项明确标注，不把“补档完成”当作“已具备实施条件”。

### 设计文档始终描述当前方案

无论新设计、迭代、补档还是修复中的设计调整，都只保留当前有效方案。需要变更方案时原位改写，删除失效内容及已解决未决项；恢复既有设计的修复不为留记录而改写正文。不在文档中回顾旧方案、追加修复经过或对照新旧版本，历史由 Git 保存。当前所需的兼容、迁移、回滚操作照常说明；时间与实施状态只保留当前值。

影响行为、接口、测试或验收的变更，要同时将相关条目和模块头部改为待迭代；纯文字或排版修正不改变实施状态。

### API 必须理出来

所有新增或变更接口，都要列出：

- 签名或路由
- 参数
- 返回值
- 错误码或错误行为

### 流程图必须画出来

核心流程必须使用 Mermaid。

### 单元测试必须基于项目现有框架

不是随便写一个测试方案，而是要先识别项目当前用的测试框架，比如：

- Vitest
- Jest
- pytest

然后基于这个框架来设计测试用例和测试文件布局。

每个模块必须在设计阶段写出完整、可直接实施的具体测试用例，不能只写“覆盖关键路径”等测试目标，也不能留给 `/engineer:fullstack` 临时补充。每条测试用例使用 `{module-name}-UT-{NNN}` 格式的稳定编号。测试代码沿用项目现有组织方式，项目级单元测试报告统一由 `/engineer:fullstack` 写入 `tests/test-report.md`，architect 不生成模块级报告。

### 设计尽量模块化

设计不能是一大坨描述，要按职责拆开。

### 用户交互必须结构化、组件化

如果涉及用户交互：

- 要拆页面层、区域层、基础组件层
- 要说明状态放在哪一层
- 要说明组件怎么组合

### 组件复用有优先级

用户交互组件不能上来就自己写，必须按这个顺序：

1. 项目内已有组件
2. 项目内组件化工具集中存放位置
3. 开源组件搜索结果
4. 最后才自研

### 涉及数据库时，必须有数据库设计

要包含：

- ER 图
- 表结构
- 索引设计
- 迁移说明

## 文件说明

- `SKILL.md`
  - 供支持 Agent Skills 的宿主读取的执行规约
- `assets/design-index.md`
  - 总设计文档模板（模块化设计入口）
- `assets/design-module.md`
  - 模块设计文档模板（每个业务模块独立使用）
- `assets/api-service.md` / `assets/api-module.md`
  - 外部服务总览和 API 模块文档模板
- `references/checklist.md`
  - 设计文档写入后、交付前的自检清单
- `references/examples/` — 订单导出设计示例
  - `index.md` 总设计文档，`task/index.md` 和 `csv/index.md` 为两个业务模块，含依赖引用与循环检测

## 使用示例

### 示例 1：单模块后端需求

```text
/designer:architect 为用户资料新增昵称更新能力，先看现有 user 模块代码，再给我设计文档
```

预期输出重点：

- 用户模块代码证据
- 更新昵称 API
- 更新流程图
- 数据库字段/索引变更
- 基于当前测试框架的单元测试设计

### 示例 2：前后端联动需求

```text
/designer:architect 为订单页新增批量导出能力，前后端都要考虑，先查现有组件和导出相关逻辑
```

预期输出重点：

- 页面模块拆分
- 用户交互组件复用方案
- 后端导出任务 API
- 异步处理流程图
- 导出任务表设计
- 前后端测试设计

## 产出质量判断标准

一个合格的输出，至少要满足：

- 有真实代码证据
- 有模块拆分
- 有 API
- 有 Mermaid 流程图
- 有单元测试设计
- 用户交互需求有组件化设计
- 数据库需求有 DB 设计
- 实施计划可直接执行

## 建议用法

对复杂需求，先用 `/designer:architect`，等设计文档稳定后，再进入实现阶段。这样可以显著减少边做边改、返工和接口跑偏。
