# architect

`/designer:architect` 是一个先读代码、再出设计文档的 skill。

它的目标不是直接写实现代码，而是把需求整理成一份可直接交给 AI 或工程师继续落地的设计文档。文档重点是：模块拆分、API、流程图、数据库设计、前端组件设计、单元测试设计。

## 什么时候用

适合这些场景：

- 新增功能前，需要先梳理设计
- 需求跨多个模块，直接写代码风险高
- 需求涉及 API、数据库、前端 UI、测试设计
- 希望先让 Claude 看懂当前代码，再做方案

不适合这些场景：

- 只改一两行的小修复
- 纯讨论，没有代码上下文
- 已经确定要直接实现，不需要单独产出设计文档

## 这个 skill 会做什么

触发后，它会按固定顺序工作：

1. 先理解你的需求
2. 搜索并阅读相关代码
3. 识别当前项目里的测试框架、测试目录约定、组件目录
4. 按业务逻辑划分模块，检测循环依赖
5. 输出模块化设计文档（总文档 + 每个模块独立文档）
6. 自检

## 这个 skill 不会做什么

- 不直接修改业务代码
- 不自动提交 commit / PR
- 不凭空猜现状
- 不写很多实现代码
- 不绕开项目已有组件和测试体系另起炉灶

## 输出内容

输出分两层：

### 1. 聊天摘要
简要说明：
- 读了哪些代码
- 推荐方案是什么
- 是否存在未决问题

### 2. 完整设计文档

模块化输出，结构如下：

```
designs/
├── index.md              ← 总设计文档（背景/范围/证据/模块索引/依赖图/跨模块约定/风险/未决问题）
└── {module-name}/
    └── index.md          ← 模块设计文档（概述/流程/API/数据结构/DB/组件/测试/实施计划/验收）
```

每个模块独立一个文件夹，按业务逻辑划分。总文档含模块依赖图和循环依赖检查结果。模块间通过相对链接引用。

## 文档的强约束

### API 必须理出来
所有新增或变更接口，都要列出：
- 签名或路由
- 参数
- 返回值
- 错误码或错误行为

### 流程图必须画出来
核心流程必须使用 Mermaid。

### 单元测试必须基于项目现有框架
不是随便写一个测试方案，而是要先识别项目当前用的测试框架，比如：
- Vitest
- Jest
- pytest

然后基于这个框架来设计测试用例和测试文件布局。

### 设计尽量模块化
设计不能是一大坨描述，要按职责拆开。

### 前端 UI 必须结构化、组件化
如果涉及前端：
- 要拆页面层、区域层、基础组件层
- 要说明状态放在哪一层
- 要说明组件怎么组合

### 组件复用有优先级
前端组件不能上来就自己写，必须按这个顺序：

1. 项目内已有组件
2. 项目内组件化工具集中存放位置
3. 开源组件搜索结果
4. 最后才自研

### 涉及数据库时，必须有数据库设计
要包含：
- ER 图
- 表结构
- 索引设计
- 迁移说明

## 目录结构

```text
skills/architect/
├── SKILL.md
├── README.md
├── templates/
│   ├── design-index.md
│   ├── design-module.md
│   └── checklist.md
└── examples/
    ├── index.md
    ├── task/
    │   └── index.md
    └── csv/
        └── index.md
```

## 文件说明

- `SKILL.md`
  - 给 Claude Code 直接执行的规约
- `templates/design-index.md`
  - 总设计文档模板（模块化设计入口）
- `templates/design-module.md`
  - 模块设计文档模板（每个业务模块独立使用）
- `templates/checklist.md`
  - 输出前自检清单
- `examples/` — 订单导出设计示例
  - `index.md` 总设计文档，`task/index.md` 和 `csv/index.md` 为两个业务模块，含依赖引用与循环检测

## 使用示例

### 示例 1：单模块后端需求

```text
/designer:architect 为用户资料新增昵称更新能力，先看现有 user 模块代码，再给我设计文档
```

预期输出重点：
- 用户模块代码证据
- 更新昵称 API
- 更新流程图
- 数据库字段/索引变更
- 基于当前测试框架的单元测试设计

### 示例 2：前后端联动需求

```text
/designer:architect 为订单页新增批量导出能力，前后端都要考虑，先查现有组件和导出相关逻辑
```

预期输出重点：
- 页面模块拆分
- 前端组件复用方案
- 后端导出任务 API
- 异步处理流程图
- 导出任务表设计
- 前后端测试设计

## 产出质量判断标准

一个合格的输出，至少要满足：

- 有真实代码证据
- 有模块拆分
- 有 API
- 有 Mermaid 流程图
- 有单元测试设计
- 前端需求有组件化设计
- 数据库需求有 DB 设计
- 实施计划可直接执行

## 建议用法

对复杂需求，先用 `/designer:architect`，等设计文档稳定后，再进入实现阶段。这样可以显著减少边做边改、返工和接口跑偏。
