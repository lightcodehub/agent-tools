# /designer:architect

输出指导开发实现的概要设计、代码架构和功能详细设计。只写本项目的设计文档；不改业务或测试代码，不生成执行报告，不自动提交或创建 PR。已有设计经用户审核通过、适用于当前范围，且用户明确要求开发时，可直接交 developer。

## 确定依据与范围

默认先开展设计，在交付成稿时确认后续安排。若后续安排影响当前设计范围，可在开始时询问。

- **新项目**：从需求、使用边界和已确认约束形成方案；明确哪些是拟采用的组织、接口、框架和命令，不把规划写成已有实现。选择项目可用的框架；尚无测试框架时在设计中选定，不留给 developer。
- **存量补档**：先核实相关源码、测试、配置、调用链和已有文档，再按同一模板补齐缺失部分。不限范围时盘点各业务模块；局部请求只补目标及必要依赖。描述当前可证实的行为，区分合理设计、已证实缺陷和待核实风险；疑似缺陷不能直接成为正确预期。即使有阻塞，也先交付已核实部分。
- **迭代或实施退回**：依据当前范围、约束和缺项证据，原位更新关联设计、用例及引用。不以修改预期掩盖实现失败。

先用需求、代码、既有约定和已确认的答复解决设计问题。只有仍须用户决定且阻塞设计或实施的事项，才集中向用户提问，说明受影响的行为。等待答复时继续可独立推进的工作。模块未决项归 §11，跨模块未决项归总文档 §6.2，写明影响和确认方。收到答复或用户调整方向后，按最新要求复核范围，原位更新受影响的设计、用例和验收条件，继续推进。

## 模板使用规则

即使只有一个模块，也保留一份项目总文档和独立的业务模块文档。新建或完整补档使用对应模板；定点修改只取需要的模板段。既有有效结构使用等价章节，不为改编号重写无关内容。

| 交付物 | 负责说明 | 边界 |
| --- | --- | --- |
| [总文档](assets/design-index.md) → `design-doc/index.md` | §1 项目目标与范围，§2 方案、主链路和取舍，§3 代码组织、依赖、共享契约归属及模块索引，§4 约束的依据、范围和核验方式，§5 公共开发与测试约定，§6 风险与待确认事项 | 架构到业务模块、层、包或目录边界为止。正文、图、表及风险中不枚举内部文件、类或函数。仅当单文件本身构成有独立职责、公开契约和依赖边界的模块时可注明文件名；配置、命令和文档链接可保留。 |
| [模块文档](assets/design-module.md) → `design-doc/{module}/index.md` | §1 职责、依赖与必要实现映射，§2 内部协作、状态/资源归属与共享规则，§3 按功能集中说明行为及实际接口，§7 影响与兼容，§8 测试，§9 实施，§10 验收，§11 未决 | §4 数据、§5 数据库、§6 UI 和 §8.4 项目内集成按需出现，省略不重编号。新项目不预排私有文件，存量证据放在模块；不按 controller/service/repository 拆业务模块。 |

用总索引指向定义方的契约与具体章节。设计成稿引用章节时，用目标文档的实际标题；保留编号时写全“编号 标题”，跨文档指明归属。需要跳转的索引或定位字段使用对应锚点，普通叙述不要求加链接。按真实代码依赖画有向图，数据返回不算反向依赖；DFS 检查当前范围并注明依据，无环部分被依赖方优先。新方案有环，列出环内模块及合并、拆边两类选择，确认解除前不交实施。存量有环仍如实补档并标明风险，不伪造排序。

新建和补档的多功能索引固定为“功能、API 定义”两列；每个入口分别链接自己的签名定义。旧表的用例引用迁至对应功能小节末尾，保留适用分支与断言，核对后删除旧列。每项功能说明触发、关键处理、结果、副作用、失败后状态及验证关联。函数、方法和构造函数统一按“签名、简介、参数、返回、错误”定义，单参也列表，无参标明无。用实际行为划分功能，不以文件、接口或每个分支为单位。跨模块读写在归属模块定义操作与失败语义，调用方链接该契约；数据表不能替代操作契约。简单行为可用一段文字，复杂分支或协作用有信息量的图（Mermaid 使用合法节点 ID 和带引号标签）；普通私有实现留给开发，不贴完整函数或超过 15 行的连续业务代码。

## 测试设计与验收

1. 总 §5.1 用固定三列八行写公共代码规范，逐行核实依据、适用范围及检查方式；局部业务规则下沉。总 §5.2 定义框架、根配置与发现规则、允许的后缀及命名、可从任意目录定位的命令、隔离清理和 Git 约定；报告字段只写 `tests/test-report.md`。模块 §8.1 用有效相对链接定位 §5.2，补本模块可执行命令、前置条件、真实调用及替身边界。
2. 每个业务模块 §8.2 都定义可直接实施的 UT：场景、具体输入及初态、可断言预期、类型、状态，覆盖正常和异常行为。从契约推导必验边界：可独立失效的条件分别触发，写明可区分的输入和可观察预期；多实例可共用 ID，不按方法数判覆盖。§8.3 落实 `tests/{module}/unit/`、`integration/` 及实际调用的 support 源码路径、数据与资源。数据及产物归被忽略的 `build/tests/`；数据集、清理、例外及防护负向对照按实际需要写明。
3. 需要验证项目内组合时，由协调模块在 §8.4 唯一定义 IT，写清参与模块、真实内部调用、允许的替身、输入、预期、运行条件、文件与命令。单测只断言本层可观察结果；投递成功不证明异步下游完成。外部 API 默认由本地调用方用替身测契约，运行时故障策略单独定义，真实远端联调仅在有需求时安排。
4. 采用模块前缀 `{module}-UT-{NNN}` / `{module}-IT-{NNN}`，两类分别按 §8 定义顺序从 001 连续递增。多处引用只定义一次。按动作与实际断言**双向**核对 §3↔§8：剔除仅作准备/观测的功能，补齐对返回值、对象身份、错误或状态有独立断言的功能。同一功能含多个入口时，按入口和调用模式限定用例及断言；仅在适用范围相同时合写，不把编号列表分配给整组入口。跨文档引用附定义方章节链接。独立变体有可复现标识；依赖共享状态的顺序操作保留在同一场景。修改模块可重编号，按输入和预期同步本版引用，保留有效断言与参数标识。不要求其他 ID 或矩阵。
5. §9 按最早可独立验证的业务能力分步，每步写明依赖和可执行的完成条件，业务行为绑定当步能完整验证的用例。能先验的行为先实现并验证；不能因同属一个模块或共享状态，就把全部功能与全部 UT 合为一步。按实施起点、已完成的前置步骤和本步交付物核对每个用例；只声明类型或端口不能兑现业务断言。依赖后续实现的完整用例移到最早就绪步骤；不写估时。§10 将本次需求逐项关联设计和 UT/IT ID，非自动化条件给出具体核验方法及理由。未确认的预期不能写成验收标准。补档逐条复核已有和新增的 §10 条件；同一行既要求业务行为又要求测试交付时分行。业务已实现但缺验证为待测试，§8 尚未编写的用例为待实现。

| 当前问题 | 查阅位置 |
| --- | --- |
| 查找依据、定位依赖或受影响调用方 | [定向读取](references/scoped-reading.md#读取方式)；有契约锚点且 Python 可用时用随附 `scripts/read_section.py`。 |
| 功能边界、共享规则、接口与验证范围 | [模块设计](references/module-design.md#功能单元)及[用例标识与引用](references/test-management.md#测试用例标识与引用)。 |

## 交付

按[检查项](references/checklist.md)读回本轮成稿，核对引用、可执行性及文档与事实的一致性。原位清除失效描述与引用，不记对话、工作经过或版本沿革。只更新总文档和本次改动模块的设计时间。新步骤由 architect 初始化，实施后 §9 状态及实施时间归 developer，§8 自测日期取同版证据；§10 和模块头部完成须依据独立 validator。代码存在、补档完成、设计修改或同会话复核都不能证明验收通过，不编造历史日期。

聊天给出文档位置、范围、依据、方案、实际核验及实施就绪结论。存量补档另列问题、代码位置或调用链、影响、严重程度与建议。交付成稿时请用户审核。开发意图尚未明确时，在同一次询问中请用户决定是否按本版实施。用户已限定只做设计时，只请其审核。用户已明确要求审核通过后开发时，本版通过且实施条件就绪即可在授权范围内交 developer。仅有审核通过而缺少开发指令时，止于设计交付。用户要求修改时，更新受影响的部分并交回审核。存在阻塞则列明受影响范围；仅验证不自动授权改设计。正式验收在干净会话执行；developer 交验或在开发会话直接调用 validator 时，由独立子代理验收。
