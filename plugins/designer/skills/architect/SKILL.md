# /designer:architect

输出指导开发实现的概要设计、代码架构和功能详细设计。只写本项目的设计文档；不改业务或测试代码，不生成执行报告，不自动提交或创建 PR。已有有效设计足以实施时由 developer 直接使用。

## 确定依据与范围

- **新项目**：从需求、使用边界和已确认约束形成方案；明确哪些是拟采用的组织、接口、框架和命令，不把规划写成已有实现。选择项目可用的框架；尚无测试框架时在设计中选定，不留给 developer。
- **存量补档**：先核实相关源码、测试、配置、调用链和已有文档，再按同一模板补齐缺失部分。不限范围时盘点各业务模块；局部请求只补目标及必要依赖。描述当前可证实的行为，区分合理设计、已证实缺陷和待核实风险；疑似缺陷不能直接成为正确预期。即使有阻塞，也先交付已核实部分。
- **迭代或实施退回**：沿用原 scope、约束与缺项证据，原位更新关联设计、用例及引用；不复写未受影响模块，不以新预期掩盖实现失败。关键选择无法从资料确定时最多补问两轮；模块问题归 §11，跨模块归总文档 §6.2，写明影响和确认方。

## 模板使用规则

即使只有一个模块，也保留一份项目总文档和独立的业务模块文档。新建或完整补档使用对应模板；定点修改只取需要的模板段。既有有效结构使用等价章节，不为改编号重写无关内容。

| 交付物 | 负责说明 | 边界 |
| --- | --- | --- |
| [总文档](assets/design-index.md) → `design-doc/index.md` | §1 项目目标与范围，§2 方案、主链路和取舍，§3 代码组织、依赖、共享契约归属及模块索引，§4 约束的依据、范围和核验方式，§5 公共开发与测试约定，§6 风险与待确认事项 | 架构到业务模块、层、包或目录边界为止。正文、图、表及风险中不枚举内部文件、类或函数。仅当单文件本身构成有独立职责、公开契约和依赖边界的模块时可注明文件名；配置、命令和文档链接可保留。 |
| [模块文档](assets/design-module.md) → `design-doc/{module}/index.md` | §1 职责、依赖与必要实现映射，§2 内部协作、状态/资源归属与共享规则，§3 按功能集中说明行为及实际接口，§7 影响与兼容，§8 测试，§9 实施，§10 验收，§11 未决 | §4 数据、§5 数据库、§6 UI 和 §8.4 项目内集成按需出现，省略不重编号。新项目不预排私有文件，存量证据放在模块；不按 controller/service/repository 拆业务模块。 |

用总索引指向定义方的契约与具体章节。按真实代码依赖画有向图，数据返回不算反向依赖；DFS 检查当前范围并注明依据，无环部分被依赖方优先。新方案有环，列出环内模块及合并、拆边两类选择，确认解除前不交实施。存量有环仍如实补档并标明风险，不伪造排序。

多功能模块提供“功能—入口—行为位置”导航。每项功能说明触发、前置与输入、关键处理、结果与副作用、失败后状态、验证关联；新增或变更接口明确签名、参数、返回和错误。用实际行为划分功能，不以文件、接口或每个分支为单位。跨模块读写在归属模块定义操作与失败语义，调用方链接该契约；数据表不能替代操作契约。简单行为可用一段文字，复杂分支或协作用有信息量的图（Mermaid 使用合法节点 ID 和带引号标签）；普通私有实现留给开发，不贴完整函数或超过 15 行的连续业务代码。

## 测试设计与验收

1. 总 §5.1 用固定三列八行写公共代码规范，逐行核实依据、适用范围及检查方式；局部业务规则下沉。总 §5.2 定义框架、根配置与发现规则、允许的后缀及命名、可从任意目录定位的命令、隔离清理和 Git 约定；报告字段只写 `tests/test-report.md`。模块 §8.1 用有效相对链接定位 §5.2，补本模块可执行命令、前置条件、真实调用及替身边界。
2. 每个业务模块 §8.2 都定义可直接实施的 UT：场景、具体输入及初态、可断言预期、类型、状态，覆盖适用的正常、边界和异常。§8.3 落实 `tests/{module}/unit/`、`integration/` 及实际调用的 support 源码路径、数据与资源。数据及产物归被忽略的 `build/tests/`；数据集、清理、例外及防护负向对照按实际需要写明。
3. 需要验证项目内组合时，由协调模块在 §8.4 唯一定义 IT，写清参与模块、真实内部调用、允许的替身、输入、预期、运行条件、文件与命令。单测只断言本层可观察结果；投递成功不证明异步下游完成。外部 API 默认由本地调用方用替身测契约，运行时故障策略单独定义，真实远端联调仅在有需求时安排。
4. 采用模块前缀 `{module}-UT-{NNN}` / `{module}-IT-{NNN}`，两类分别按 §8 定义顺序从 001 连续递增。多处引用只定义一次。按动作与实际断言**双向**核对 §3↔§8：剔除仅作准备/观测的功能，补齐对返回值、对象身份、错误或状态有独立断言的功能。混合参数组标明各功能适用的实例和具体断言，不用整段编号泛指。跨文档引用附定义方章节链接。独立变体有可复现标识；依赖共享状态的顺序操作保留在同一场景。修改模块可重编号，按输入和预期同步本版引用，保留有效断言与参数标识。不要求其他 ID 或矩阵。
5. §9 按最早可独立验证的业务能力分步，每步绑定功能、依赖和当步可完整运行的用例。能先验的行为先实现并验证；不能因同属一个模块或共享状态，就把全部功能与全部 UT 合为一步。需后续能力的场景留到依赖就绪时，不拆散断言；不写估时。§10 将本次需求逐项关联设计和 UT/IT ID，非自动化条件给出具体核验方法及理由。未确认的预期不能写成验收标准。补档逐条复核已有和新增的 §10 条件；同一行既要求业务行为又要求测试交付时分行。业务已实现但缺验证为待测试，§8 尚未编写的用例为待实现。

## 按任务取用规则

沿索引定位目标及必要调用方；完整读取命中本次能力的库 skill、相关 API 和实际调用，不自动注册。先定位所需章节；当前上下文已读且仍有效的不重读。示例不是默认输入，只有复杂文档组织无法由模板解释时才查[相应示例](references/examples/index.md)。

| 当前问题 | 查阅位置 |
| --- | --- |
| 查找依据、定位依赖或受影响调用方 | [定向读取](references/scoped-reading.md#读取方式)；有契约锚点且 Python 可用时用随附 `scripts/read_section.py`。 |
| 功能边界、共享规则、接口与验证范围 | [模块设计](references/module-design.md#功能单元)及[用例标识与引用](references/test-management.md#测试用例标识与引用)。 |
| 填写项目级约定与模块测试细则 | [代码规范八项](references/coding-conventions.md#固定格式与覆盖维度)及[测试管理](references/test-management.md)的适用章节。 |
| UI、持久化、外部服务 | 按[专项设计](references/conditional-design.md)选择所需章节和模板；不生成占位章节。 |
| 文档表达、状态及交付核验 | [实施状态](references/document-style.md#实施状态判定)、[交付前文档核验](references/document-style.md#交付前文档核验)。 |

## 交付

按[检查项](references/checklist.md)读回本轮成稿，核对引用、可执行性及文档与事实的一致性。原位清除失效描述与引用，不记对话、工作经过或版本沿革。只更新总文档和本次改动模块的设计时间。新步骤由 architect 初始化，实施后 §9 状态及实施时间归 developer，§8 自测日期取同版证据；§10 和模块头部完成须依据独立 validator。代码存在、补档完成、设计修改或同会话复核都不能证明验收通过，不编造历史日期。

聊天给出文档位置、范围、依据、方案、实际核验及实施就绪结论。存量补档另列问题、代码位置或调用链、影响、严重程度与建议。仅要求设计时到此结束；原任务含实施且本范围与必要依赖已就绪时返回 developer。存在阻塞则列明受影响范围；仅验证不自动授权改设计。正式验收在干净会话执行；developer 交验或在开发会话直接调用 validator 时，由独立子代理验收。
