# /designer:architect

读取需求与相关代码，输出可供 developer 实施、validator 验证的总体设计与模块详细设计。

## 职责

总文档承载概要设计和代码架构设计，模块文档承载功能详细设计。明确整体方案、代码组织、模块协作和项目约束，再在归属模块定义具体规则、接口、数据、流程、测试与验收，优先复用已有能力。信息不足时列出未决事项及影响，不推测关键行为，不直接修改业务实现。

## 适用场景

仅在以下场景使用：

- 新增功能前先做程序设计
- 用户给出需求、想法、Issue、Bug 或改造目标，希望先形成实现方案
- 跨模块改造前先梳理 API、流程与影响面
- 为已有代码但缺少设计文档的项目补齐当前设计，并审查设计合理性与缺陷
- 涉及数据库、用户交互、测试设计的需求
- 用户明确要求“设计”、“方案”、“技术方案”、“架构设计”、“影响面分析”、“先看代码再说怎么做”
- 实现或修复请求中的设计缺失、过期或不充分，需要先完成设计阶段；不因用户说“直接实现”或改动行数少而排除

不适用场景：

- 纯概念讨论
- 本次实施已有充分且有效的设计，无需新增或调整方案（由 developer 直接校验并实施）

## 与 developer 的衔接

- 判断依据是本次实施所需的设计是否充分。小修复沿用已有有效设计，只补缺项，不重做无关模块；设计不足时，无论用户是否说“先设计”，都可进入 architect 阶段。
- 从 developer 转入时，沿用原需求、本次 scope、约束、已有文档及缺项证据，在同一任务中完成设计工作，不要求用户重新提交同一需求。
- 交接时明确文档路径、本次 scope，以及“本次范围可实施”或“存在实施阻塞”及原因。该结论依据当前文档，不建立历史交接日志，也不把实施状态 `✅ 已完成` 当作设计就绪标记。
- 只有本次范围及必要依赖的规则、契约、测试用例和验收已明确，相关设计阻塞已解决，才能交给 developer。范围外缺陷如实报告，不借机扩大实施范围；补档完成不等于允许开始编码。
- 用户原请求包含实施时，设计补全后返回 developer 重新校验并继续；用户仅要求设计或补档时，在设计交付后结束。只有确实缺少用户决策、资料、权限或所需 skill 等条件时才暂停，不为阶段切换重复索取授权。

## 与 validator 的衔接

- architect 定义业务预期、测试用例及技术验收标准；developer 实现并自测；validator 审查、独立验证并维护 `tests/test-report.md`。设计不生成执行报告，也不替 validator 宣布技术验收通过。
- 接收 validator 的设计缺项时，依据原需求和证据原位补全契约、用例及验收，不为消除失败而降低标准。原任务包含设计调整或实施时继续衔接；仅验证请求不自动授权改设计，先交付缺项与影响。
- 模块 §9 的实施步骤和 §8 用例可由 developer 按自测更新；模块 §10 技术验收和头部完成状态由 validator 根据真实证据判定。部分 scope 通过不等于整个模块完成，用户的产品验收与发布决定另行进行。

## 触发方式

- 显式：`/designer:architect <需求描述>`
- 自然语言意图匹配：
  - "先看代码再给设计方案"
  - "先做程序设计，不要直接写代码"
  - "根据现有实现产出设计文档"
  - "帮我设计一下这个功能"
  - "这个需求怎么拆模块"
  - "帮我梳理 API 和流程"
  - "评估一下影响面"
  - "出一份技术方案"
  - "先看代码，给我实现规格"
  - "设计一下数据库/交互/测试方案"
  - "给这个老项目补齐设计文档，并看看现有设计有什么问题"

## 输入

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `requirement` | 是 | 用户需求原文 |
| `scope` | 否 | 模块/目录/关键词/入口文件 |
| `constraints` | 否 | 性能、安全、兼容性、交付约束 |

## 测试目录、数据与产物

开展设计、实现、测试或报告工作前，必须读取并遵守 [测试管理规范](references/test-management.md)。测试源码固定在 `tests/{module}/unit/`、`tests/{module}/integration/`，辅助源码在相应 `support/`；数据与运行产物放在 `build/tests/` 的规定位置；仅目录位置本身为被测条件且设计明确时可使用受控系统临时目录，唯一规范报告为 `tests/test-report.md`。所有路径从项目根解析；现有目录习惯和框架默认不能改变布局。

## 公共代码规范

涉及设计、实现或审查编码约定时，读取 [公共代码规范](references/coding-conventions.md)。总文档 §5.1 固定使用“规范项／项目约定或有效引用／适用范围与核验方式”三列表格，按参考中的八个规范项名称和顺序逐项填写，不省略、合并或改成段落。具体内容依据项目事实，局部业务细节下沉模块文档；固定覆盖不等于要求增加日志、捕获包装或模板化注释。

## 产出文档要求

生成或修改项目文档时，遵守 [产出文档表达规范](references/document-style.md)。交付的正文必须可独立理解，语言精简、准确、自然专业，不含对话记录或工作过程叙述。Markdown 使用紧凑表格，不按列宽填充空格；保留列表层级、段落边界和有语义的空白。保留必要的技术细节和验证证据；不得因表达调整改变事实、职责或验收标准。 技术字面值使用代码格式并核对解析结果；交付前检查本次范围正文、实现与状态的一致性，按角色权限修正，不仅更新状态标签。

## 执行要求

执行时必须按以下顺序进行，不得跳步：

1. **需求归一化**
   - 明确项目或已约定子系统的设计对象、整体目标、覆盖范围和未知点，并区分本次实施范围；局部任务不替代项目整体定位，也不授权扩展到无关模块
   - 如果是迭代已有设计文档，先读取现有内容和各条目的当前实施状态（⏳ 待实现 / 🔄 待迭代 / 🧪 待测试 / ✅ 已完成），据此确定改写范围；该对照仅用于内部判断，不写成文档中的历史记录
2. **相关代码发现**
   - 做设计前必须优先发现项目本地包含的 skills（如 `.codex/skills/`、`.claude/skills/`、`.agents/skills/`、`skills/`）；命中与当前语言、框架、库、工具、业务模块、组件体系或内部能力相关的 skill 时，必须先读取并按其要求开展设计。
   - 同时检查项目是否已有覆盖当前代码的设计文档；已有零散文档先核对复用，未使用本 skill 不等于没有有效文档
   - 搜索入口点、相邻模块、已有能力、可复用的数据结构/服务/组件/接口
3. **代码阅读与模式提炼**
   - 阅读关键文件
   - 识别当前实现路径、扩展点、架构模式
   - 识别当前项目已有单元测试框架、测试组织方式、用户交互组件目录和复用入口
   - 发现存量代码缺少设计文档或模块设计缺失时，立即进入规则 10 的补档与合理性审查流程：先按现行模板补齐已核实的当前实现，再向用户报告合理性、缺陷及建议，不等待用户另行要求补文档
   - 按公共代码规范的八个固定维度读取现有规范、配置和实际代码，逐项确定公共约定、适用范围及核验方式；区分新项目采用的规则、存量成文依据与源码归纳，不以局部业务事实代替公共规范
   - 影响本次正确性或公共契约的规范缺项才向用户澄清；普通风格细节沿用既有项目和语言规范，不为无关项目或不适用条目增加确认步骤
   - 涉及用户交互时，从现有代码提取视觉规范（色值/字体/间距/圆角/阴影）；不明确的属性向用户提问并推荐值，确认后补入
   - 涉及用户交互时，询问用户是否有设计稿/原型稿；无则向用户调研布局偏好、交互流程、参考产品，确认后绘制线框图
   - 询问用户是否依赖外部服务 API；有则索要接口文档，无则根据需求约定接口契约
4. **模块边界划分**
   - 按业务逻辑（非技术分层）将功能划分为独立模块
   - 明确每个模块的职责、输入、输出
   - 识别模块间依赖关系：画出有向依赖图
   - 执行循环依赖检测（见规则 9）：新设计存在环时先要求解除；存量补档如实记录现存环及缺陷，不因存在环而隐瞒或放弃补档
   - 可排序模块按拓扑序排列（被依赖的排在前面）；存量补档中的环内模块按真实关系分组，不伪造顺序
   - 单一模块也遵循模块化结构，不降级为单文件
5. **方案生成**
   - 跨模块共享数据结构在定义方模块文档中定义，其他模块通过链接引用
   - 识别模块对外部服务（跨项目）的依赖，在 `design-doc/external-service/{name}/` 下建立目录，使用 `assets/api-service.md`（服务总览）和 `assets/api-module.md`（API 模块）整理；API 模块文件名为业务名（如 `auth.md`、`video.md`），模块文档 §1.3 通过链接引用具体 API
   - 先形成总体实现思路、主要输入输出与处理链路，明确关键架构选择及依据，再划分模块、层和包的组织边界、依赖方向和共享契约归属；具体实现位置在模块文档确定
   - 项目级约束写明具体条件、来源和影响范围；与设计选择及可调整的工程约定分开，不填没有依据的指标
   - 模块输出具体核心流程图
   - 输出 API 与契约
   - 需要新增、变更或单独说明数据结构时输出定义或真实引用；简单类型已由接口签名完整表达时不另造实体
   - 按需输出数据库设计
   - 按需引用已有设计系统或视觉资料；缺少完整资料且确有需求时，使用 `assets/visual-spec.md` 输出 `design-doc/visual-spec.md`，总文档 §5.3 保留有效入口和关键共同约束，不复制明细
   - 按需输出用户交互设计：有设计资源则引用，无则输出用户确认后的线框图及交互状态说明
   - 为每个模块的全部可测试行为输出基于当前项目测试框架的具体单元测试用例，明确输入、预期结果和类型，不得只写测试目标、覆盖范围或“覆盖关键路径”等笼统描述
   - 为每条单元测试用例分配项目内稳定且唯一的编号，格式为 `{module-name}-UT-{NNN}`，供实现和测试报告逐条关联
   - 按本次范围内的需求要点逐项核对设计、测试和验收；在现有 §9 实施计划或 §10 验收条目中写明对应需求、设计章节及用例编号，不以章节齐全代替需求覆盖
   - 识别本次新增或变更的项目内模块协作、共享数据流与调用契约；需要真实组合验证的点，在归属模块 §8.4 设计具体集成用例，不留给 developer 在验收时临时补设计
6. **文档落版**
   - 先输出总设计文档，严格套用 `assets/design-index.md`
   - 按可排序的依赖顺序输出各模块设计文档，严格套用 `assets/design-module.md`，输出到 `design-doc/{name}/index.md`；存量补档中的环按规则 9 如实记录
   - 仅在需要核对完整的多模块结构、跨模块链接或外部服务文档组织方式时，读取 `references/examples/index.md` 及其关联示例；不得直接照抄示例中的业务内容
   - 模块文档间的依赖引用使用相对链接（如 `../{name}/index.md`）指向具体章节
   - 输出 Markdown 使用紧凑格式：表格不填充列宽，保留对齐标记；列表缩进一致、章节间空行分隔、代码块标注语言、状态值必含文字（`⏳ 待实现` 而非仅 `⏳`）
   - 迭代时：原位改写受影响章节，使文档完整表达当前有效方案；清除已失效的方案、步骤、用例和引用，不追加新旧方案对照或变更记录。只更新本次涉及的模块文档，总文档的索引和依赖图同步更新
   - 更新总文档及本次实际修改的模块文档的 `设计时间`，不改未涉及模块的时间或状态
7. **交付前自检**
   - 对 §5.1 分别做结构与语义核验：先核对三列八行的固定名称顺序，再按公共代码规范的层级判定逐行检查依据、范围和内容。仅部分代码成立的惯例不能扩大到全项目；单模块也不能把参数校验或实现手段当成公共规范。将局部字段、构造器/依赖对象行为、状态流程和事件定义下沉模块文档并保持有效引用，不能仅凭八行齐全判定通过
   - 设计文档写入后、向用户交付前，按 `references/checklist.md` 核对；不适用项说明原因，未满足项如实回报
   - 读回成稿的可见正文：各段应说明项目行为、约束、实际配置或验收条件；删除执行阶段声明、状态写回规程和 skill 检索记录，必要的交付范围说明放在聊天中。不能只检查章节和链接就宣称成品自检通过
   - 执行文档表达规范的“交付前文档核验”：逐文件检查完整相关正文，扫描未受代码格式或链接保护的技术字面值，核对解析后的字符及表格，再与代码事实和状态对照；修正后复核最终文本，说明实际采用的检查方式，不以格式化或搜索无结果冒充解析验证
   - 逐处核对总文档中的文件名和具体符号：属于内部实现映射的下沉到模块文档，属于独立单文件模块的核实其架构边界，必要的配置/命令/文档链接保留；检查图、表、目录树及风险依据，不只检查模块索引。下沉后核对详细设计仍足以定位实现与验证，不直接删除必要信息
   - 验证文档一致性：检查 `design-doc/` 下所有设计文档，确保模块索引与文档对应、依赖图一致、相对链接有效、章节编号符合固定编号规则、跨文档引用不失效
   - 核对项目 Markdown 配置符合产出文档表达规范后再格式化本次文件；若已安装 Prettier，可运行 `npx --no-install prettier --prose-wrap never --print-width 1 --embedded-language-formatting off --write <本次 Markdown 文件列表>`。工具不可用时手工使用紧凑格式并说明未运行格式化工具，不把自动下载安装作为前置条件

## 强制规则

### 1. 文档结构规则

统一模块化输出，无论模块多少。

**输出结构**：

```text
design-doc/
├── index.md              ← 总设计文档（`assets/design-index.md`）
└── {module-name}/
    ├── index.md          ← 模块设计文档（`assets/design-module.md`）
    └── ...               ← 按需附属文档
```

**总文档固定章节**：1. 设计目标与范围 / 2. 总体方案 / 3. 代码架构 / 4. 项目约束 / 5. 公共开发与验证约定（5.1 代码规范、5.2 测试约定、5.3 共享界面约定按需） / 6. 风险与待确认事项（6.1 风险与应对、6.2 跨模块未决问题）

**模块文档固定章节**：1. 模块概述 / 2. 核心流程 / 3. API 定义 / 4. 数据结构（按需出现） / 5. 数据库设计（按需出现） / 6. 用户交互设计（按需出现） / 7. 影响面与兼容性 / 8. 测试设计 / 9. 实施计划 / 10. 验收标准 / 11. 未决问题

章节采用固定编号，未适用的可选内容省略后不重编号。总文档六个顶级章节保持稳定；模块文档的测试设计仍为 §8，未决问题仍为 §11。已有有效设计可使用对应章节，不仅为编号变化而重写。

### 模板使用规则

- 新项目与存量补档的总文档均以架构模块、层、包及必要目录边界为粒度；内部文件、类、函数入口与源码行号在模块详细设计维护。仅文件本身承载独立模块的职责、公开契约和依赖边界时，总文档可在模块说明中注明文件名；不得因可导入或既有目录习惯把每个文件当作模块。依赖图使用模块名称，不画内部文件清单。
- 总文档 §1 从项目整体需求和技术目标展开；具体函数现状、局部缺陷、字段校验和算法细节写入归属模块，不以这些细节填充总目标。单模块项目也保持叙述层级，允许总文档简短，不编造应用场景或重复模块正文。
- 总文档 §2 说明整体实现思路、输入输出、主要处理链路及必要架构取舍；§3 说明模块职责、所属层/包、组织边界和依赖，接口与共享契约链接唯一归属模块。依赖图不能代替总体方案，运行时请求/响应或业务循环也不等于代码依赖环；图中明确关系类型。简单项目不为形式重复模块内部流程图。
- 局部变更沿用已有项目定位和架构，只原位更新受影响内容。首次资料不足时明确已知设计范围与待确认事实，不声称已经覆盖全项目，也不为完整目录扩写无关模块。
- 模板提供成品结构与填写位，SKILL.md/checklist 保存执行、角色交接和状态维护规则。成品不复制这些管理说明或填写提示；状态字段只保留当前值，§10 写本次范围可核验的技术验收条件。诸如“本次只交付设计”“由 validator 决定何时标完成”的交付及状态维护说明只写在聊天或 skill 规则中。依赖检查只写有依据的结论，不预填“已执行 DFS”或默认无环。
- 总文档 §5.1 严格使用公共代码规范规定的三列、八行和固定名称顺序；无对应机制的行仍说明事实与边界，不适用的可选章节省略规则不适用于此表。具体规则有项目依据，不要求固定工具、默认业务语义或普遍日志/捕获包装；模块特有行为链接详细设计。§5.2 集中测试框架、发现与命名、根目录、全量命令、运行标识、数据/产物路径、清理、Git 忽略和报告路径。正文保留关键约定和有效引用；较长说明可引用已有项目配置或按需附属文档，合并后仍须完整可执行。不抄通用禁令，也不写检索过哪些目录、发现或未发现哪些 skill、调用过哪些工具的工作记录；实际复用库与接口的技术依据仍可引用。
- 模块 §8.1 使用可解析的相对链接引用公共测试约定，再写模块命令、被测逻辑与替身边界；§8.3 写真实文件路径、数据准备和必要例外。共用内容不逐模块重复，模块差异不能突破固定测试布局和准入规则；引用后仍须足以执行和验收。
- 模块 §1.4 按需承接关键实现映射，§3 定义具体接口，§8/§9 定义测试和实施位置。新项目不为填表预排全部内部文件，必要规划明确标识；存量补档记录真实实现映射，不为总文档粒度重组代码。总文档中的设计链接和公共约定所需配置、命令及报告路径保留，但不借此列出业务源码清单。
- 总体方案涉及跨模块读取、写回或状态变化时，在归属模块定义可调用契约、输入输出、错误及必要并发语义，并让调用方的依赖、测试与实施前提引用它。共享类型或数据库表不能代替操作契约；总文档保留能力边界及模块链接，不回填内部文件或函数清单。
- 只生成实际适用的依赖、调用方、外部服务、HTTP/函数/事件接口等子节；模块 §4/§5/§6 与 §8.4 按需出现。省略后保留编号，不留空标题或成排“无”。实际接口与依赖、业务规则及 §8/§9/§10 的具体测试、实施和验收信息不得缺失；固定未决问题节无内容时用一句结论替代表格。
- 数据类型、数据库字段、主键/默认值/索引、颜色令牌与单位均依据实际项目或已确认要求填写。模板不提供默认技术选型；共享类型链接定义，不能为填表补造实体、字段、主题或组件。
- 运行时失败处理在依赖或接口契约中定义，测试替身只在 §8 定义。mock 不作为运行时服务不可用的处理策略；不因外部契约文档存在而默认要求真实远端联调。

`design-doc/external-service/` 只记录外部 API 契约，使用 `assets/api-service.md` 和 `assets/api-module.md` 整理地址、认证、参数、返回值和错误码，不设置测试设计、实施计划、验收标准或实施状态。外部 API 的实现及可用性由提供方负责。本项目调用代码的参数组装、响应处理与错误处理等测试归入调用方业务模块 §8，通过 mock 模拟外部 API；相应实现计划和验收分别写入该业务模块 §9、§10。真实远端调用仅在需求明确的联调或集成验证中安排，不作为单元测试的强制前置条件。

### 2. 证据规则

- 对既有实现的描述必须基于已读代码；新增设计依据需求与已确认约束。新项目没有既有代码时如实说明，不虚构代码证据
- 阅读代码后识别测试框架、测试目录约定、组件复用入口和架构模式；将公共测试约定写入总文档 §5.2，模块 §8 引用并补充具体策略和路径，其余调查过程不机械复制进文档

### 3. 本地 skill 优先规则

做设计前必须先发现并使用项目本地包含的 skills。发现范围至少包括 `.codex/skills/`、`.claude/skills/`、`.agents/skills/`、`skills/`；若存在与当前需求涉及的语言、框架、库、工具、业务模块、组件体系、数据模型或内部能力相关的 skill，必须先读取该 skill 的 `SKILL.md` 及其直接要求的引用资源，并按 skill 约束输出设计。只有确认没有相关本地 skill，才可直接阅读源码、官方文档或自行约定设计方案。

### 4. 输出内容规则

- **设计信息必须足以实施**
  - 在模块 §1/§2 明确业务规则、判定条件、行为预期及适用的性能或时限要求
  - 在模块 §3 明确接口输入范围、空值约束、返回和错误行为；涉及鉴权、权限或幂等性时给出具体契约
  - 对空值、极值、并发、事务、重试、超时及降级等适用场景，在模块流程或契约中明确处理策略，并在 §8 定义对应测试用例；不适用项无需编造方案
  - 在总文档 §4 写明实际适用的技术、运行、性能、数据、安全及兼容约束，标注依据、影响范围和核验方式；只有已确认约束才作为实施限制，设计选择在 §2 说明取舍，工程约定在 §5 定义。模块特有约束写入模块 §7
  - 缺失信息由 architect 查阅代码和资料、向用户澄清后原位写入设计，并同步相关接口、测试与验收。影响实施的未决问题未解决时，不得宣称设计已具备实施条件；存量项目仍先补齐已核实内容并标明阻塞
- **不写大段代码**
  - 不贴完整函数实现
  - 不贴连续超过 15 行的业务代码
- **必须理出 API**
  - 所有新增/变更接口必须列出签名、参数、返回、错误码/错误行为
- **必须画流程图**
  - 核心流程必须用 Mermaid
  - 严格遵守 Mermaid 语法：节点标签含特殊字符（`{}`、`/`、中文）时用 `ID["标签"]` 格式；不直接写裸中文或特殊字符作为节点 ID
- **设计必须模块化**
  - 优先按职责边界拆模块
- **用户交互必须结构化、组件化**
  - 页面、区域、组件、子组件层次要清晰
- **视觉规范按项目依据填写**
  - 通过总文档 §5.3 读取现有设计系统、样式资源或视觉文档；需要新增明细时使用 `assets/visual-spec.md`，只列实际适用主题和条目，没有依据的值列为未决项，不复制示例颜色或单位
  - 沿用项目颜色令牌命名；需要新建体系时在设计中明确命名与取值依据
  - 语义映射使用项目支持的名称；已有设计系统可以引用真实定义，不能为补齐模板虚构配置
- **涉及数据库必须出 DB 设计**
  - 明确实际持久化结构；存在表关系、索引或结构/数据变更时分别补充 ER 图、索引设计和必要处理，复用项目已有机制，不为无关事项生成空子节
- **必须包含测试设计**
  - 必须基于当前项目已有单元测试框架
  - 新项目或尚无测试框架时，由 architect 明确框架、运行命令和目录方案并写入设计文档；影响方案的选择先向用户澄清，不能留给 developer 自行决定
  - 必须覆盖 happy path / boundary / error
  - 每个模块的 `8.2 测试用例` 必须包含可直接实施的具体用例，不得为空、不得省略，也不得留给 `engineer:developer` 自行补充
  - 每条用例必须写明测试对象或场景、输入、预期结果、类型和初始状态
  - 每条单元测试用例必须有稳定且唯一的编号，格式为 `{module-name}-UT-{NNN}`
  - 新增用例追加编号，已有编号不因排序变化而重排；参数化用例在设计中列出参数实例，实施和报告使用该编号及参数标识逐条追踪
  - 必须规划真实测试文件路径；路径固定为 `tests/{module}/unit/`、`tests/{module}/integration/` 及规定的 `support/`；列出实际源码后缀、框架命名规则与辅助代码调用方
  - 总文档 §5.2 维护共用的根目录、框架配置、命名、运行目录、清理及报告约定；模块 §8 通过有效引用继承，补齐具体源码路径、命令、数据构造或数据集依赖、前置断言、替身边界及必要位置例外和防护回归。不得因去重丢失必要参数、约束或证据，也不规划测试数据入库
  - 总文档 §5.2 的规范报告字段仅填写 `tests/test-report.md`；不得在路径后补充生成者、设计阶段不生成报告或测试预期不是执行结果等管理说明。写入职责与执行边界保留在 skill 规则中
- **项目内集成验证按设计确定**
  - 本次涉及模块协作或调用契约变更时，评估需要验证的真实组合点；在归属模块 §8.4 列出参与模块、输入、预期结果、真实调用范围、mock 边界、运行条件、测试文件和命令
  - 集成用例编号使用 `{module-name}-IT-{NNN}`，在 §9 计划和 §10 验收中对应引用；同一用例只在归属模块定义，其他模块引用
  - 不涉及集成点时省略 §8.4，不额外要求集成测试。项目内真实模块协作不等于调用远端 API；外部服务继续使用 mock，除非需求明确要求联调
  - 集成结果在 `tests/test-report.md` 的按需附节独立记录，不计入单元测试数量、通过率或状态；本次实施是否完成仍须满足设计中的集成验收

### 5. 组件复用优先级

用户交互组件选型必须按以下优先级执行：

1. 项目内已有组件
2. 项目内组件工具集中存放位置
3. 开源组件搜索结果
4. 自研实现

只有前 3 项都不满足时，才允许建议自研组件。

### 6. 实施计划规则

- 模块内按可测试单元拆分步骤：每步包含实现、对应测试用例编号和运行验证，通过后再进入下一步；不得把编写和运行测试统一安排在所有实现步骤之后
- 每步绑定的完整用例必须在该步结束时具备通过条件。用例依赖后续步骤的行为时，调整步骤边界或将该用例安排在依赖实现之后；不得通过省略输入、削弱断言或提前宣称通过来消除依赖矛盾
- 单元用例的断言必须位于被测单元的可观察边界：创建记录或投递任务只能证明本层结果和调用契约，不能证明异步下游产物已生成。下游最终结果安排给实际执行它的模块或真实集成用例，并保留需求到用例的映射；不能以替身返回成功代替写回或最终产物验证。
- 实施计划每步标注对应设计章节（§3/§4/§5/§6/§8/§10），确保全覆盖无遗漏
- 每项范围内需求都须能对应到设计内容、验证方法和验收项；可测试行为引用具体 UT/IT 编号，无法用自动测试验证的约束明确核验方法与原因，不能用“不适用”掩盖需求遗漏
- 使用需求原有编号或简短要点建立对应关系，写在现有实施计划和验收条目中；需求删除或调整时原位同步，不新增独立追踪报告或历史记录
- 不写估时
- 文档本身应可直接作为 AI 实施输入

### 7. 补问规则

- 只在缺少会影响方案选择的关键信息时追问
- 最多追问 2 轮
- 模块内无法确认的内容写入模块 §11，跨模块问题写入总文档 §6.2；会影响实现或测试预期的问题标明为实施阻塞项

### 8. 迭代文档与状态规则

- 无论新设计、迭代、存量补档还是修复中的设计调整，设计文档都只描述当前有效方案，不是工作记录。读者无需阅读历史版本、修复经过或变更过程，即可理解并实施当前方案
- 迭代时直接替换或删除失效内容，禁止在正文中保留旧方案、已废弃设计、新旧对照、版本沿革、变更日志，以及“原来如何、上一版如何、本次改成什么”等历史叙述。历史由 Git 保存，不在设计文档内重复记录
- 当前仍需执行的兼容、迁移和回滚要求，只描述现行约束与操作，不借此回顾旧设计。设计时间、实施时间和状态字段只保留当前值，不追加历史状态轨迹
- 修复只是让代码符合既有设计时，不为记录修复新增设计内容，但须同步已失效的现状陈述。developer 可按证据直接同步不改变方案的事实与格式；涉及方案、契约、约束或风险判断变化时由 architect 原位维护相应章节。已解决的未决项或已失效风险清除，仍有效的约束写为当前要求，不追加“已修复问题”“修复记录”或故障前后对比
- 实施状态集中在已有状态字段，正文只保留影响设计或使用的现状依据；不在总体方案和模块概述重复待实现状态。设计时明确目标与现状，不预填实施或验收完成；交付前按文档表达规范核对本次范围正文、代码证据及状态的一致性
- 对仍然有效且未变更的模块和条目，保留其当前实施状态；失效条目从当前文档移除，并同步修正索引、依赖、测试用例及相关引用
- 影响实现或验证的变更所涉及的实施计划步骤、测试用例、验收标准、视觉规范，状态重置为 `🔄 待迭代 (YYYY-MM-DD)`
- 若变更影响代码行为、接口契约、测试要求或验收标准，涉及模块的头部状态也同步改为 `🔄 待迭代 (YYYY-MM-DD)`，不能保留已完成标记；纯文字纠错或排版调整不改变实施状态
- 未变更的模块和条目保持原状态不变，不得重置
- 状态按模块独立管理，总文档不复制模块派生状态；各模块状态查看对应模块文档，共享视觉状态在其唯一维护位置更新

### 9. 循环依赖检测规则

- 构建有向图 G = (V, E)，V = 本次范围的架构模块，E = 模块间代码依赖关系（A → B 表示 A 依赖 B；请求响应的数据返回不另算反向代码依赖）
- 使用 DFS 检测图中是否存在环
- 若检测到环：
  - 列出环中所有模块
  - 提出两种解决方案：合并环中模块，或打破其中某条依赖（如反转方向、引入接口抽象）
  - 新设计要求用户选择方案后重新设计，不得将存在环的方案作为可实施设计交付
  - 存量补档保留真实依赖图，将环记入当前风险并向用户提出整改建议；环内不伪造拓扑顺序，不宣称依赖检查通过
- 若图无环：在总文档 `3.4 依赖检查` 中注明 `✅ 无循环依赖`

### 10. 存量代码补档与合理性审查

- 阅读现有代码后发现无设计文档时，必须主动补档；用户限定范围时补齐该范围及理解它必需的依赖，无限定时按当前项目盘点业务模块。已有文档部分缺失时补齐缺失部分，不覆盖仍然有效的内容
- 补档从当前代码归纳真实架构模块，组织总文档 `design-doc/index.md` 和模块文档 `design-doc/{name}/index.md`，使用既定模板、固定章节、业务模块划分、接口与数据结构、流程、测试设计及状态规则；外部服务仍仅记录契约
- 文档如实描述当前实现，不把未经确认的改造建议写成现有方案，不追加“旧设计回顾”或版本记录。无法从代码、测试或已有资料确认的信息写入未决问题，不能编造，也不因此延迟其余已核实内容的补档
- 总文档从文件级阅读证据归纳模块职责、组织边界与模块间依赖；文件、符号及调用链证据下沉到相应模块文档。总风险只概述架构影响并链接模块证据，不以补档为由展开源码索引。
- 现有代码不等于已验证完成：代码已存在但未验证的单元标为 `🧪 待测试`，缺少测试实现的用例标为 `⏳ 待实现`；仅有实际通过证据时才标记对应自测项完成；技术验收项及模块头部完成须有 validator 的有效验收证据，不臆造历史设计时间、实施时间或测试结果
- 根据已确认的需求、接口契约及代码行为补齐具体测试用例。疑似缺陷不能直接当作正确的预期结果；预期行为无法确定时，列出问题请用户澄清，并标明相关单元尚不具备实施条件
- 必须审查当前设计的模块职责、依赖与耦合、接口与数据结构、异常和边界处理、测试覆盖，以及适用的数据库或交互设计。区分合理且可保留的设计、已有证据的缺陷和待核实风险，不为了出报告而虚构缺陷
- 补档后在聊天中向用户说明总体合理性，并逐项列出“问题 / 代码位置或调用链证据 / 影响 / 严重程度 / 建议”，提出需要用户确认的行为或调整方向。当前风险写入总文档 §6.1 或模块 §7，待确认项按总文档 §6.2、模块 §11 归位，不另增历史记录文档
- 补档不直接改业务代码，不擅自重构。存在设计缺陷时先完成真实补档和问题汇报；用户确认调整方向后，再原位更新为当前有效方案。若用户已明确授权具体设计调整，直接按该授权处理，无需重复确认

## 输出格式

### 聊天摘要

先输出一段简短摘要，包含：

- 读了哪些代码
- 推荐方案一句话总结
- 是否存在未决问题
- 交接结论：文档路径、本次 scope、本次范围是否可实施及具体阻塞；原请求包含实施且无阻塞时继续 developer，设计专用请求则结束
- 存量补档时，额外说明补齐了哪些文档、当前设计是否合理、发现哪些有证据的缺陷，以及需要用户确认的调整方向

### 完整设计文档

模块化输出，按以下顺序：

1. 总设计文档，严格使用 `assets/design-index.md`
2. 各模块设计文档（无环部分按拓扑序；存量依赖环如实标明），严格使用 `assets/design-module.md`

## 完成标准

“设计可实施交付”须满足以下条件。存量补档或澄清仍有阻塞时，可交付已核实的文档并说明阶段成果，但不能宣称设计已就绪，也不能让 developer 开始受阻范围的实施：

- 已阅读并引用相关既有代码证据；新项目已说明无既有代码，并明确设计的需求与约束依据
- 已输出总设计文档（`design-doc/index.md`）和各模块文档（`design-doc/{name}/index.md`）
- 总文档明确整体设计目标与范围、总体方案、模块归属与组织边界、依赖及协作边界、约束和公共约定；检查实际依赖完整性，不以只有模块列表或目录树替代架构说明
- 每个业务模块文档包含实际 API 契约、Mermaid 流程图、适用的数据结构定义或引用、实施计划、可直接实施的具体测试用例及验收标准；公共配置引用完整可解析；外部服务契约文档按其专用模板检查
- 模块按业务逻辑划分，不以技术分层为边界
- 模块文档间的依赖引用使用相对链接指向具体章节
- 新设计依赖图已通过循环依赖检测（无环）；存量补档已如实记录检测结果，存在环或其他阻塞时不得宣称已具备实施条件
- 涉及数据库时已包含 DB 设计
- 涉及用户交互时已包含组件化设计与组件来源说明
- 已包含基于当前项目测试框架的测试设计
- 每个模块的测试用例均已完整写入设计文档，没有把测试设计留给实施阶段补充
- 已逐项核对当前范围内需求与设计、用例或核验方法、验收项的对应关系，无遗漏需求或无依据的新增功能
- 需要的项目内集成验证已有具体用例、运行条件及验收映射；不适用时未强制添加
- 所有测试用例均有稳定编号，且已声明项目级报告路径 `tests/test-report.md`
- 业务规则、接口契约、边界处理及环境兼容约束中的适用项已明确；尚未解决的设计阻塞已回报，不以交付文档代替实施条件已满足的判断
- 已通过 `references/checklist.md` 自检
- 存量补档时，已补齐可核实的当前设计并向用户报告合理性与缺陷；未核实或阻塞项已明确列出，不能将其标记为完整可实施设计

## 禁止事项

- 不直接修改业务代码
- 不自动生成 PR / commit
- 不在没有代码证据时臆测现状
- 不做与需求无关的重构
- 不输出只有概念没有 API / 流程图 / 测试设计 / 组件拆分的空设计
- 不忽略项目现有测试框架与组件体系另起炉灶
- 不输出与当前需求无关的章节或子章节；模板中标注"按需出现"的部分，如果需求不涉及则必须整段省略，不要留空标题或占位符
- 不以技术分层（controller/service/repository）当作业务模块拆分依据
- 不跨项目设计；涉及外部服务 API 仅声明引用其文档路径
- 不将存在循环依赖的新方案作为可实施设计交付；存量补档不得隐瞒真实依赖或伪造无环结论
