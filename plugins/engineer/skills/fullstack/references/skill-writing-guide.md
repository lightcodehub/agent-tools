# 库与工具的 skill 编写指南

库 skill 是供 agent 发现并使用现有能力的轻量入口。普通库也可以有 skill，不要求必须存在复杂工作流；重点是让后续开发先复用已有能力，避免重复实现。

## 1. 创建与维护范围

- 本次产出的可复用库或工具（非一次性胶水代码）必须有对应 skill。按可独立复用的库或工具组织，不为每个函数生成独立 skill。
- 先查找对应能力已有的 skill，优先更新，不建立多个独立维护的副本。
- 本次修改已有库的接口、能力或调用约束时，同步更新其 skill 和 API 文档；相关内部库缺少 skill 时，可基于已读代码和文档补齐入口。
- 只处理当前任务相关且可维护的项目代码。第三方依赖优先使用其官方文档及已有 skill，不批量改写依赖目录或为无关库补档。

## 2. 最小内容

正文结构按实际能力组织，不强制固定标题。至少让 agent 能找到以下信息：

| 内容 | 要求 |
| --- | --- |
| 能解决的问题 | description 写明功能、使用场景和相关开发意图关键词，不能只有库名或“工具集合” |
| 能力与边界 | 说明支持什么、何时优先复用、哪些需求不适用 |
| 代码入口 | 指向真实的导出接口、模块或 CLI；已有能力明确要求优先调用 |
| API 文档 | 给出随库维护的文档链接，并要求调用前读取对应章节；详细参数、返回值和完整示例以 API 文档为准 |
| 必要约束 | 按需说明初始化、输入、依赖、错误处理和调用顺序；不为普通库编造工作流 |
| 使用与验证 | 给出一个精简示例或指向文档中的可运行示例，说明工作目录、执行方式和预期结果 |

先核对 API 文档与实际代码。有缺失或过期时更新相关文档；skill 负责发现和导航，不复制一整份 API 文档。只有会影响正确使用的关键约束才同时写进 skill。

## 3. 协议与宿主扩展

`SKILL.md` 以 YAML frontmatter 开始，随后为 Markdown 正文。例如：

```yaml
---
name: archive-tool
description: "使用项目内的归档工具创建和读取归档文件；开发归档导入、导出功能时，先查阅其能力并复用现有接口。"
---
```

示例须替换成库的真实能力，不原样复制。依据 [Agent Skills 协议](https://agentskills.io/specification)：

- name 与 skill 目录同名，1–64 字符，使用小写字母、数字和连字符，不以连字符开头或结尾，不包含连续连字符。
- description 为非空字符串，不超过 1024 字符，同时说明能力与触发场景。
- 可选通用字段为 `license`、`compatibility`、`metadata`、`allowed-tools`。metadata 为字符串到字符串的映射；compatibility 为不超过 500 字符的非空环境说明；allowed-tools 为实验性的空格分隔工具列表，实际语义取决于宿主。

`when_to_use`、`argument-hint`、`effort` 是 [Claude Code 扩展](https://code.claude.com/docs/en/skills#frontmatter-reference)。目标平台包含 Claude Code 时可保留，检查其他目标宿主是否接受；不得仅因通用校验器的白名单报错就删除。触发信息和参数说明同时放入 description 与正文，不假定其他宿主执行扩展的配置语义。严格拒绝扩展的分发入口单独适配产物，保留多平台源文件。

## 4. skill 随库分发，宿主入口负责发现

- skill 的唯一维护源必须与所属库处于同一可移动、可分发单元。默认使用 `<库根目录>/skills/<skill-name>/SKILL.md`；已有满足随库迁移要求的布局可沿用。
- 库的 API 文档、skill 及其必要资源随代码进入版本管理和发布包；检查忽略规则、打包文件清单，避免发布代码时遗漏文档或 skill。
- 项目级发现目录只作为入口，不维护另一份独立内容。用户主动执行 `/engineer:discover-skills` 时，根据目标宿主为 Codex 的 `.agents/skills/<skill-name>` 或 Claude Code 的 `.claude/skills/<skill-name>` 创建相对软链接；fullstack 不自动执行注册。
- fullstack 可直接使用宿主通过插件等方式已提供的 skill，无需为了使用它另行注册。本地注册脚本只核对文件系统入口，不读取宿主已安装插件清单，不能保证消除插件入口与源码入口之间的重复；用户按需决定扫描范围，不自动写入用户全局目录。
- 标准目录不是任意目录的全盘扫描器：skill 跟着库移动后，需要在接收项目建立发现入口；库在项目内改路径时，需要更新入口。

示例布局：

```text
project/
├── packages/my-tool/
│   ├── src/
│   ├── docs/api.md
│   └── skills/my-tool/SKILL.md
├── .agents/skills/my-tool -> ../../packages/my-tool/skills/my-tool
└── .claude/skills/my-tool -> ../../packages/my-tool/skills/my-tool
```

本地发现目录的软链接支持见 [Codex](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills) 与 [Claude Code](https://code.claude.com/docs/en/skills#choose-where-skills-load)。插件打包和上传入口的规则另外核对，不直接套用本地软链接方式。

## 5. 路径与入口维护

- 文件引用基于 skill 的真实源目录解析。例如上例中 API 文档为 `../../docs/api.md`，库根目录为 `../..`；使用软链接入口时先解析真实源目录，不能按链接所在的标准目录计算库路径。
- 不写开发机器绝对路径，不假定当前工作目录就是库目录。命令必须明确在库根目录还是消费项目目录运行；脚本按自身真实位置定位资源，或通过明确的参数接收调用项目位置。
- skill 自带的辅助脚本可放在 `scripts/`；调用库中已有脚本时直接引用，不为满足目录形式复制代码。
- 首次接入、新增库或迁移后，由用户选择合适时机执行 `/engineer:discover-skills <项目路径> <codex|claude|both>`，一次完成扫描与入口创建；不要把它放进每次实施的自动前置步骤。
- 用户执行注册 skill 时，脚本跳过正确入口，清理所选项目发现目录中的失效软链接；同名目录、普通文件或指向其他有效来源的链接保留并报告。fullstack 不自行执行清理、注册或覆盖。
- 若系统不支持软链接或无创建权限，当前任务仍可直接读取源 skill；说明自动发现尚未就绪，采用目标宿主支持的安装方式或由用户提供所需权限，不用独立副本掩盖问题。

## 6. 验证与交付

- 按协议检查通用字段，按目标宿主检查扩展；引用文件、代码入口和 API 文档都存在并与实现一致。
- 核对源 skill 的内容与引用。已有注册结果时可说明入口状态；没有注册结果时说明用户可手动注册，不运行全项目扫描来补出一个“已注册”结论。
- 在允许的环境中验证引用的最小示例或相关已有测试，记录验证范围；涉及远端或有副作用的示例按已有授权执行，未运行则说明。
- 迁移或发布时核对代码、API 文档、skill、资源的相对关系，说明需要用户更新的发现入口，不能留下写死的机器路径。
- 交付时简要列出复用或新增的能力、skill 源位置、发现入口及验证结果，不要求另建能力清单或历史记录文档。
