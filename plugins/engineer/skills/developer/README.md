# developer

`/engineer:developer` 按设计实施、修复和重构代码，编写持久测试源码，逐单元自测后交验。该角色不限于前后端全栈；实际实现依照项目技术栈。

## 职责

- 读取本次设计和必要依赖，发现缺项进入 `/designer:architect` 补全；设计有效则直接复用。
- 阅读相关库 skill 与 API 文档，优先复用既有能力，逐单元实现、编写测试、运行并修复。
- 保留自测命令、源码/配置版本、用例与结果、退出码及原始证据；按规范管理文件和资源。
- 接收 validator 的实现或测试问题，在已授权范围内修复、自测并重新交验；改变预期先返回 architect。

代码审查、独立回归与集成验证、规范报告和技术验收由 `/inspector:validator` 负责。developer 仍须自测，不能写完代码就移交。

## 使用

```text
/engineer:developer 按这份设计文档实现用户昵称更新并写测试
/engineer:developer 修复 validator 指出的错误处理问题
```

正式交验由 developer 在原授权范围内启动不继承开发对话的 validator 子代理，无需用户再次发起。用户直接在干净会话调用 validator，可当场验收。只要求实现或无法隔离时，交付已有成果并注明“未执行独立验收”；子代理未返回有效结论时说明独立验收未完成。

## 自测与交验

所有路径从消费项目根目录解析。源码固定在 `tests/{module}/unit/`、`integration/` 及实际调用的 support，数据与产物在 `build/tests/`。详细要求见 [测试管理规范](references/test-management.md)。

按[自测回执](references/self-test.md)记录每轮带时区的开始与完成时间。每轮自测先确定唯一 run-id、捕获当时源码/配置快照并配置参数实例采证，数据按模块和用例隔离。方法级结果不能替代实例证据，后续验收结果不能反填早期自测。自测摘要和原始结果放本轮 artifacts；失败、中断或未启动同样如实记录，保留 validator 尚需读取的证据并说明清理时机。

developer 不写 `tests/test-report.md`。交验只传范围、设计和版本等事实、已知失败或阻塞及证据入口；旧报告已过期时说明适用版本。子代理按设计确定授权范围内应验证的行为并执行，开发对话和自测判断不随交接传入。

交接示例：“使用 validator 验收昵称更新。设计见 `design-doc/profile/index.md` §3、§8、§10；比较基线为提交 `a4f81d2`，待验版本为当前工作树（含未提交测试）。使用 Python 3.12，测试库未启动，自测证据见 `build/tests/runs/dev-42/artifacts/`。” 若只能在原开发会话复跑，结果仅在聊天和本轮 artifacts 中提供，注明“同一上下文复核，未执行独立验收”；即使用例全绿也不覆盖规范报告或回写验收状态。

## 状态与完成

developer 更新模块 §9 的实施步骤、§8 用例的实际自测状态和实施时间。例如 5 月 6 日自测通过的用例记为 `✅ 已完成 (2026-05-06)`；5 月 8 日独立验证时仍保留 5 月 6 日，自测日期无据则注明未知。验收退回的 §9 步骤由 developer 更新。模块 §10 技术验收与头部完成由 validator 判定；自测通过可继续下一单元，但不代表整个模块通过验收。技术验收不代替产品验收或发布决定。

交验前还须按代码和执行证据同步本次范围的设计正文、README 与 API/使用说明，删除过期的现状描述。纯事实和格式修正可直接处理；改变方案、契约或风险判断交 architect，不以实际缺陷反向修改设计要求。保留范围外未完成项和明确版本的历史事实。

## 库能力与授权

产出可复用库或工具时，按 [skill 编写指南](references/skill-writing-guide.md) 同步真实 API 文档与轻量入口。发现与注册由用户主动执行 [discover-skills](../discover-skills/SKILL.md)，developer 不自动创建注册链接。

不擅自扩大范围、修改预期、提交、推送或发布。交验前按 [自检清单](references/checklist.md) 核对实现、自测、状态与文件准入。

## 产出文档要求

交付的项目文档遵守 [产出文档表达规范](references/document-style.md)：直接说明有效规则、条件和依据，语言自然、精简、准确；不带对话痕迹或工作过程叙述。Markdown 表格采用紧凑格式，不填充列宽；测试报告保留必要的结果、失败原因和重试证据。 命令、路径及标识符使用代码格式并核对解析后的字面值；本次范围的正文、实现与状态保持一致，不能只更新状态而保留过期现状。

## 设计文档读取与适用性

总文档承载概要设计与代码架构设计：§1 目标与范围、§2 总体方案、§3 代码架构、§4 项目约束、§5 公共约定、§6 风险与待确认。§5.1 定义代码规范，§5.2 定义公共测试约定；模块 §8 以相对链接引用，并提供具体路径、命令、用例、数据准备与必要例外。既有有效设计使用其对应章节。实际接口、依赖、业务规则与测试验收信息必须完整；无适用内容的 HTTP、依赖、数据结构、数据库和 UI 子节按规则省略。

模板仅提供成品字段和可删除的填写提示。实际语言、数据库及视觉参数来自项目依据，运行时失败处理与测试替身分别定义；文档不复制角色操作规约或预填检查结论。

## 公共代码规范

依据 [公共代码规范](references/coding-conventions.md)，总文档 §5.1 固定使用三列、八个规范项及规定顺序；新项目与存量补档的格式和覆盖范围一致。每行写明公共约定或有效引用、适用范围与核验方式，没有相关机制仍说明实际边界。区分采用的规则、存量成文依据与源码归纳；具体业务契约下沉模块文档。固定八行不要求增加工具、日志、捕获包装或机械注释，已有必要处理仍须落实。

总文档的新项目设计与存量补档均按架构模块、层和包组织，不列内部实现文件或函数入口。具体代码映射在模块详细设计维护；仅文件本身构成独立架构模块时可注明文件名，依赖图仍使用模块名称。配置引用、测试命令和文档链接不作为架构单元。

跨模块读写及状态变化必须有归属明确的操作契约，并与调用方依赖、测试及实施前提对应。单元验证本层可观察结果，异步下游产物由实际模块或真实集成验证；共享类型、表结构或替身成功都不能代替这些证据。

## 定向读取

依据 [定向读取规则](references/scoped-reading.md)，总设计兼作模块与依赖索引：先定位目标及公共约束，再读相关设计、契约和实现。依赖内部细节按需展开，公开契约变更时核对调用方；索引失效或出现新证据时扩大范围。读取量优化不改变实现授权、必要回归和独立审查要求。

`scripts/read_section.py` 使用 Python 3 标准库，提供 Markdown 标题列表与精确章节读取；只输出所选章节，不修改项目文件、不缓存正文。用它承接总设计中的契约链接，避免宽行号读取带入相邻契约。

## 模块文档组织

按 [模块设计规则](references/module-design.md)，模块文档定义内部设计与功能详细设计。关键行为及协作明确，普通实现细节留给 developer；§2 集中内部职责与真正共享的规则，§3 按功能说明完整行为与实际接口，§8/§9/§10 引用其设计并分别承担测试、实施和验收。简单功能可以短段落表达，不强制六张表或流程图；旧有效设计按对应内容使用。
