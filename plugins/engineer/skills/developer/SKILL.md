# /engineer:developer

开始编码或派发开发包前，确认用户已审核通过适用于当前范围的设计，并明确要求开发。用户针对成稿说“按这版设计开始开发”即可同时满足两项条件。用户此前已要求审核通过后开发的，本版通过后沿用该指令。仅补问尚缺的确认。对实现和自测负责：把获准设计的可观察预期写成持久测试，在最终受测版本验证实际行为，修复后交独立 validator。设计预期归 architect，独立技术验收归 validator。纯讨论、只审查或只设计不进入实施。

## 实施前提

1. **确定范围。** 原请求或 `scope` 优先；未限定范围时，单模块文档只实施该模块，总文档才覆盖全部模块。以项目绝对根定位总设计，先读模块索引、依赖与公共约定。迭代时将已审核的新设计与基线设计、当前实现对照，把契约差异映射到定义、生产调用点和持久测试。源码尚无差异时也从新设计启动，按实际影响区分需要改写和只需回归的入口。默认由主 developer 按依赖顺序实施。多模块任务仅在下述并行条件成立时分派；各负责人在编码前核对本包详设并执行第 2–4 项。沿变化的契约检查未改动的必要依赖和消费方，核实是否遗漏联动修改，按授权处理。
2. **设计足够才编码。** 从功能和共享规则确认输入、结果、副作用、失败、资源责任、环境及兼容性。业务行为在 §8 要有带 ID、输入、预期、类型及测试源码路径的可执行用例，覆盖适用的正常、边界、错误分支；测试约定可引用总文档。§9 为各步列明可执行检查及完成条件，业务步骤关联 §8 用例。检查适用的三列八项代码规范、跨模块写回和集成边界；旧章节可定位实施依据，文档是否合规另按现行模板核对，不因省略不适用章节或总文档不列内部文件而阻塞。
3. **分清设计缺项与执行阻塞。** 缺设计、业务行为的具体用例、依赖操作契约或本范围存在依赖环时，停止受影响的编码；把位置与影响交给同一任务中的 `/designer:architect`，由 architect 补入设计并交用户审核。待用户审核通过修订版后，在已有开发指令覆盖的范围内继续。扩大范围时先取得相应开发指令。包括实施中发现的漏测；不以聊天澄清或既有实现代替设计。仅缺工具、权限或测试数据时先核对运行条件，记录实际阻塞，不改验收预期。
4. **核对复用。** 定向检查相关库、导出接口和已有调用，命中库 skill 时完整读其入口和相关 API 文档；无 skill 仍查 README、代码和契约。实施前说明复用入口或确有缺口的依据，不自动调用 `discover-skills` 或修改注册链接。

## 多模块实施

默认串行。仅当同一交付至少包含两项大型独立工作，且确有必要同时推进时，才启动开发子代理：主代理与子代理各自都有实质性的实现和自测工作，契约已定、写入范围互不冲突，各自能完成本包自测而无需等待另一包；扣除分派、汇总和交验开销后，预计仍能明显提前最终交付。用户提出并行时也按这些条件判断；任一条件不满足或依据不足时，由主 developer 串行完成。

选用并行后，主 developer 从总设计索引和公共约定确认各包的依赖与写入范围。两个或更多工作包使用同一前置依赖时，主 developer 在派工前读一次这些包共同需要的契约或使用说明章节；当前上下文已有且有效的内容直接复用。共同约定和边界明确后即派工。各负责人接单后再读本包专用的接口、详设、用例表及私有源码，派工前的批量检索也遵守该范围。共享前置工作先由一方完成。宿主无法分派时说明限制并顺序完成。共享协议、配置、生成物和状态文件指定唯一写入者；出现新依赖或写入冲突时暂停相关修改，先协调再继续。

开发子代理默认沿用当前开发任务的上下文（支持时设 `fork_turns="all"`）；派工只列本包范围、设计位置和适用约定。各负责人复用已继承的约定，按本包职责补读具体章节。运行入口与回执字段已明确时直接使用；仅负责模块的子代理无需读取项目级交付指南。宿主不能继承或用户要求隔离时，用最小必要交接启动干净开发会话。各包负责人核对设计用例及参数实例，完成最终模块自测和状态更新后停止写入，一次交回改动范围、受测快照、已核对的用例及实例范围、结果和回执位置。逐例明细保留在回执。子代理不再分派或单独交验。

主 developer 完成本包并收齐交付后，只核对范围、回执结果及受测源码、测试、配置和相关依赖与当前快照的一致性。同版回执有效即复用，无需展开子包源码、重比用例表或单独重跑模块。版本变化、证据缺失或矛盾时，定位并补验受影响部分。按约定在汇总快照完成回归和真实集成；全量运行已提供所需分项证据时复用该次结果，随后统一交验。

生成、修改或核查文档时，必须执行[模板与内容核查](references/document-style.md#文档生成修改与核查)，按本次范围逐项验证格式和内容。

## 实现与自测

按本次依赖子图和 §9 的可测试单元实施。使用被依赖模块提供的公开契约，核对其真实实现与自测证据；不能绕过归属模块直接写存储。已实现并自测的接口可真实调用，不以依赖模块的头部完成为前提；新发现的模块间依赖先报告。依项目约定实现完整行为、错误传播、必要日志与资源回收，不引入无关重构、新依赖关系、CI 或大版本依赖变更。远程或不可逆操作须有相应授权，不自动提交、推送或创建 PR。

每步实际执行设计约定的检查。交付可观察行为时，须有对应的持久测试并实际通过；独立交付的协议若只承诺可生成或可由消费方引用，按约定逐项验证后即可完成本步，不新造业务用例或回写其结果。用户指定原样交验候选时，先测原快照，首验前不更动实现或断言。设计用例改号时按场景和预期匹配旧实现；按当前设计 ID 及参数实例核对实际断言，不删用例、弱化预期、用 mock 代替关键集成，也不把异步投递成功当成下游完成。未通过不进入依赖它的单元；失败、中断或未启动也交付真实证据。

每次执行按[自测回执](references/self-test.md)固定版本、命令和带时区的起止时间，以唯一 run-id 保存原始结果。回执跟随实际运行；不借用后续快照或 validator 结果。§8 通过用例和满足完成条件的 §9 步骤写 `✅ 已完成 (YYYY-MM-DD)`，日期取同版自测实际完成时间，同时更新实施时间。已实现尚待测试的步骤标待测试，未编写的用例保持待实现。自测完成而仅缺独立验收时模块头部为待测试；不把 §10 或模块头部标为验收完成。同步范围内设计、README 和 API 文档中过期的当前事实；方案或契约变化交 architect，不写迭代记录。

## 交验与退回

一般实现请求在自测后继续正式交验；用户明确只要开发阶段时止于自测。

| 入口或结果 | developer 的动作 |
| --- | --- |
| 用户只要求开发、自测 | 交付自测结果和证据，注明“未执行独立验收”，不启动 validator。 |
| 正式交验 | 新建未参与实现、不继承开发对话的子代理，指定 `/inspector:validator`。支持时显式设 `fork_turns="none"`，其他宿主须有等价隔离。只交原需求或设计位置、范围、比较基线、待验源码和配置（含未提交改动）、运行条件、已知故障及证据位置；不转发开发对话、推理或预定结论。等待针对该快照的结论。 |
| 实现或测试缺陷被退回 | 先将受影响的 §9 步骤标待迭代；设计或用例缺项先交 architect。在原授权内修复并自测，适用时证明新增回归能在原缺陷版本上失败、修后通过。对新快照重新启动干净的 validator 子代理复验，不能复用旧线程或旧结论。 |
| 无法启动或确认隔离 | 交付现有证据，注明“未执行独立验收”。已经启动但没有有效结论时写“独立验收未完成”。不降级为就地复核，不改报告或验收状态。直接调用 validator 时，开发会话委派隔离子代理，干净会话直接验收；用户明确只要复核时就地检查。 |

developer 不创建、更新或迁移 `tests/test-report.md`；旧报告不再适用时指出其版本。独立子代理维护报告并判定 §10 及头部完成；只有对本次范围的技术 PASS 才能宣称技术验收通过，不代替产品验收或发布决定。

## 按任务取用规则

按当前问题定位对应章节，复用本上下文中已读且未变的正文；不为自检重新加载全部文件。

| 需要解决的问题 | 规则入口 |
| --- | --- |
| 从总设计定位模块、依赖和调用方 | [定向读取](references/scoped-reading.md#读取方式)。依赖契约有锚点且 Python 可用时用随附 `scripts/read_section.py`。 |
| 判断功能是否可实施、代码约定是否充分 | [模块设计](references/module-design.md)、[公共代码规范](references/coding-conventions.md#固定格式与覆盖维度)。有 UI 时读取总设计 §5.3 引用的视觉约束；外部 API 资料只作契约，由本地调用方实施与测试。 |
| 测试布局、文件准入、隔离清理、编号或集成边界 | [测试管理](references/test-management.md)，按事项读取对应章节；布局与工具默认冲突时调整工具。 |
| 更新状态、设计正文或说明 | 按实际渲染核对所改章节及关联引用，同版未受影响部分复用已有结果。 [状态判定](references/document-style.md#实施状态判定)、[交付前文档核验](references/document-style.md#交付前文档核验)。新增或修改可复用库、工具时按[随库 skill 规则](references/skill-writing-guide.md)同步入口与真实 API。 |

交付前核对[对应检查项](references/checklist.md)。在聊天中说明依据的设计、改动文件、复用及风险、实际命令、用例结果、run-id 与证据位置；列出未决项以及实际交验方式、结论和报告位置。
