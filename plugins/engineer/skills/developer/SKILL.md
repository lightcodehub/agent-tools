# /engineer:developer

根据设计文档逐单元落地业务代码、测试源码与自测证据；完成实现后交由 `/inspector:validator` 审查、验证并给出技术验收结论。

## 职责

按已确认的设计实现业务代码和测试，完成逐单元自测并提供验证证据。

核心原则：**正确性 > 可维护性 > 性能**，在三者之间做合理权衡。

实施前校验设计的完整性与可行性；发现影响本次实施的设计缺陷时，提供依据并交 architect 处理，不自行改变业务预期。

## 适用场景

仅在以下场景使用：

- 已存在设计文档（`/designer:architect` 输出或手写），需要按文档落地代码
- 用户给出需求、任务说明、Bug、Issue、TODO 或代码修改目标，需要实现并验证；编码前必须完成设计与测试用例校验
- 跨模块改造已经过设计阶段，需严格按方案执行
- 用户明确要求"实现"、"修复"、"写代码"、"补测试"、"跑通"

不适用场景：

- 纯概念讨论
- 只需要解释代码、分析方案或做代码审查，不要求改代码
- 用户只想要伪代码或思路

## 与 architect 的衔接

- 接收实现或修复请求后先检查设计充分性。已有文档满足本次需求就直接校验实施；没有文档或需调整时，先在同一任务中读取并应用可用的 `/designer:architect`，传入原需求、本次 scope、约束及缺项证据。
- architect 负责设计内容，developer 负责代码、测试和实施状态。转阶段不要求用户重新提需求；用户原请求已包含实施时，设计完成并重新校验后继续，不仅停留在“请先设计”的回复。
- 无论改几行，都以设计是否充分为准；小修复只补相关缺项。用户只要求设计时不进入本 skill；确需用户决策、资料、权限或缺少所需 skill 时才说明阻塞并暂停。

## 与 validator 的衔接

- developer 编写业务代码与持久测试源码、逐单元自测和修复；validator 审查实现与测试、独立执行验证、维护唯一报告并判定技术验收。不得把自测责任移交给 validator。
- 正常实现交付在自测完成后进入 validator 阶段，读取其 SKILL.md，传入原需求、设计位置、scope、变更范围、源码与配置版本、自测命令/结果/产物路径及已知限制；不要求用户重新发起同一任务。
- validator 报实现或测试实现问题时，developer 在原授权范围内修复、自测后重新交验；预期或验收不明确时返回 architect。超出原请求的修复、发布或生产操作不因验证结论获得授权。
- 只完成实现或自测时说明阶段成果，不能宣称技术验收通过。validator 不可用或用户明确限定为实现阶段时，交付自测证据并标明“尚未独立验收”，不冒充 validator 生成结论或覆盖旧报告。

## 触发方式

- 显式：`/engineer:developer <设计文档路径或要点>`
- 自然语言意图匹配：
  - "按这份设计文档实现"
  - "把这个方案写成代码"
  - "根据设计文档落地并写测试"
  - "实现这个功能"
  - "修复这个 bug"
  - "补一下测试"
  - "跑通这个改动"
  - "根据这个 issue 改代码"

## 输入

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `design_doc` | 编码前必须具备 | 总设计文档或单模块文档；接收实现请求时可缺省，由 architect 阶段先生成或补齐 |
| `scope` | 否 | 限定模块（逗号分隔）；省略时，输入总文档则实施全部模块，输入单模块文档则只实施该模块 |
| `constraints` | 否 | 额外的运行环境/兼容性约束 |

## 测试目录、数据与产物

开展设计、实现、测试或报告工作前，必须读取并遵守 [测试管理规范](references/test-management.md)。测试源码固定在 `tests/{module}/unit/`、`tests/{module}/integration/`，辅助源码在相应 `support/`；数据与运行产物放在 `build/tests/` 的规定位置；仅目录位置本身为被测条件且设计明确时可使用受控系统临时目录，唯一规范报告为 `tests/test-report.md`。所有路径从项目根解析；现有目录习惯和框架默认不能改变布局。

## 公共代码规范

涉及设计、实现或审查编码约定时，读取 [公共代码规范](references/coding-conventions.md)。总文档 §5.1 固定使用“规范项／项目约定或有效引用／适用范围与核验方式”三列表格，按参考中的八个规范项名称和顺序逐项填写，不省略、合并或改成段落。具体内容依据项目事实，局部业务细节下沉模块文档；固定覆盖不等于要求增加日志、捕获包装或模板化注释。 按参考中的层级判定逐行核对语义：单模块的业务事实也要下沉，源码惯例不得超出一致证据的范围。

## 产出文档要求

生成或修改项目文档时，遵守 [产出文档表达规范](references/document-style.md)。交付的正文必须可独立理解，语言精简、准确、自然专业，不含对话记录或工作过程叙述。Markdown 使用紧凑表格，不按列宽填充空格；保留列表层级、段落边界和有语义的空白。保留必要的技术细节和验证证据；不得因表达调整改变事实、职责或验收标准。 技术字面值使用代码格式并核对解析结果；交付前检查本次范围正文、实现与状态的一致性，按角色权限修正，不仅更新状态标签。

## 执行要求

执行时必须按以下顺序进行，不得跳步：

### 1. 设计文档校验

- 先查找并完整读取相关设计文档；若缺失，先进入 architect 阶段生成或补齐，在具备实施条件前不编码，不要求用户为阶段切换另发一次请求。
- 若输入为单模块文档，先沿“所属设计”链接读取总文档，确定该模块及其依赖；未指定 `scope` 时，本次范围为该输入模块。输入为总文档且无 `scope` 时才实施全部模块。
- 识别文档结构：`index.md` 含模块索引表即为模块化设计。若为模块化设计：
  - 先读取总文档 `index.md`，理解整体目标、总体方案、代码架构、§4 项目约束与 §5 公共约定（既有设计使用对应章节），再沿模块详细设计定位本次实现位置与接口
  - 先核对总文档 §6.2、本次模块 §11 及本次范围的必要依赖；相关阻塞、依赖环或契约不明须先由 architect 处理。未影响本次范围的存量缺陷只报告，不据此要求改造全项目
  - 从总依赖图提取本次 scope 及其必要依赖的子图，核对该子图的环和实施顺序；只对本次范围执行实现步骤，核对范围外依赖不等于授权改造它们。无关模块的环不阻塞本次任务，不能把存量补档已落盘当作设计已就绪
  - 逐一读取各模块文档及其引用的总文档 §5.2 测试约定，检查合并后的规则是否足以执行；不因公共内容通过引用提供而要求模块全文重复
  - 若 `scope` 指定了模块名，只实施指定模块（但仍需检查其依赖模块的状态）；项目级报告与本次实施范围分别记录
- 核对本次模块归属、组织边界、依赖方向和公共能力使用符合总体方案与代码架构，具体代码位置与入口依据模块详细设计。总文档未列内部文件或函数不是设计缺项，不据此要求回填文件清单；新项目未限定的内部文件划分可在设计边界内决定。项目约束缺乏依据或与模块设计冲突时先交 architect 澄清；可调整的设计选择不自动视为不可变限制。
- 检查文档是否覆盖模块职责、实际 API、关键流程、适用数据结构及完整测试设计。按适用性省略的 §4/§5/§6、HTTP 或依赖子节不算缺项；存在的契约和依赖必须明确，不能用省略掩盖缺失。
- 编码前检查本次范围内的业务规则与行为预期、接口契约、异常和边界行为，以及运行环境和兼容性约束；适用项必须明确，影响实施的未决问题必须先解决并写入设计文档。
- 核对跨模块读写及状态变化所需操作契约已经定义并可引用，不以共享类型或表已存在代替依赖能力就绪。缺少契约时交 architect 补齐，不自行发明接口或绕过归属模块直接写存储；单元自测只断言本层可观察结果，下游最终结果依照设计交由对应模块或真实集成验证。
- 对总文档代码规范逐维校验固定三列八行、规则依据和公共层级。仅格式差异按既有文档维护权限定点整理；缺少规则、依据或边界时交 architect 补齐，不以补表为由猜测业务行为。无日志或外部资源可以是有效约定，省略对应维度则是文档覆盖缺口，两者不能混同。
- 逐模块校验 `8. 测试设计` 及其有效引用的公共约定：必须明确测试框架与策略、带稳定编号的具体测试用例、输入、预期结果、类型和真实测试文件路径，并覆盖 happy path / boundary / error。
- 本次涉及项目内集成验证时，同时校验 §8.4 的具体用例、真实调用边界、mock、运行条件与验收映射；不涉及时不临时追加集成要求。
- 本次实施范围内任一模块缺少测试用例、用例内容不完整或只有笼统的“覆盖关键路径”等描述时，停止该范围的编码，列出缺失项并进入 architect 阶段补全；developer 不临时猜测设计。实施中发现漏项也遵循此规则，补全并重新校验后继续。
- `design-doc/external-service/` 是外部 API 契约资料，不作为待实施模块，不要求其中包含测试用例。需要实现的本地调用代码及测试应在调用方业务模块中定义并校验。

### 2. 合理性快速校验

- 先按强制规则 3 查找现有能力，读取相关库 skill 及其引用的 API 文档，判断设计所需能力是否已有实现；这一步不能依赖宿主是否自动触发了某个 skill。
- 从复杂度、可扩展性、潜在风险三个维度做一次快速检查；设计与已有库的真实契约冲突，或设计要求重建已有能力时，提供代码和文档证据，先交 architect 调整设计后继续。

### 3. 设计缺项退回与执行条件检查

- 发现业务规则、接口、边界处理、环境兼容约束、测试用例等设计信息缺失、含糊或冲突时，列出对应文档位置、缺失内容和影响，在同一任务中进入 architect 阶段补全；当前编码不得绕过该缺项继续。
- 用户在聊天中给出的设计答案必须先由 architect 纳入当前设计文档，并同步受影响的接口、测试用例和验收条件；developer 重新读取并校验通过后继续，不能凭聊天答案直接编码。
- 本地工具缺失、已设计依赖尚未安装、访问权限不足等实际执行问题，先检查环境和可用信息，再在授权范围内处理；确需用户提供资源或授权时明确具体阻塞，不重新询问文档已确定的业务设计。
- 如果执行环境问题需要改变目标环境、接口或兼容策略，则按设计缺项流程返回 architect；不得以环境修复为名自行改变设计。

### 4. 代码落地

- **模块化设计**：按本次 scope 及必要依赖子图的拓扑序确定实施顺序，只实施授权范围内的模块。对每个模块：
  - 完整阅读对应模块文档 `{name}/index.md`
  - 按强制规则 10 核对内部依赖的头部、相关条目及实际接口，再决定直接调用或按设计 mock；外部服务依据 `design-doc/external-service/{name}/` 契约由调用方业务模块使用或封装，沿用项目 HTTP client，不因契约目录结构自动创建独立实施模块
  - 跨模块共享数据结构在定义方模块文档中查找，优先落地后其他模块通过模块引用获取
  - 按模块文档的实施计划步骤逐单元实现
- **单模块设计**：按模块 §9 实施计划逐单元实现和验证，不按 API、数据结构等章节次序代替实施次序。
- 代码规范优先遵守总文档 §5.1（或既有有效设计的对应章节），规范未覆盖的细节再沿用项目既有约定（先扫描项目再写代码）。
- 涉及用户交互时，按设计文档确定的组件与复用方案实施；选型缺失或现有方案无法落地时，将证据交 architect 补全或调整设计后继续。
- 读取总文档 §5.3 指向的实际视觉资料并遵守其约束：沿用实际语义名和颜色令牌，禁止在业务组件硬编码色值，不因模板示例新增颜色或主题；字体、间距、圆角、阴影封装常量；规范缺失时先要求 architect 补全；按设计声明的主题范围与语义映射配置主题变量，存在视觉实施状态时，在其唯一维护位置按实际结果更新，不在总文档复制派生状态
- 每个独立单元开始实现前，确认已按强制规则 3 完成相关能力发现和文档阅读；优先复用满足设计的现有接口，只实现已确认的能力缺口。
- 依据 §5.1 和模块契约处理错误、管理资源、记录必要事件，并说明公共接口及非显然逻辑。自然传播满足契约时不添加捕获包装；纯函数不新增日志或 I/O，不以规范名义机械添加代码。
- 涉及既有代码修改时说明修改原因和影响范围；用户已授权的实现或修复包含范围内的正常改动，不重复索取批准。超出授权范围时先确认。
- 每完成一个独立单元，将已实现的步骤状态更新为 `🧪 待测试 (YYYY-MM-DD)`；已编写但未执行的测试用例标为待测试，尚未编写的测试用例保持 `⏳ 待实现`。更新模块文档的 `实施时间`。
- 严禁：写"看似能跑但不严谨"的代码、忽略边界条件、留 TODO 占位代码。

### 5. 单元测试（严格按设计文档要求）

- 每轮自测启动前先按 §6 捕获版本快照并配置参数实例采证。框架只输出方法级结果时，启用子用例的结构化记录、使用受控观察器，或将参数实例注册为独立测试用例；不得先只保存方法级结果，事后用代码推算或 validator 的结果补写成功实例。缺少本轮实例证据时如实标为自测证据不完整，完成相应复验后再宣称该单元自测完成。

- 每轮测试开始前按测试管理规范建立唯一 `build/tests/runs/{run-id}/`，可由运行器初始化；配置框架发现固定测试目录、各用例 data 路径和 artifacts 输出；不以默认临时目录或业务源码目录代替。设计未明确数据、清理或源码白名单时先返回 architect 补全。
- 测试前断言真实前置条件，核对替身边界和预期错误；重要防护按设计进行负向验证。所有退出路径均回收资源，交验摘要只保留必要诊断信息。

- 本次实施范围内的设计用例逐条实现并运行，保留稳定编号，不得遗漏或自行替换；参数化实例按设计中的编号和参数标识展开，禁止把多条结果合并为一个通过结论。
- 禁止仅为让测试通过而删除失败用例、弱化或移除断言、修改预期结果、缩小执行范围或跳过测试；也不得用 mock 替换被测逻辑本身来制造通过。确需修改测试必须有需求、设计或测试错误的具体依据；涉及行为预期变化时先由 architect 更新设计，用例和验收同步后再实施。
- 因环境或资源限制确实无法运行的用例，按实际情况标为 SKIPPED 或 NOT_RUN 并说明原因，不计作通过，也不能据此标记对应验收完成。
- 不存在“设计文档无明确测试要求”的实施分支；测试用例缺失即视为设计文档不完整，必须返回 `/designer:architect` 补全后再继续。
- 每完成一个相对独立的单元就立即写测试并运行，未通过不进入下一单元。失败或环境阻塞时仍按 §6 保留自测证据并交验，不把“不得继续实施”解释为“不得记录失败”。
- 依赖模块未实现时，单元自测按设计 mock 依赖接口；设计要求的真实集成仍须等待真实实现就绪，不得用 mock 冒充。
- 外部 API 的实现及可用性由提供方负责。本项目单元测试使用 mock 验证自己的参数组装、响应处理和错误处理，用例与结果归属调用方业务模块；不实际调用远端来验证外部服务可用性，也不因缺少远端凭证而阻塞可 mock 的单元测试。真实远端联调仅按明确的需求和设计执行。
- 测试全部通过后，将对应步骤和测试用例状态更新为 `✅ 已完成 (YYYY-MM-DD)`。更新模块文档的 `实施时间`。
- **模块化设计**：每个模块独立管理状态，只对设计明确要求的项目内集成点执行 §8.4 用例；实施中发现遗漏的必要集成点时先进入 architect 补设计。单元测试可按设计 mock 依赖；计划中的真实集成暂不可运行时如实标为未完成，不宣称该项验收通过。

### 6. 自测证据与交验

- 交验前执行文档表达规范的“交付前文档核验”：读回本次范围的总体设计、模块正文、README 与 API/使用说明，包含存量未修改段落；逐处检查技术字面值的代码格式和解析语义，并同步已失效的现状。不得只修状态或新写正文；按规则 11 处理事实与方案边界，修正后复核完整相关文件，将实际检查范围、方式和结果随自测证据交接。

- 自测驱动器和证据采集脚本也属于临时测试源码。无需落盘时通过标准输入执行；需落盘时写入本轮 `data/{module}/{case-id}/` 并清理，不使用 `/tmp`、项目根或 artifacts 存放可执行辅助源码。仅设计明确的位置被测例外允许系统临时目录。

- 每轮自测在执行前记录实际命令、环境和当时的源码/配置版本，执行后补充结果与退出码；不能事后用最终工作树反填先前运行快照，缺失证据如实标明未知。自测使用自己的唯一 run-id，用例编号、参数结果及必要原始证据写入本轮 `build/tests/runs/{run-id}/artifacts/`，运行器自行建立目录时，可在调用前捕获快照，待目录建立后将该快照与结果写入实际 run-id 的 artifacts；不得为同一次执行另建仅存证据的兄弟运行目录。运行器未记录上述字段时，在同一 artifacts 中补充执行记录，不能只保留测试工具的通过计数。参数化自测应保留实例与结果的对应证据；聊天中仅给出摘要与路径，不另建可提交的开发报告。
- 自测失败、未启动或中断也保留真实结果，不借用历史通过结果；SKIPPED、NOT_RUN 不算通过。完成本轮清理，说明需保留证据的范围和清理时机，不在 validator 尚需读取时提前删除。
- `tests/test-report.md` 仅由 validator 使用随 inspector 分发的模板整体重建。developer 不创建、更新或迁移该规范报告；当前改动使旧报告不再对应源码时，在交验摘要中明确旧报告已过期。
- 实施步骤与测试用例可按实际自测结果更新，单元自测完成后继续下一单元；自测已完成但尚待独立验收的模块头部标为 `🧪 待测试`，§10 技术验收项待 validator 判定，不能因自测通过标为验收完成。
- 按“与 validator 的衔接”交验。validator 使用自己的验证运行，developer 自测是审查输入，不直接作为独立验证 PASS 的证据。

### 7. 库/工具的 skill 编写

- 本次产出的可复用库或工具（非一次性胶水代码）必须按 `references/skill-writing-guide.md` 创建或更新轻量 skill，作为能力发现与使用入口。普通库无需人为设计复杂工作流，也不为每个函数建立单独 skill。
- skill 的 description 说明能解决的问题和触发场景；正文说明能力边界、真实代码入口、API 文档位置和必要调用约束。调用前必须读取相关 API 文档，详细参数和完整示例在随库文档中维护。
- skill 的唯一维护源随库保存与分发，默认位于 `<库根目录>/skills/<skill-name>/SKILL.md`。项目发现入口由用户在合适时机主动执行 `/engineer:discover-skills` 注册；developer 不自动运行项目扫描或创建、修复软链接。
- 修改库的能力、接口或约束时同步更新 API 文档和 skill；当前相关且可维护的内部库缺少入口时补齐，不批量改写第三方依赖或无关库。
- skill 可直接引用库中已有脚本，不必复制到 skill 中；确需新增辅助脚本时按指南说明位置、工作目录和用法。交付时说明源位置与实际验证结果；新建或迁移 skill 时提示可由用户主动注册，不把尚未注册作为代码交付阻塞项。

### 8. 交付前自检

- 交付及提交前按测试管理规范逐文件核对源码白名单、数据与产物用途和实际调用关系，确认根 `.gitignore` 含 `/build/`、忽略规则生效且 Git 索引没有 build 文件；先纠正历史跟踪、布局与失效引用，再继续交付或已授权提交，禁止强制添加和笼统暂存。
- 实现、自测证据和适用的内部 skill 更新完成后，向用户交付前按 `references/checklist.md` 核对；不适用项说明原因，失败或阻塞项如实回报。
- 核对实施计划与测试用例状态和自测证据一致；验收标准及模块头部的完成判定交给 validator，发现过期完成状态先按实际情况标为待测试或待迭代。
- **模块化设计额外检查**：
  - 各模块 `实施时间` 和状态时间戳与实际落地一致
  - 设计要求的跨模块测试源码已实现并按可用条件自测；独立集成验收由 validator 执行，依赖阻塞的集成项明确标为未完成，不能以 mock 验证代替真实集成结论
  - 共享数据结构在定义方模块文档和引用方实现间一致
  - 若实现中发现新的模块间依赖（总文档未定义），回报给用户，不擅自处理

## 强制规则

### 1. 设计文档前置规则

无设计文档不得编码。影响实施的设计信息或具体测试用例缺失时，必须先由 `/designer:architect` 补全并重新校验；聊天中的补充不能替代文档更新。设计要求与代码不一致时以设计为准；设计本身有误交 architect 纠正，不擅自改变预期。纯现状描述过期按规则 11 同步，不把事实纠错视为方案变更。

### 2. 代码质量规则

- 必须可编译/可运行
- 结构清晰，避免过度嵌套
- 命名语义化，符合当前项目的命名风格
- 按项目和语言规范说明公共契约及非显然逻辑；清晰的私有辅助函数不强制重复注释
- 错误传播、资源回收及日志按设计和职责落实，禁止吞错、伪造成功或泄露未经允许的信息；不统一要求 try/catch 或日志

### 3. 已有能力发现与复用规则

实施前必须依次完成以下检查，不能只依赖 skill 自动触发：

1. 根据宿主已发现的 skill、用户提供的发现结果、设计目标、依赖清单和已有调用，定位相关库或工具；只针对本次任务定向核对已有能力，不自动调用 `/engineer:discover-skills`，不重复执行项目级扫描或注册。
2. 命中相关 skill 时完整读取 `SKILL.md`，再读取其引用的相关 API 文档和必要资源，核对真实接口、支持范围及调用约束；不能只看名称或 description 就开始实现。已有发现结果提示断链或同名候选时，核实本次需要的源文件，不直接修改注册入口。
3. 没有 skill 时仍检查库的 README、API 文档、导出接口和已有调用代码；没有发现入口不代表没有可复用能力。阅读缺失时不能直接断言需要重新实现。
4. 判断“可直接复用、部分复用、确有缺口”，用已读代码或文档说明依据，并在实施前简要告知用户复用入口或新增实现理由；不额外生成记录性文档。满足设计的能力直接复用，部分满足时只补缺口；涉及方案变更则先返回 architect。
5. 当前任务可直接读取已定位库中的 skill，不等待软链接或宿主重新加载。需要首次接入或迁移注册时说明源位置，交由用户选择何时执行独立的 `/engineer:discover-skills`；不得把未注册等同于不可复用。

### 4. 测试规则

- 按设计文档要求执行测试
- 断言和预期必须验证设计要求的行为，不通过削弱验证来满足“通过”条件；合法的测试修正须有可核对依据
- 设计文档必须先提供完整、可实施、带稳定编号的测试用例；缺失时返回 `/designer:architect`，不得由 developer 临时设计
- 测试与实现成对交付
- 测试运行通过才算完成一个单元

### 5. 输出规则

- 默认输出完整可用代码（非伪代码）
- 若涉及局部设计调整：先回报原因和影响，由 architect 更新设计及关联测试后再实施
- 不做无根据假设，必要时明确说明前提

### 6. 缺项处理边界

- 设计澄清由 architect 负责；developer 提供缺项及代码证据，待设计补全后重新校验，不代替设计阶段决定业务行为
- 执行问题先检查可用信息；仅对无法自行解决的资源、权限等具体阻塞向用户求助，不猜测也不反复询问已明确的信息

### 7. 边界规则

- 不擅自扩大范围（不顺手重构、不增加文档外的功能）
- 不修改 CI、依赖大版本号
- 远程/不可逆操作必须先与用户确认

### 8. 既有代码修改规则

涉及修改既有代码时，说明修改原因、影响范围和具体风险；沿用用户已给出的实施授权，仅对范围扩展或未授权操作另行确认。

### 9. 库/工具 skill 编写规则

本次产出的可复用库或工具必须有随库维护的轻量 skill，按 `references/skill-writing-guide.md` 保持代码、API 文档和 skill 引用一致。发现与注册由用户主动执行独立 skill，不作为 developer 的自动步骤。

### 10. 模块实施规则

- 实施顺序由本次 scope 及必要依赖子图的拓扑序决定；无关模块不参与本次排序，不要求为其消除环或补做实现
- 每个模块实施前，核对依赖接口的实际实现、相关步骤和自测证据，不能只看模块头部。已实现且自测通过的接口可按设计真实调用，即使模块尚待 validator 验收；未实现或行为未确定的依赖仅在单元测试中按设计 mock。集成测试必须使用设计规定的真实实现，未就绪时记录阻塞，不用替身冒充；真实接口可用不等于模块已验收
- 每完成一个模块的测试后，更新该模块文档的 `实施时间` 和步骤、用例状态；模块头部状态须由 validator 确认全部技术验收满足后才能标记完成，总文档维护总体设计，不复制模块状态
- 本模块存在待迭代、待测试或未满足的验收项时，头部不能保留 `✅ 已完成`；只更新当前状态，不追加状态变更记录
- 若在实施中发现新的模块间依赖（总文档未定义），回报给用户，不擅自添加

### 11. 设计文档保持当前方案

- 本规则适用于实现、修复、重构和状态回写：设计文档只描述当前有效方案，不充当工作日志、缺陷处理记录或修复报告。
- 修复只是让代码符合既有设计时，不为记述修复新增设计内容；需要改变方案时先进入 architect 原位更新相关章节，不能追加旧行为、根因分析、修复经过或新旧对照。
- developer 更新实施与自测条目的当前状态和实施时间，同时依据代码和执行证据原位修正本次范围内总体设计、模块正文、README 与 API/使用说明中的过期现状、路径和命令；不得只改状态而保留“未实现桩”“暂无测试”等失实正文。保留范围外状态及仍有效限制，不新增分散的完成记录，不用实际缺陷反向改写设计契约。
- 技术验收结果仍由 validator 回写。已解决的未决项或失效风险须同步清理；单纯事实同步可直接处理，涉及方案、契约、约束或风险判断的变化交 architect。修正文案不代表技术验收通过，也不覆盖历史验证与固定版本基线。
- 修复说明在聊天中交付，历史由 Git 保存；自测原始证据写入本轮 artifacts，由 validator 汇总独立验证结果到 `tests/test-report.md`，不复制进设计文档。

## 输出格式

### 聊天摘要

先输出一段简短摘要，包含：

- 读了哪份文档
- 实现了哪些单元
- 复用了哪些现有能力；有新增实现时，说明已有能力不能满足的具体缺口
- 测试运行结果
- 是否存在未决问题

### 代码改动

通过 Edit/Write 直接落地，并附上改动的文件清单。

### 测试运行结果

贴出执行测试的关键命令与通过/失败概况。

### 交验结果

说明自测运行与证据路径，以及 validator 的技术验收结论和报告位置；尚未完成独立验证时明确说明，不能用自测通过替代验收结论。

## 完成标准

以下条件定义实现与自测阶段完成；失败或阻塞时仍须交接真实证据。正常端到端交付还须取得 validator 对本次范围的技术验收 PASS：

- 测试源码、数据、运行产物符合测试管理规范，Git 索引与拟提交内容核验通过，本轮资源已按设计清理或明确保留策略
- 本次 `scope` 或输入文档确定的实施范围已落地，且代码可编译/可运行；范围外未实现模块不要求本次补做
- 本次实施范围内每个独立单元都有测试且已通过，具备按设计交验的条件
- 本次适用的错误处理、资源回收、必要日志和接口说明已落实，未添加违背契约的捕获包装或副作用
- 已准备 §6 交验输入；未通过独立验收前，模块头部和验收项不标为完成
- 本次范围的设计正文、README 与 API/使用说明已按证据同步，技术字面值显示准确；没有用状态回写掩盖过期现状或未解决的契约冲突
- 未决问题与文档偏差已回报
- 实施前已核对相关库 skill、API 文档及既有实现，复用选择或能力缺口有依据
- 如产出或修改了可复用库/工具，随库 skill 与 API 文档、引用已同步；示例未验证的部分已说明，新建或迁移 skill 的注册需求已告知用户

## 禁止事项

- 无设计文档直接编码
- 跳过单元测试或推迟到最后再统一补
- 写伪代码、留 TODO 占位、用 mock 假数据冒充实现
- 修改设计文档以外的模块或做"顺手重构"
- 超出用户授权范围修改既有代码
- 省略必要公共契约或非显然逻辑说明，或用模板化注释代替清晰实现
- 自动 commit / push / 创建 PR
