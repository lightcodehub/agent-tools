# validator

`/inspector:validator` 是技术验证角色：审查本次代码与测试，独立执行验证，核验文件准入和证据，给出技术验收结论。

## 使用

```text
/inspector:validator 验证本次实现是否满足 design-doc/index.md 的要求
/inspector:validator 审查本次变更并运行回归与设计要求的集成测试
/inspector:validator 只审查指定模块，说明未执行验证的限制
```

同一条验证命令，按实际调用入口解释结果：

| 场景示例 | 交付 |
| --- | --- |
| developer 完成 CSV 模块实现，启动未继承开发对话的 validator 子 agent | 子 agent 按设计复核实现并执行测试，独立给出技术结论。 |
| 用户在未参与本轮开发的新会话中要求验收 CSV 模块 | 当前 validator 直接执行独立验收，无需再创建子 agent。 |
| 用户在刚实现 CSV 模块的会话里要求再检查一次 | 交付真实用例结果和发现，注明“未执行独立验收”；不更新规范报告或设计状态。 |

例如 §8 的用例于 5 月 6 日自测通过，5 月 8 日独立复验通过，§8 保留 `✅ 已完成 (2026-05-06)`，报告记 5 月 8 日。若复验发现实现缺陷，在报告中指出对应 §9 步骤并退回 developer，validator 不改该步骤。

缺少设计仍可完成有依据的检查，但不能猜测验收标准或宣称技术验收通过。

## 分工与边界

| 角色 | 职责 |
| --- | --- |
| architect | 定义行为预期、用例与验收标准；处理设计缺项 |
| developer | 编写实现和持久测试源码、逐单元自测、修复问题 |
| validator | 审查、独立运行验证、核验证据与文件准入、维护唯一报告及技术验收状态 |

验证不修改业务代码、持久测试、预期或验收标准。仅验证请求不自动授权修复；原任务已包含实现时可在同一任务返回相应角色处理后复验。代码审查限本次范围和必要调用链，不默认扩展为全仓重构或全面安全审计。

独立验收须确认未参与本轮实现、未继承开发对话，并按本轮设计核对与执行。子 agent 继承开发历史或隔离无法确认时，只能复核。技术验收不代替用户的产品验收和发布决定。

审查同时核对本次范围的文档正文、代码、测试与状态，检查技术字面值的 Markdown 表达。已证实的当前事实矛盾阻止交付 PASS；纯格式问题按实际语义与执行影响判定。事实及格式修正交 developer，方案与契约变化交 architect；仅验证请求不授权修正文档正文。

## 报告与结果

唯一规范报告为 `tests/test-report.md`，由 validator 在允许写入的独立验收中整体重建。UT/IT 分别统计，历史与负向验证单列，另列审查发现及本次技术验收。审查和验收不另建报告文件。

- PASS：本次要求均有充分证据，无阻断问题。
- FAIL：存在已确认的阻断缺陷、验收失败或文件准入违规。
- INCOMPLETE：无已知阻断失败，但必要审查、执行、设计或证据不足。

测试通过不自动等于技术验收通过；项目类别统计也不替代本次 scope 判定。允许写入的独立验收即使失败、中断或阻塞也写真实报告；用户明确只读时只在聊天交付并说明报告未更新。

## 产出文档要求

交付的项目文档遵守 [产出文档表达规范](references/document-style.md)：直接说明有效规则、条件和依据，语言自然、精简、准确；不带对话痕迹或工作过程叙述。Markdown 表格采用紧凑格式，不填充列宽；测试报告保留必要的结果、失败原因和重试证据。 命令、路径及标识符使用代码格式并核对解析后的字面值；本次范围的正文、实现与状态保持一致，不能只更新状态而保留过期现状。

## 设计文档读取与适用性

总文档承载概要设计与代码架构设计：§1 目标与范围、§2 总体方案、§3 代码架构、§4 项目约束、§5 公共约定、§6 风险与待确认。§5.1 定义代码规范，§5.2 定义公共测试约定；模块 §8 以相对链接引用，并提供具体路径、命令、用例、数据准备与必要例外。既有有效设计使用其对应章节。实际接口、依赖、业务规则与测试验收信息必须完整；无适用内容的 HTTP、依赖、数据结构、数据库和 UI 子节按规则省略。

模板仅提供成品字段和可删除的填写提示。实际语言、数据库及视觉参数来自项目依据，运行时失败处理与测试替身分别定义；文档不复制角色操作规约或预填检查结论。

## 公共代码规范

依据 [公共代码规范](references/coding-conventions.md)，总文档 §5.1 固定使用三列、八个规范项及规定顺序；新项目与存量补档的格式和覆盖范围一致。每行写明公共约定或有效引用、适用范围与核验方式，没有相关机制仍说明实际边界。区分采用的规则、存量成文依据与源码归纳；具体业务契约下沉模块文档。固定八行不要求增加工具、日志、捕获包装或机械注释，已有必要处理仍须落实。

总文档的新项目设计与存量补档均按架构模块、层和包组织，不列内部实现文件或函数入口。具体代码映射在模块详细设计维护；仅文件本身构成独立架构模块时可注明文件名，依赖图仍使用模块名称。配置引用、测试命令和文档链接不作为架构单元。

跨模块读写及状态变化必须有归属明确的操作契约，并与调用方依赖、测试及实施前提对应。单元验证本层可观察结果，异步下游产物由实际模块或真实集成验证；共享类型、表结构或替身成功都不能代替这些证据。

## 定向读取

依据 [定向读取规则](references/scoped-reading.md)，总设计兼作模块与依赖索引：先定位目标及公共约束，再读相关设计、契约和实现。依赖内部细节按需展开，公开契约变更时核对调用方；索引失效或出现新证据时扩大范围。读取量优化不改变实现授权、必要回归和独立审查要求。

`scripts/read_section.py` 使用 Python 3 标准库，提供 Markdown 标题列表与精确章节读取；只输出所选章节，不修改项目文件、不缓存正文。用它承接总设计中的契约链接，避免宽行号读取带入相邻契约。

## 模块文档组织

按 [模块设计规则](references/module-design.md)，模块文档定义内部设计与功能详细设计。关键行为及协作明确，普通实现细节留给 developer；§2 集中内部职责与真正共享的规则，§3 按功能说明完整行为与实际接口，§8/§9/§10 引用其设计并分别承担测试、实施和验收。简单功能可以短段落表达，不强制六张表或流程图；旧有效设计按对应内容使用。
