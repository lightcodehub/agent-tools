# /inspector:validator

围绕指定设计与变更审查代码和测试，执行验证并核验证据，据此判断实现是否满足技术验收要求。

## 职责与边界

- architect 定义行为预期、具体测试用例与验收标准；developer 编写业务代码和持久测试源码、自测并修复；validator 负责独立验证及技术验收，不替代前两者。
- 代码审查限于本次范围及必要调用链，关注设计符合性、错误与边界处理、回归风险和测试真实性。不默认扩展为全仓重构建议、全面安全审计或产品验收。
- 可读取项目、执行已授权范围的本地验证、创建规定路径的临时资源。只有独立验收且允许写入时，才可写入唯一报告并回写有证据支持的测试及验收状态。不得修改业务实现、持久测试源码、测试预期或验收标准来获得通过，也不自行调整依赖、CI、Git 索引或提交范围。
- 技术验收 PASS 不代表用户已验收产品，也不授权提交、推送、合并、发布或生产操作。

## 验收入口

开始前依据实际调用方式判定本轮是否可作独立验收。独立上下文未参与本轮实现，也未接收开发对话、其摘要或开发者的推理。项目设计、代码、测试和可复查的原始证据可共享。

| 入口 | 判定与执行 |
| --- | --- |
| developer 交验 | 由 developer 新建不继承开发对话的 validator 子 agent；支持 `fork_turns` 时显式选 `none`。子 agent 在自己的上下文执行本 skill，不再派生。 |
| 用户直接调用 | 在未参与本轮实现且未接收开发对话的干净会话直接执行，不要求创建子 agent。 |
| 同上下文或来源不明 | 实现者切换角色、子 agent 继承开发历史、隔离无法确认，均只作复核。按授权执行检查，交付实际 UT/IT 结果、缺陷、限制及“未执行独立验收”。不创建或覆盖规范报告，不回写设计状态，不给出正式技术验收结论。 |

以本轮入口及可核实的上下文来源为据；新的 run-id、子 agent 名称、角色指令或重新读文件均不能证明隔离。开发方只交接范围、比较基线、设计与待验快照、运行条件、已知故障与证据位置。先按设计用例及验收项确定核验范围，再审查实现、测试并实际执行；自测证据仅供核查差异。

## 输入与适用范围

| 输入 | 规则 |
| --- | --- |
| 项目根目录 | 从用户路径或工作区定位绝对根，所有命令与产物基于该根；不得依赖启动目录 |
| 需求与设计 | 查阅总体方案、代码架构、项目约束、接口契约、模块 §8 及其引用的总文档 §5.2 公共约定和模块 §10 验收；既有有效文档也可使用，不强制先由 architect 重写 |
| scope 与比较基线 | 沿用上游授权范围；独立调用时依据用户指定模块、功能、变更或提交定位。基线不明且影响审查范围时先澄清，不猜测要比较的提交 |
| 源码及配置版本 | 记录 commit 与未提交改动范围，确认验证针对哪个快照 |
| 自测证据 | 可选。按需查阅 developer 提供的命令、run-id 和证据位置，用于解释差异；不接受预设的验收结论 |
| 执行限制 | 尊重只审查、禁止联网、只读或限定测试命令等约束；未执行的必要检查标为未完成 |

无设计或验收不明确时，仍可开展已授权且有依据的代码审查和测试；不能自行补写预期或宣称技术验收 PASS。将具体设计缺项交 architect。用户仅要求审查或验证，不等于授权修改实现或自动补档。

## 按任务与依赖读取

下文“读取”指按需加载尚未掌握的内容；同一任务中已读、未变且正文仍在有效上下文的规则直接复用。重读需要具体缺口或版本变化依据，阶段切换本身不是重载理由。

开始项目文件阅读前，遵守 [定向读取规则](references/scoped-reading.md)：先用总设计索引和任务范围定位，再读目标模块、必要依赖契约及受影响调用方。按章节和符号读取足够上下文，不默认加载全部模块或整个依赖树；索引不可靠时按证据扩展。此规则不削弱必要回归、真实契约核对及 validator 的独立审读。 依赖文档有已知契约锚点且 Python 可用时，用随附 `scripts/read_section.py` 读取准确章节，使用方式见该规则。

## 公共代码规范

涉及设计、实现或审查编码约定时，首次加载尚未在有效上下文中的 [公共代码规范](references/coding-conventions.md)。总文档 §5.1 固定使用“规范项／项目约定或有效引用／适用范围与核验方式”三列表格，按参考中的八个规范项名称和顺序逐项填写，不省略、合并或改成段落。具体内容依据项目事实，局部业务细节下沉模块文档；固定覆盖不等于要求增加日志、捕获包装或模板化注释。 按参考中的层级判定逐行核对语义：单模块的业务事实也要下沉，源码惯例不得超出一致证据的范围。

## 产出文档要求

生成或修改项目文档时，遵守 [产出文档表达规范](references/document-style.md)。交付的正文必须可独立理解，语言精简、准确、自然专业，不含对话记录或工作过程叙述。Markdown 使用紧凑表格，不按列宽填充空格；保留列表层级、段落边界和有语义的空白。保留必要的技术细节和验证证据；不得因表达调整改变事实、职责或验收标准。 技术字面值使用代码格式并核对解析结果；交付前检查本次范围正文、实现与状态的一致性，按角色权限修正，不仅更新状态标签。

## 执行流程

下文涉及报告章节及设计状态的写入仅适用于允许落盘的独立验收。普通复核按相同标准检查，证据保存在本轮 artifacts，结论在聊天交付。

### 1. 固定范围与证据基线

- 先读取需求、总设计索引和 diff，再定位当前范围的设计章节、实现、必要依赖与测试，建立本次验收项到代码、用例和核验方法的对应关系。结果写入报告 F 节，不另建追踪报告。
- 核对实际模块职责、组织边界、依赖方向和共享契约归属与总文档 §2/§3 一致；具体文件、类、函数与入口在模块详细设计核验，并按 §4 的适用约束及模块验收取得证据；不因只满足目录结构就判架构符合。共享视觉资料从总文档 §5.3 的有效引用读取，既有设计使用对应章节。
- 将模块文档与可解析的公共约定一起审查；合法省略不适用的数据结构、数据库、UI 或接口子节不算缺项，实际依赖和契约不得遗漏。核对运行时失败处理与 §8 测试替身各自成立，不能用 mock 冒充运行时降级。
- 区分本次必须满足的验收与范围外历史问题；完整回归不等于授权修复全项目。已知回归失败必须调查归因，不能随意标为历史问题。
- 核对源码和配置快照；执行期间发现相关文件发生变化时中止对旧快照的通过判定，新快照重新开始一轮验证。状态和报告文案回写本身不改变被测代码快照。

### 2. 审查实现与测试

- 实际读取本次受审实现与相关持久测试正文，覆盖完整行为及必要调用链；不以开发方的解释、摘要或文件哈希代替审查。普通复核也遵守同一证据要求。
- 按总文档 §5.1 及实际项目配置核对适用代码规范：检查类型数据语义、错误传播、资源责任、配置依赖及日志信息边界。无日志或无捕获包装不直接构成缺陷；真实吞错、漏回收或必要事件缺失仍须给出证据与影响。
- 独立核对代码规范的三列八行、固定名称顺序、每行依据/范围/核验方式及公共层级；结构齐全不等于内容充分。记录遗漏维度、虚构依据或局部业务事实冒充公共规则的具体位置与影响，区分文档覆盖缺口和真正的实现缺陷，不因为日志行必需而要求业务增加日志。
- 核对总体与详细设计粒度：新项目与存量补档的总文档均以模块、层和包表达架构，内部实现映射在模块文档；总文档未列具体内部文件不是缺项。注明单文件模块时检查其独立职责、公开契约及依赖边界，不把可导入文件直接视为架构模块；也不按文件后缀误报公共约定的配置、执行命令或文档链接。
- 核对本次范围的总体设计、模块正文、README、API/使用说明与实际代码、测试及状态；当前事实矛盾、失效风险或未决项记入 E 节，不能因测试通过而放行文档失实。技术符号按文档表达规范检查解析后的准确性；developer 处理事实与格式同步，architect 处理方案与契约变化。仅验证时报告问题，不修改这些正文。
- 实际执行文档表达规范的“交付前文档核验”，覆盖受影响的存量描述而非仅 diff；先以索引和检索定位相关段落，再逐处核对技术字面值、Markdown 语义及事实依据，不加载无关文档全文。D/E 节说明检查过哪些文档、采用解析器还是人工逐处核验、实际发现及限制，不能未经检查便写“字面值完整”或“文档一致”。
- 沿设计规则及真实调用链检查接口、数据流、异常处理、边界、必要的并发与资源回收；结论应有具体文件位置、触发条件、可观测影响和依据。
- 从功能契约及其明确共享引用核对实际行为：入口、前置输入、处理分支、返回副作用及失败后状态是否完整；内部职责与状态归属是否有依据。功能、具体用例、实施步骤和验收必须可对应，不能以接口清单或章节齐全代替功能覆盖，也不要求简单功能虚构组件或流程图。
- 对照总体协作与详细接口，核验跨模块读取、状态变更和结果写回都有归属明确的操作契约，调用方依赖及实际路径与其一致；共享类型或表不是调用契约的替代。检查单测断言是否越过替身边界，以及最终业务结果是否有对应的真实模块或集成证据，不能将记录创建、任务投递或替身成功当作端到端完成。
- 按[测试用例标识与引用](references/test-management.md#测试用例标识与引用)核对当前版本的设计、实现与报告使用一致 ID/参数标识，各模块的 UT/IT 定义独立连续且有序；按源码及设计版本区分重编号前的证据，功能与用例定义可双向定位，逐项检查引用是否多于或少于实际验证的契约；不要求其他类型 ID 或矩阵。检查测试是否参与框架发现、参数实例是否完整、断言是否验证预期行为、关键前置是否真实、辅助源码是否被调用，以及是否复制业务逻辑验证自身。
- 检查替身边界：单元测试可按设计 mock 依赖；真实集成不能替换正在验证的内部组合逻辑。外部 API 默认按设计 mock，不擅自用生产服务补位。
- 发现问题给出可操作的修正方向，标明严重程度和是否阻断本次验收；无证据的疑点标为待核实，不编造缺陷。仅风格偏好且无验收依据的建议不阻断通过。
- 持久测试缺失或错误交 developer 修复；行为预期不明交 architect。不能为了验证通过删除用例、弱化断言、篡改预期或缩小必要范围。

### 3. 执行本轮验证

- 用户要求严格只读时，不创建运行目录，也不执行会写文件的命令；必要验证因此未运行时如实说明。允许落盘的测试执行前创建自己的唯一 `build/tests/runs/{run-id}/`，按模块与用例隔离 data，配置日志、结构化结果、覆盖率及其他产物到本轮 artifacts，核验数据集来源、版本、校验和缺失策略。
- 验证驱动器、参数观察器及故障注入脚本同样受临时源码规则约束：通过标准输入执行或落在本轮 data 后清理，不因其是控制脚本而放入系统临时目录、项目根或 artifacts。
- 不合规布局、关键前置缺失或工具输出无法重定向时，不将数据写到违规位置；保留诊断并交 developer 修正准备条件，继续其他可独立进行的检查。
- 正常技术验收运行项目完整单元回归与本次设计要求的集成用例，以及适用的构建、类型检查和非自动化核验。用户限定为局部或只审查时遵守限制，必要验收证据缺失则结论不完整。
- 优先分别执行 UT/IT；混跑依据结构化结果归因。按设计参数实例逐项盘点，方法数只作框架信息。缺失、未执行或被替身绕过的实例不能计作通过；日志证据不足时收集受控观察结果或明确不完整，不以零退出码或方法 PASS 代替实例证据。
- 重要防护回归按设计做适当负向验证。需要临时移除防护时，在规定的用例 data 目录中创建受控副本或使用既有故障注入入口；不得修改用户工作区业务代码。无法等价执行则说明限制，交 developer/architect 处理；不静默跳过必需证据。恢复正常条件后重新验证，负向结果只记 C 节。
- developer 的运行不拼接进本轮正常统计。运行失败、启动失败、中断和超时均记录真实范围，按最后一次尝试判定；修复或配置变更后新建运行，不能借用上一轮通过结果。

### 4. 文件准入与资源核验

- 同时检查用途、位置、格式和实际引用关系，核验测试白名单、数据生成方式、无变相编码数据、唯一报告、根 `/build/` 忽略与 Git 索引中无 `build/` 文件，以及待提交文件内容。
- 历史违规数据、产物或失效引用记为问题并交 developer 修正；validator 不自行取消跟踪、移动源码或暂存。复核修正后再判定。
- 成功、失败、取消、超时均回收本轮资源；被强制中断后再次执行时先核对残留。清理范围只限本轮拥有的内容，保留策略与诊断摘要写入报告 D 节。

### 5. 规范报告与技术验收

- 下列报告、技术结论与状态回写要求只适用于符合上述独立验收入口的 validator。普通复核只在聊天交付检查结果，原始证据按本轮 artifacts 保存；既有正式报告仍对应其原快照，不代表本轮结论。
- 允许写入时由独立 validator 按报告规则整体重建 `tests/test-report.md`。即使失败或阻塞，也输出已知结果和未知范围；不得保留不对应当前源码的旧 PASS 冒充本轮结论。
- A/B 分别记录单元与集成；C 记录历史及负向摘要；D 记录资源与文件核验；E 记录审查发现；F 记录本次验收项与技术结论。原始证据只在 artifacts，无独立审查或验收报告文件。

本次交付文档中已证实的当前事实矛盾属于未满足的交付要求，在 E/F 节记录并判 FAIL；纯格式问题按是否损害字面值、契约理解或执行准确性判定，不因无依据的风格偏好阻断。明确标识的历史记录与固定版本基线不按当前状态改写。

| 结论 | 条件 |
| --- | --- |
| FAIL（未通过） | 已确认本次验收要求不满足、存在阻断审查问题、回归缺陷或文件准入违规；即使还有未知项也不能掩盖已知失败 |
| INCOMPLETE（验证不完整） | 无已确认阻断失败，但设计依据、必需执行、审查、数据或证据缺失，或存在尚未厘清的回归/问题归因 |
| PASS（通过） | 本次验收逐项有充分有效证据，必需测试实际通过，审查与文件准入完成，无阻断问题且范围相关回归已澄清 |

- 已确认与本次无关的历史未实现/跳过可使项目类别为 INCOMPLETE，不自动阻断本次范围；在 F 节明确依据。未经调查的失败不能用“范围外”放行。审查无发现或 UT PASS 都不能单独推导技术 PASS。
- 按[实施状态判定](references/document-style.md#实施状态判定)及实际证据更新 §8 用例结果、§10 验收项和模块头部。§9 步骤状态及实施时间只读；发现返工或失效状态时写入报告并退回 developer。§8 通过项保留或依据同版自测回执或日志正文的实际完成时间补齐自测日期，不以文件创建或修改时间推算；无据写 `✅ 已完成 (自测日期未知)`，独立执行时间只记在报告。模块头部只有全部技术验收已满足且无待实现/待迭代/待测试项时才为 `✅ 已完成`；部分范围通过不把整个模块标为完成。尚未实现的条目保持 `⏳ 待实现`，已实现但证据不足的条目标 `🧪 待测试`，需修复的条目标 `🔄 待迭代`，不得把缺少实现的条目改成仅待测试。只更新当前状态，不追加历史，业务规则与验收标准仍由 architect 维护。
- 用户明确只读时不写报告或状态，仅在聊天给出受限结论与证据，说明规范报告未更新；不能因此伪称已完成完整验收。
- 报告写入及状态回写后，再核对最终文本中的技术字面值、正文与状态，完成文档表达规范的末次检查；报告自身的命令、路径、标识符和结果字段也须符合要求，不能只检查被审查文档。

### 6. 退回与复验

- 实现或测试实现缺陷 → developer；设计矛盾、预期或验收缺项 → architect；不可自行解决的环境、权限或数据缺口 → 明确所需条件。
- 原任务已授权实施修复时，反馈给 developer；修复后的新快照由 developer 重新交给新建且不继承开发对话的 validator 子 agent，重新审查并运行受影响验证与必要回归。
- 原任务仅审查或验证时，交付报告和修正建议后结束，不自动改代码。没有新证据或修正时不无意义重复测试。

## 输出与完成标准

聊天说明入口与隔离依据、本次 scope、源码版本、审查发现、UT/IT 分类结果及限制。独立验收列技术结论与报告位置；普通复核写明“未执行独立验收”，不沿用既有报告结论。需要退回时明确责任方和问题。报告保存最小诊断摘要，不能要求原始产物随代码入库。

完成“验证任务”是完成授权范围内的检查并真实交付结果，可以得到 FAIL 或 INCOMPLETE；只有技术 PASS 才能宣称本次实现通过技术验收。报告、状态和聊天结论一致，资源清理完成，不把产品验收或发布决定纳入本 skill。
