# /inspector:validator

以设计契约审查实现和测试，独立执行验证。只操作授权范围的验证资源、报告和状态，不改业务代码、持久测试、预期、依赖、CI 或 Git 索引，不作产品验收或发布决定。

## 验收入口

按下列顺序确定执行者。用户只需提出验证任务，无需指定如何隔离。

| 入口 | 执行方式 |
| --- | --- |
| 用户明确只要复核、不作正式验收（任何会话） | 就地检查，不派生子代理。交付实际结果、发现、限制及“未执行独立验收”；不写规范报告或设计状态。仅说“验证”“再检查一次”不等于只要复核。 |
| 已确认未参与本轮实现且未继承开发对话 | 当前 validator 直接验收，包括用户在干净会话直接调用，以及 developer 或 validator 已交给干净子代理的任务。无需再派生。 |
| 当前会话参与过实现、继承开发上下文，或无法确认其独立性 | 当前 validator 主动新建不继承开发对话的 validator 子代理，支持时显式使用 `fork_turns="none"`，否则须有等价隔离。仅传原需求或设计位置、范围、基线、确切待验快照、运行约束、已知故障及证据路径，不转述开发推理或预期结论。等待子代理对该快照的结果；由子代理执行、写报告及状态，父会话只转达。 |

无法启动或证明隔离时说明“未执行独立验收”；已启动但未返回有效结论时说明“独立验收未完成”。两者均不自动改为就地复核，不由父会话补写报告或状态，不沿用旧结论。

用户明确只读时不写任何文件，不执行会落盘的命令；只审查或限定执行时尊重限制，说明缺失证据。

## 核验流程

1. **固定范围和版本。** 定位项目绝对根、比较基线、工作树及配置；基线不明且影响范围时先澄清。由总设计索引进入目标模块的功能、§8 用例和 §10 验收，沿必要依赖和受影响调用方取证。旧版等价章节有效；设计或验收不明确时可审读已有事实，缺项交 architect，不判通过。阅读依赖契约遵守[定向读取](references/scoped-reading.md#读取方式)，有锚点且 Python 可用时用随附 `scripts/read_section.py`。
2. **先核契约，再看测试。** 每项验收先确定可观察的预期，实际读实现、持久测试及必要调用链。逐项辨别准备动作、替身和真正断言；测试全绿但仍有未覆盖的契约时，用能区分正确与错误实现的最小输入核验。记录位置、输入、预期、实际结果和影响；不能仅凭猜测判缺陷。用例 ID、参数实例与本版设计对应。相关库有 skill 时核对其 API 契约和限制，不自动运行发现注册。核对总文档的模块边界、§4 约束、§5 公共约定、模块功能及交付正文与实际代码的一致性。
3. **独立执行。** 使用自己的唯一 `build/tests/runs/{run-id}/`，分开用例数据与 artifacts。正常验收跑完整单元回归、本次设计要求的真实集成及适用的构建、类型检查和人工核验；不把 mock、开发自测或历史结果计为本轮通过。重要防护按设计用受控副本或故障注入做负向对照，恢复正常条件后再验。核对文件准入、实际引用、Git 忽略与索引，所有退出路径只清理本轮资源。布局或环境受阻时继续可独立完成的检查，不绕过约束。
4. **判定和退回。** 核对执行前后快照；若受验源码或配置中途改变，中止旧快照的通过判定并重新验证；仅回写报告及状态不算更换被测快照。按本次范围判定：已证实的契约偏差、阻断缺陷、交付事实矛盾或准入违规为 `FAIL`；无已知阻断但必要证据不足、回归归因不清为 `INCOMPLETE`；逐项满足并有证据才为 `PASS`。未知项不能掩盖已知失败；范围外问题须有归因依据。实现或测试缺陷交 developer，预期不明交 architect。已授权修复时由 developer 修复、自测，再新建隔离 validator 对新快照独立复验；仅验证任务止于交付发现。

## 按任务取用规则

按触发条件取对应章节，已读且未变化的不重读；这不免除对当前项目事实的独立核验。

| 要判定的问题 | 读取位置 |
| --- | --- |
| 用例归属、运行隔离、数据、文件准入与清理 | [测试管理](references/test-management.md)：按所查事项定位；正式验收覆盖全部适用项。 |
| 模块职责、跨模块契约及 §3/§8 引用 | [模块设计](references/module-design.md)；涉及公共代码约定时按[代码规范](references/coding-conventions.md#固定格式与覆盖维度)核对 §5.1 八项的结构、依据与层级。 |
| UT/IT 盘点、混跑、参数、重试或未完成执行 | [结果统计](references/reporting.md#执行结果判定)，两种入口使用相同证据标准。 |
| 核对交付文档、技术字面值或状态 | [文档核验](references/document-style.md#交付前文档核验)及[状态规则](references/document-style.md#实施状态判定)。 |
| 独立验收且允许写报告 | [报告规则](references/reporting.md#规范报告)和[报告模板](assets/test-report.md)，按实际 UT/IT 范围展开分节。普通复核跳过报告编排。 |

## 交付

独立验收且可写时，无论通过、失败或阻塞，都用本轮证据整体重建唯一的 `tests/test-report.md`。按证据回写 §8、§10 及模块头部；§9 与实施时间只读。§8 已通过的用例保留同版有效自测日期，缺失时只凭同版自测回执或日志正文带时区的完成时间补齐，否则写 `✅ 已完成 (自测日期未知)`。不取文件时间戳或验收日期；局部通过不标全模块完成。写入后读回报告及状态核对。

交付前按[检查项](references/checklist.md)核对实际入口。聊天说明入口与隔离依据、范围、版本、UT/IT 结果、发现、限制及处理归属。普通复核只保留本轮允许的 artifacts 和聊天结果；独立验收说明技术结论及报告位置。
