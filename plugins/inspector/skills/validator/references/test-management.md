# 测试目录、数据与运行产物规范

本规范适用于设计、实现、测试、报告生成和经用户授权的代码提交。architect、developer 与 validator 各携带同文副本，以便插件独立分发；修改时同步三份。

## 1. 根目录与固定布局

所有路径相对于被操作项目的根目录解析，不依赖命令启动时的当前工作目录。设计须明确根目录定位方式；执行时先解析绝对根路径，再显式设置工具 root、工作目录和所有输出路径。不得把 skill 安装目录当作项目根目录。

```text
项目根目录/
├── tests/
│   ├── {module}/
│   │   ├── unit/                 # 单元测试源码
│   │   ├── integration/          # 集成测试源码
│   │   └── support/              # 模块测试辅助源码
│   ├── support/                  # 跨模块测试辅助源码
│   └── test-report.md            # 唯一规范报告
└── build/
    └── tests/
        ├── runs/
        │   └── {run-id}/
        │       ├── data/{module}/{case-id}/
        │       └── artifacts/
        └── datasets/{dataset-id}/{version}/
```

- 模块名称必须对应设计模块；跨模块集成测试归发起或协调流程的模块，其他模块引用。
- 没有对应内容的目录不创建；`tests/` 下禁止任务、PR、日期或批次目录。
- 测试框架必须配置为执行上述测试源码目录。不得以语言限制、框架默认或现有习惯改变布局；存量布局不符合时，在设计中明确迁移与调用调整，不能仅声明例外后继续。
- 框架配置放项目根目录，不得用配置需求扩大 `tests/` 白名单。`build/` 专用于生成内容，不放需要版本控制的源码。

## 2. tests 文件准入白名单

| 类型 | 唯一允许位置 | 准入条件 |
| --- | --- | --- |
| 单元测试源码 | `tests/{module}/unit/` | 当前语言合法源码，符合框架命名规则，实际参与单元测试 |
| 集成测试源码 | `tests/{module}/integration/` | 当前语言合法源码，验证设计规定的真实集成边界 |
| 模块测试辅助源码 | `tests/{module}/support/` | 被本模块测试实际调用 |
| 跨模块测试辅助源码 | `tests/support/` | 被多个模块测试实际调用 |
| 规范报告 | 仅 `tests/test-report.md` | 统一模板，仅含必要摘要，无完整样本或原始日志 |

未列入白名单的文件一律不得放入 `tests/`。设计根据实际语言与框架逐项列出允许的源码后缀、测试文件和测试名称规则，不能写成“任意源码文件”。准入同时检查用途、位置、格式与实际引用关系；仅有合法后缀不构成放行理由。

辅助源码可构造最小场景、搭建受控替身、调用真实接口探针、生成或编译临时辅助程序、创建和回收资源，必须有实际测试调用。不得收容一次性排查脚本、执行记录或包装后的固定数据；不得复制核心业务逻辑后验证自身，或替换关键内部环节后声称真实集成。测试与辅助代码名称描述行为，问题编号只可用于追踪注释，不能替代模块归属和行为命名。

## 3. 测试数据与隔离

输入与预期输出样本、固定 fixture、快照、黄金文件、JSON/XML/CSV 样本、数据库、图片、音视频及其他数据集，以及测试创建的文件、目录、Socket 等资源，均为测试数据。无论真实或合成，都不得作为数据文件提交。

- 每轮测试开始前建立唯一 `build/tests/runs/{run-id}/`，可由运行器在初始化时创建；使用不会与已有运行冲突的标识（如 UUID），禁止覆盖他轮目录。同一次执行的命令、版本快照、结果和原始日志归档到该 run-id 的 artifacts，不另建仅存证据的兄弟运行目录。
- 每用例独立使用 `data/{module}/{case-id}/`，参数实例与并行执行也必须隔离，不共享可变数据。优先使用框架临时目录机制，将根目录配置到本轮 data，并落实到模块和用例；不能配置时由辅助源码显式创建受控目录。
- 辅助程序的临时源码、编译结果均写入该用例目录，包括测试执行驱动器、证据采集器、探针和故障注入脚本；不能因脚本只负责启动测试或汇总结果就放到系统临时目录、项目根、artifacts、`tests/` 或业务源码目录。不需要文件时可直接通过标准输入执行；需要落盘则使用本轮 data 并按设计回收。
- 固定或大型复用数据只放 `build/tests/datasets/{dataset-id}/{version}/`，默认只读；需要修改时先复制到当前用例目录。
- 设计须明确数据来源、版本、校验方式及缺失策略。数据未取得或校验不通过时按设计失败、`NOT_RUN` 或 `SKIPPED`，不得静默通过，也不得用生产数据补位。
- 只有仓库外路径、跨文件系统等目录位置本身为被测条件且无法在 `build/tests/` 等价验证时，才可使用受控系统临时目录。设计必须明确具体原因、创建内容、隔离与清理方法、哪些结果汇总到本轮 `artifacts/`。不能为方便使用例外，也不能另设仓库内产物目录。

禁止把测试数据移到源码、资源或文档目录、改源码后缀、编码为 Base64/十六进制/大字符串、塞入报告或设计文档。不能以保留证据或被报告引用为由提交。允许源码包含构造最小场景的合成字段、边界值和断言常量，通过构造器生成数据，不隐藏完整预制样本或数据集。生产模块自身需要的资源按生产规范管理，不因测试读取改变归属，也不得为测试再复制到 `tests/`。

## 4. 运行产物与报告

原始日志、JSON/JSONL 事件、JUnit、截图、终端录制、覆盖率、执行回执、统计摘要、源码校验清单、临时构建与安装记录、故障注入原始输出，统一写入 `build/tests/runs/{run-id}/artifacts/`。生成的缓存也应配置到本轮产物目录，不得污染源码目录。

项目只保留 `tests/test-report.md` 一份规范报告，不另建模块、类别或历史报告目录。报告由 validator 独占维护，developer 只输出自测证据，architect 只声明报告路径。用户明确只读时，validator 仅在聊天交付并说明规范报告未更新，不违反只读限制落盘。报告只含本轮命令、环境、源码版本、验证范围、实际用例及分类统计、必要失败原因、重试说明、验证限制、与验收相关的审查发现及技术验收结论及足以理解结论的最小诊断摘要。单元与集成分别统计并判定状态，不合并为一个未定义的项目整体状态；只有盘点完整且项目既无设计集成用例也无实际集成测试时，集成部分才可标为“不适用”，本次未执行不能等同于不适用。历史验证、负向验证和本轮正常测试单列说明，不混合计数。

报告不能成为原始日志或样本容器；引用生成产物不构成其入库许可，删除本地原始产物后报告仍须可理解。长期保留原始产物只能使用已授权的 CI 工件存储，不自动上传。

## 5. 真实性与清理

- 单元断言限于被测单元的真实可观察结果与依赖调用契约；异步投递、记录创建或替身成功不能证明下游产物已生成。完整业务结果由对应模块或真实集成用例承接，调整验证边界时保留需求覆盖，不仅删除原预期。跨模块写回的集成验证保留真实操作契约及归属模块实现，存储驱动替身只承担通用数据行为，不复制业务迁移规则或冒充真实数据库隔离验收。

- 执行前断言关键前置条件真实成立；区分预期错误和 panic、EOF 等无关错误，不把异常退出一概当成预期失败。
- 明确被测逻辑和替身边界；重要防护类回归做适当负向验证。普通类型、范围和错误分支用正常边界及异常用例覆盖，不仅因存在判断语句就安排删代码试验。负向设计须明确故障变体、触发输入和被破坏的可观测契约，并核对变体确实改变目标行为；底层接口仍提供等价保护时，删除显式判断不构成有效变体，不预写其必然失败。设计阶段尚无执行证据时只描述预期，不宣称已证明。负向验证后恢复正常条件，正常验证使用未移除防护的版本，两类结果分开记录。validator 通过受控副本或既有故障注入入口执行，不修改用户工作区业务代码；无法等价验证时记录限制并交相应角色处理。
- 成功、失败、取消、超时均须回收进程、连接、Socket 等资源；使用测试框架清理钩子及运行器退出处理，异常中断后核对并补清理本轮残留。
- 临时数据默认在用例或本轮结束后清理。排错产物保留时明确目录、范围、期限与清理策略；仅清理本次拥有的资源，不误删只读数据集、其他运行目录或用户文件。

## 6. Git 忽略、迁移与提交检查

项目根 `.gitignore` 必须包含 `/build/`。设计交付须规划该约束；developer 自查、validator 技术验收及已授权提交前实际执行以下核验，所有 Git 命令显式使用已定位的项目根目录：

1. `git -C "$project_root" check-ignore -v --no-index -- build/tests/runs/probe/artifacts/check.txt build/tests/datasets/probe/v1/check.txt`：检查最终匹配为忽略规则，不能只看退出码；排查否定规则；这两个探针不能替代实际路径核验，还须检查现有及计划写入的 build/tests 路径，确认嵌套忽略文件和否定规则没有放行其他路径。
2. `git -C "$project_root" ls-files -- build/`：索引中必须没有任何 build 文件；`.gitignore` 不会取消既有跟踪。
3. 结合 `git -C "$project_root" status --short`、`git -C "$project_root" diff --name-status`、`git -C "$project_root" diff --cached --name-status`、`git -C "$project_root" ls-files --others --exclude-standard` 及逐文件内容，按用途、位置、格式、引用关系核对所有拟提交项，不能只检查 `tests/` 或扩展名。
4. 检查改名、移动、编码或嵌入源码的绕过；扫描结果只是线索，必须核对实际内容与调用。报告引用、任务归属和证据保留均不能豁免。

已跟踪的历史数据或产物迁入规定位置，保留必要本地内容后逐项取消跟踪，并修正或移除失效引用；取消跟踪产生的删除记录允许提交。需要维护的源码先移出 build，不能以取消跟踪误丢源码。禁止强制添加被忽略内容，禁止整个目录笼统暂存代替逐文件审查。validator 发现不合规时记录问题并交 developer 修正，不自行移动业务或测试源码、取消 Git 跟踪或暂存文件。布局或提交范围不合规时必须先纠正，不能仅在交付说明中告知后继续提交；本规范本身不授予 commit、push 或发布权限。

## 7. 职责与验收

### 测试用例标识与引用

- 每个业务模块以总设计索引中的模块标识作为前缀。单元用例使用 `{module}-UT-{NNN}`，集成用例使用 `{module}-IT-{NNN}`。用例只在归属模块 §8 定义一次。跨模块集成用例使用发起或协调模块的前缀，调用方引用同一 ID。
- 交付设计时按 §8 权威定义的实际出现顺序核对编号。每个模块的 UT、IT 独立从 `001` 起依次递增，三位起，不留空号、不重复、不倒序。功能分组、表格分页和参数实例均不重启编号。只统计定义行，正文引用及其业务顺序不参与序列检查。
- 同一设计版本内用例 ID 稳定。迭代可以整理本次修改模块的编号：已有编号连续时优先按编号排列定义，需要补齐空号或调整用例编排时允许重新编号。先按用例场景、输入、预期和参数标识匹配新旧定义，再一次性更新本版 §3、§8、§9、§10 及其他模块的有效引用，重新展开编号区间核对指向。其他模块的定义保持原号。编号变化本身不改变用例含义或实施状态，也不要求另交对应表。
- architect 负责当前设计及跨文档引用。developer 实施时同步测试名称、标记或发现映射中的旧引用。validator 按实际设计与实现版本验证并生成报告。旧报告和已归档执行证据按原版本解读，重编号后的相同数字不能继承旧结果。
- 参数化用例保留主 ID，并定义能区分实际输入的参数标识；实现、执行证据与报告沿用同一 ID 和参数标识。用例定义、引用和参数实例不能被混算成多个用例身份。 参数实例是按约定前置独立执行的输入变体；同一场景中依赖共享状态的连续操作、多个断言或重复调用仍是一个用例实例，不能因为出现多个值就拆成参数实例。步骤标签如有需要须明确为同一实例内的步骤，不改变隔离方式、输入顺序或统计口径。
- §8 每条用例说明所验证的具体功能或共享规则，并给出可定位的文档章节/锚点；同组归属相同时可在组头统一说明。跨功能或跨模块共享用例只定义一次，明确各功能对应的实例或断言，不能仅凭前置操作或方法名猜测归属。
- 以每个实例的被测动作和预期断言确定覆盖范围。准备数据、建立初态、观察其他操作的结果或清理资源，本身均不构成对所用功能的验证。只有断言明确检验该功能的契约时才归属它。同一场景内逐个区分断言。例如，读取记录以确认另一操作失败后数据未变，验证的是失败隔离。若同一用例还明确断言查询返回当前存储的同一对象，或对非法输入返回特定错误，则把这个断言同时归到查询功能。按各操作的返回值、对象身份、错误及状态断言逐项反查，即使用例标题只点名一个功能。仅校正归属时，沿用已有参数标识及其生成规则。
- 以 §8 的断言归属为准逐功能核对 §3 引用集合：展开编号范围、组链接和参数分支，剔除多引并补齐漏引。编号区间仅适用于区间内每个用例的全部实例都验证该功能的情况。部分实例适用时，将该 ID 单列并指明入口或参数，或直接引用 §8 已限定分支的归属说明。混合归属表可作为导航，但须标明实际适用子集，或直接链接 §8 中已经筛好的归属说明。§9 的运行范围与 §10 的验收证据分别标明。修正错误引用时保留原用例及断言。
- 功能小节可直接引用 ID，也可链接带归属的用例组或表；目标必须显式列出具体 ID，并足以辨认本功能适用的用例。组名、概括性“全部测试”或链接本身不代替 ID。§9/§10 的用例引用也须可定位到权威定义；跨文档引用附所在文档及准确章节/锚点，不只提供孤立编号。
- 本规范只要求测试用例 ID，不要求新增需求 ID、设计项 ID、功能 ID，也不要求产出追踪矩阵。项目已有标识和资料按实际需要引用；没有编号的需求或功能可用名称、要点及文档位置说明关系，不为填表发明编号或额外文档。

§8 保留具体输入、前置及可断言结果，§9/§10 引用功能与用例。不得因去重只写“符合设计”，也不把测试预期当成唯一业务规则定义。

设计在总文档 §5.2 集中维护公共测试约定；模块 §8 以有效相对链接引用，补齐具体源码与辅助源码路径、模块命令、数据准备、前置断言、被测逻辑、替身边界及必要例外。合并后的设计必须明确后缀与命名、框架配置、根目录、data/artifacts/datasets 路径、数据集来源/版本/校验/缺失策略、隔离清理及验收和适用的防护验证；去重不减少这些要求。既有有效设计可使用对应章节，不强制仅为编号而重写。不规划数据入库或独立报告目录。

developer 按设计编写实现及测试、逐单元自测，配置数据与产物路径，按白名单和 Git 索引自查，修正失效引用并提供自测证据；不维护规范报告。validator 审查实现与测试、独立运行回归和集成验证、复核文件准入，独占更新唯一报告与技术验收结论；不得通过修改业务代码、测试预期或验收标准取得通过。developer 交验必须启动不继承开发对话的 validator 子 agent；用户在未参与本轮实现、未继承开发对话的干净会话直接调用 validator 时，就地独立验收。与实现同上下文、继承开发对话或来源无法确认时，只能复核：在本轮 artifacts 和交付摘要记录实际测试结果，标明“未执行独立验收”，不创建或覆盖规范报告，不回写设计状态。双方分别为自己的运行创建唯一目录、隔离和清理资源。技术验收不代替产品验收或发布决定。验收须同时满足：源码准入与真实调用成立；数据和产物位置合规；build 被忽略且无跟踪文件；无数据变相入库；唯一报告无需原始产物入库仍可理解；失败、中断、取消后的隔离和清理与正常执行一致。
