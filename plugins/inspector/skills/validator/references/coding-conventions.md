# 公共代码规范

用于设计、实现和审查消费项目的公共编码约定。architect、developer、validator 各携带同文副本。新项目与存量补档使用相同格式、覆盖维度和内容层级；具体约定依据项目事实，不套用统一的业务规则或技术选型。

## 依据与归属

- 先读取项目现有规范、实际代码、格式化/静态检查/类型检查配置及相关库的接口说明。现有配置能完整表达的规则直接引用，并列出真实检查命令；不得虚构配置、工具或执行结果。
- 总文档 §3 定义代码架构，§4 定义项目约束，§5.1 仅记录项目公共编码约定。模块特有的字段取值、参数校验、类型或构造器行为、错误码、事务状态、恢复流程和日志事件在模块文档维护；总表保留公共原则及有效引用，不复制局部实现事实或业务契约。
- 只补充影响本次实现的公共选择。类型语义、错误传播、资源责任或配置含糊且影响正确性时，由 architect 澄清并写入设计；普通风格细节沿用已有项目及语言规范，不为填满表格追问或引入工具。
- 已有代码用于确认现状，不将有证据的缺陷提升为规范。设计与实际接口冲突时提供依据，按角色职责处理，不直接削弱要求。
- 新项目明确采用的规范及设计选择，区分拟配置工具与已存在工具。存量补档优先引用已核实的成文规则和配置；从源码归纳的惯例须说明依据与范围，不能把单个实现、缺陷或无依据的建议写成全项目规范。未发现明确规则时如实说明已知依据与缺口，不能笼统写“沿用当前源码风格”代替具体约定。
- 源码归纳须在声称的适用范围内一致成立；仅部分文件有某种命名、注释或实现方式时，不能据此写成“全项目”惯例。尚未形成统一约定的维度如实写明缺口、已有有效依据与实际核验范围，不为填满八行补造制度。

## 公共规则与局部事实的判定

公共规则约束代码如何组织接口、表达类型和错误、使用依赖及维护说明；模块契约定义业务应接受什么输入、返回什么状态及如何执行。即使项目只有一个业务模块，字段校验、特定构造器、存储方式或状态变换也不能因此成为公共编码规则。

逐行检查：去掉具体业务对象和实现手段后，该约定是否仍能作为相应范围的编码原则。若一行实际上在描述某个参数、类、依赖对象或流程如何工作，把事实保留在模块文档，总表只引用契约或提炼有依据的公共原则。不能只把具体对象改成“数据”“资源”等泛称后保留原业务规则。

- “类型与数据约定”写类型表达、转换、可变性和校验责任原则；不写记录或数据对象的实现方式，例如冻结数据类、具体容器布局或构造器是否校验。这些方式即使在多个模块重复出现，也仍在模块数据结构中说明，总表通过契约引用保持可追溯。
- “注释与接口说明”写有依据的说明约定及核验范围。没有成文规则且源码不足以形成统一惯例时，明确尚未形成统一约定，只核对已有说明与接口契约；不要用“现有模块含文档字符串”等集合描述掩盖仅少数对象有说明的事实，也不要求为填表给全部代码补注释。

例如证据不足时可说明“未形成统一注释格式约定；已有注释和文档字符串须与实际行为一致，公共契约见模块 API”，核验范围限定为已有说明与公开契约。已有明确项目规范时应引用真实规则，不套用此缺口表述。

下列示例只说明层级，不是所有项目的默认约定：

| 不放入公共表的局部事实 | 公共表可表达的原则或引用 | 局部事实归属 |
| --- | --- | --- |
| 数量不接受字符串或布尔值 | 不通过隐式转换绕过接口契约，具体输入约束见模块设计 | 模块参数与校验契约 |
| 数据类冻结、构造器不校验字段 | 类型注解不替代契约校验，返回对象的可变性由公开契约约束 | 模块数据结构与构造行为 |
| 通过构造器注入账本 | 依赖使用与生命周期遵循模块契约，复用已明确的公共能力 | 模块依赖及实现映射 |
| 某模块有职责文档字符串 | 如实说明已有注释惯例的范围；未形成统一约定时不推广，核对已有说明与接口一致 | 证据所在模块；总表注明真实核验范围 |

## 固定格式与覆盖维度

总文档 §5.1 使用一张紧凑表格，列名固定为“规范项”“项目约定或有效引用”“适用范围与核验方式”。按下表顺序保留八个规范项，名称不改写，不删减、合并、拆分或另加维度，不用段落或列表替代表格。每行给出实际约定或有效引用，以及对应范围和核验方法；引用已有规范也保留该行。表格齐全只证明覆盖已盘点，不能代替内容与依据核验。

| 规范项 | 应明确的公共内容 |
| --- | --- |
| 规范依据与检查 | 适用的项目/语言规范、已有配置位置、实际检查命令；没有相关工具时说明核验方式，不默认新增依赖 |
| 命名与接口风格 | 文件、类型、函数和变量命名，以及公开接口和内部实现的区分；不重复模块目录和依赖设计 |
| 类型与数据约定 | 项目共享的类型、空值、转换和可变性原则；共用的时间、单位、精度或编码约定仅在有依据时说明，模块特有取值与校验链接详细设计 |
| 错误处理 | 异常或错误返回形式、允许捕获/转换的位置、传播责任；具体业务错误由模块契约定义 |
| 资源与执行 | 实际涉及的文件、连接或其他资源由谁取得与释放；并发/异步、共享状态、取消和超时仅在适用时明确 |
| 配置与依赖使用 | 已有配置入口、校验位置和默认值来源，现有库的使用入口；不在业务代码重复建立配置体系或擅自增加依赖 |
| 日志 | 公共可观测性目的、日志入口、记录边界、等级和字段选择原则及信息保护；具体事件/字段链接模块契约，没有日志需求时不增加日志 |
| 注释与接口说明 | 公共契约和非显然约束、算法意图或取舍的说明方式；使用当前语言和项目规范，不机械地给每个私有函数添加注释 |

没有日志、外部资源、运行配置或检查工具时仍保留对应行，简述实际情况、适用边界和核验方式，不能留空、仅写“不适用”或静默省略。例如仅内存串行调用的项目，资源行可说明无需外部资源释放并通过依赖与调用链审查核验；这不是要求增加资源、日志或工具。未知情况不能冒充不存在，影响正确性的缺口按角色职责澄清，普通风格细节不因填表触发无必要追问。

核验方法必须对应检查对象：测试结果不能代替格式、注释和规范依据审查；无格式化或类型检查工具时说明人工核对范围，不虚构自动检查命令。纯函数无 I/O、原样异常传播、必要资源回收和已确定事件仍须在相应行或其模块引用中明确，不因按需设置具体规则而遗漏。

## 异常处理与资源责任

- 保留接口规定的错误形式和传播行为。自然传播已经满足契约时，不增加捕获包装；仅在需要转换接口语义、执行恢复动作或承担资源/可观测性责任的边界处理异常。
- 不以宽泛捕获吞掉错误、返回默认成功、改变异常类型或丢失必要错误上下文。框架统一处理已经满足要求时，不在每层重复处理同一失败。
- 对本模块拥有的资源按语言/框架已有机制回收，覆盖实际适用的成功、失败、取消和超时路径。释放失败须按模块约定显式处理，不宣称资源已成功释放。清理异常不得隐式覆盖原始业务异常；提交完成后的清理故障与业务失败如何区分，由模块契约明确，不假定已提交结果仍可回滚。
- 类型、参数和状态校验依据真实接口要求设置，不添加与契约无关的防御分支；普通边界测试和重要防护回归按测试规范区分。

## 日志与注释

- 日志按明确需求和模块责任设置，不以“关键路径”名义要求所有函数或所有层记录。纯函数或明确无 I/O 的模块不因编码规范增加日志、标准输出或环境访问。
- 使用项目已有日志入口；需要记录的事件指定责任边界，避免同一异常逐层重复记录。必要日志不能因“不强制日志”而省略；不记录凭据、敏感内容或未经允许的完整输入输出。
- 公共接口说明输入、返回、错误及必要副作用；非显然实现说明原因或约束，不逐句复述代码。不以注释数量替代可读性，也不为明显的私有辅助逻辑制造模板化注释。

## 三角色校验

architect 交付前分别执行结构检查和逐行语义检查：核对三列八行、固定顺序，再按“公共规则与局部事实的判定”核对依据、范围和层级；发现局部事实即下沉并核对原契约未丢失。developer 接收设计时逐维核对，不以“八行齐全”替代规则充分性；旧文档仅格式差异时按文档维护权限定点整理，缺少规则或依据时交 architect 补齐，不重写无关设计或擅自改变已有语义。validator 分别核验结构覆盖、依据真实性和内容层级，再对照实际实现与证据判断；不因没有日志、try/catch 或私有函数注释直接报缺项，也不放过真实的吞错、资源泄漏、必要日志缺失或信息泄露。
