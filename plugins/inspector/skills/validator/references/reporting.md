# 规范报告与结果判定

报告表述遵守 [文档表达规范](document-style.md)：按事实写明结果、原因与限制，不复述对话或排查过程；保留本规范要求的失败、重试及历史证据摘要。

仅符合 [验收入口](../SKILL.md#验收入口) 的独立 validator 可以写入 `tests/test-report.md`。报告信息表注明实际入口及隔离依据。普通复核仅在聊天说明本轮结果、缺陷及“未执行独立验收”，不创建或覆盖规范报告，不回写设计状态；既有报告只对应其原快照。用户明确只读时同样不写报告或状态并说明限制。下述落盘要求只适用于允许写入的独立验收。执行前读取本规则及 [报告模板](../assets/test-report.md)；模板的 A/B 分节在同一文件展开。

- 项目唯一规范测试报告固定写入项目根目录下的 `tests/test-report.md`；全项目只保留这一份规范报告，不创建模块级报告。
- 正常技术验收运行项目完整单元测试集；只审查或限定执行范围时按用户限制执行并如实标记未运行项，并按 [统一模板](../assets/test-report.md) 整体重建报告。A、B 节的正常测试结果只使用同一轮验证数据，不拼接历史运行数据；历史与负向验证仅在 C 节说明，不参与正常统计；多条测试命令记录各自范围、结果和退出码。
- 优先使用设计中分别定义的单元与集成测试命令。若同一命令混跑 UT/IT，必须根据结构化结果确认各类用例及完成情况，按类别归因；不能把混合命令的非零退出码直接当作单元测试失败。
- 同一源码与配置下重试同一测试范围，以最后一次尝试（包括失败、中断或未启动）判定该范围，先前失败单列在重试记录中，不再作为最终失败重复计数；只有最后一次完整执行通过才能判为通过，不能借用此前通过结果。改动源码、配置或测试范围后属于新一轮验证，不能拼接前一轮结果。
- 执行失败、启动失败或中断时也整体重建本轮报告，明确计划范围、实际范围、阻塞原因和盘点是否完整；已知未执行用例标记 `NOT_RUN`。不能枚举的用例数量写“未知”，不能伪造明细或把历史通过结果当成本轮结果。
- 报告是面向人的 Markdown 文档，第一行必须是 `# 测试报告`，随后使用“报告信息”表记录项目、时间、框架、运行环境、测试命令、源码版本、范围、状态和耗时；不得在标题前添加 YAML Front Matter。
- A、B 节按测试类别分别列出业务模块的全部用例及结果，分别提供执行摘要、模块汇总、状态与通过率，不生成 UT/IT 合并总数、通过率或未定义的项目整体状态。只有完整盘点确认项目既无设计集成用例也无实际集成测试时，才省略 B 节并将集成标为“不适用”；未执行或盘点不完整仍须保留 B 节并如实记录。
- 报告必须同时覆盖设计文档中的全部测试用例和本次发现的全部实际测试：设计用例未实现标记 `NOT_IMPLEMENTED`，已有测试未执行标记 `NOT_RUN`，框架跳过标记 `SKIPPED`，执行结果标记 `PASS` 或 `FAIL`；设计外测试标注“设计外补充用例”。
- 设计用例采用对应设计版本权威定义中的 ID 及参数标识关联实现和报告，按模块提供可定位到用例定义的文档章节/锚点，不为报告重新编号或新增其他类型 ID、矩阵；已有设计外测试按“文件路径 + 完整测试名 + 参数标识”识别并注明归属模块，避免与已匹配的设计用例重复计数。发现本次实施范围内的设计漏项先交 architect 补全；范围外历史测试照实登记，不能临时发明设计编号。
- 规范统计以测试实例为最小单位：非参数化用例计一个实例，设计外已有测试同样按实际实例计数。设计用例含参数时，同一测试方法覆盖多个输入时逐实例列出状态，缺失实例计为 `NOT_IMPLEMENTED`，已实现未执行计为 `NOT_RUN`。框架的方法数只能另列为执行信息，不得代替实例总数、PASS 数或通过率。被 mock 掉的真实集成边界不获得真实集成 PASS；未执行的真实参数实例不得记为 0。
- 声称某条日志证明某个参数结果前，核对日志确实包含该参数与结果。框架只输出方法级结果时，优先用框架的结构化结果或位于本轮用例 data 目录的临时观察器补充参数级证据，不改持久测试源码；无法可靠取得时标明证据不足；类别状态按下述 FAIL 优先规则判定，不用 INCOMPLETE 覆盖已确认失败，也不猜测通过或伪称已有记录。
- 各类别盘点完整时，该类别总数等于各模块明细及五类结果数量之和；盘点不完整时单列已知数量，该类别总数和通过率写“未知”。通过率为 PASS 数 / 全部用例数（包括跳过、未实现、未运行）；零用例时写“—”。
- 报告中单元部分及各模块的单元状态按最后一次尝试的单元结果判定：有最终单元失败用例或确认影响单元执行的启动、收集、运行错误为 `FAIL`；否则，有单元跳过、未实现、未运行、盘点不完整、零用例、执行未完成或混合结果无法可靠拆分时为 `INCOMPLETE`；只有非空单元用例集全部实际通过且已完整执行才为 `PASS`。重试前的失败保留说明，执行错误记入详情，不虚构失败用例。
- 混跑时若单元集已确认完整通过，非零退出码仅由 IT 失败造成，则单元状态仍为 `PASS`，IT 在 B 节记为 FAIL；若该失败违反本次验收要求，F 节技术结论为 FAIL；若失败归属不明，保留命令错误并将无法确认的单元结论标为 `INCOMPLETE`，不能猜测通过或失败。
- 本次实施完成度与报告中的单元、集成状态独立判断：范围外未实现或跳过可使对应类别为 `INCOMPLETE`，不要求扩大实施范围；本次范围内的用例及验收必须通过，回归失败必须调查并说明，不能据此宣称项目整体通过。
- 历史验证、负向验证和本轮正常验证分开说明，不混合计数；报告不得收录完整样本或原始日志，链接产物也不授予其入库许可。
- Vitest、Jest、pytest 等工具生成的 JUnit、JSON、coverage 写入本轮 `artifacts/`，只作为报告数据来源，不能替代 `tests/test-report.md`。覆盖率不可用时明确写明，不得推测或编造。
- §8.4 集成用例按 `{module}-IT-{NNN}` 在同一报告的按需附节记录命令、结果及原因；不混入单元用例数量、通过率和状态。单元测试 PASS 不代表本次实施已完成，仍需检查设计要求的集成验收。

代码审查发现和技术验收分别写入模板 E、F 节；技术验收结论按 SKILL.md 的规则独立判断，不能用 UT/IT 通过率代替。
